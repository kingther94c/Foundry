# Codex deep-dive

## Summary

openai/codex (the Rust CLI, cloned at main on 2026-08-29) is organized as a headless core ("codex-core") driven by two bounded async queues: clients submit Submission{id, op} (protocol/src/protocol.rs: Op enum — TurnInput, Interrupt, ExecApproval, PatchApproval, Compact, ThreadRollback, Review, Shutdown, RunUserShellCommand...) and receive Event{id, msg} (EventMsg enum: TurnStarted/TurnComplete, AgentMessage, AgentReasoning, ExecCommandBegin/OutputDelta/End, ExecApprovalRequest, ApplyPatchApprovalRequest, TokenCount, Error...), with SUBMISSION_CHANNEL_CAPACITY=512. A user turn spawns a task whose loop (core/src/session/turn.rs::run_turn) repeatedly: drains pending user input queued mid-turn, builds the full conversation history into a stateless Responses API request (store:false, include:["reasoning.encrypted_content"], stable prompt_cache_key per thread), streams output items, dispatches tool calls, and loops while needs_follow_up (i.e., tool calls were emitted or new pending input exists). There is no hard iteration cap; termination is model-driven, bounded instead by context-window token status that triggers inline auto-compaction, by user Interrupt (CancellationToken → TurnAborted), and by error paths that emit Error and break so the user regains control.

Safety is a three-valued decision system that maps directly onto Foundry's PolicyEngine: core/src/safety.rs returns SafetyCheck::{AutoApprove, AskUser, Reject}, computed from AskForApproval {untrusted(UnlessTrusted), on-request (default; "on-failure" is now just a serde alias), granular{...}, never} crossed with SandboxPolicy {read-only, workspace-write{writable_roots, network_access, exclude_tmpdir...}, danger-full-access, external-sandbox}. A separate execpolicy crate holds a rules engine (Decision::{Allow, Prompt, Forbidden}, prefix_rule token-prefix matchers with justification), and user approvals can be persisted as policy amendments (ReviewDecision::{Approved, ApprovedForSession, ApprovedExecpolicyAmendment, Denied{rejection}, Abort}). Commands are segmented at shell operators (|, &&, ||, ;, subshells) and each segment is policy-evaluated independently; commands using redirection/env-prefix/wildcards are never rule-matched (prompts/templates/permissions/approval_policy/on_request.md). Windows went from "no sandbox — approve everything or run full-access" (pre-Sept-2025) to a native sandbox (Mar 2026, hardened May 2026) built from restricted tokens plus dedicated local users (CodexSandboxOffline/CodexSandboxOnline), ACLs, Windows Filtering Platform network deny, DPAPI, private desktops, an elevated helper service, and ConPTY/stdio bridging (codex-rs/windows-sandbox-rs, ~30 modules; WindowsSandboxLevel::{Disabled, RestrictedToken, Elevated}). The sheer size of that crate is itself the lesson: honest trusted-host + strong ASK policy is a defensible V1; a real Windows sandbox is a multi-quarter kernel-adjacent project.

Editing is centered on apply_patch, the V4A envelope grammar (*** Begin Patch / Add File / Delete File / Update File [+ Move to] / @@ context hunks / *** End Patch), chosen over unified diff because it is line-number-free (hunks locate by context search, not offsets), file-oriented, trivially parseable, and trained into OpenAI models; it is exposed to GPT-5-class models as a grammar-constrained "freeform/custom tool" with a Lark grammar (core/src/tools/handlers/apply_patch.lark) so the model emits raw patch text with no JSON escaping, and applied with graduated fuzzy context matching (exact → rstrip → trim → Unicode-punctuation-normalized; apply-patch/src/seek_sequence.rs). Sessions are append-only JSONL "rollouts" at ~/.codex/sessions/YYYY/MM/DD/rollout-<ISO-ts>-<thread_id>.jsonl, each line {timestamp, ordinal?, type, payload} over a RolloutItem union (SessionMeta, ResponseItem, Compacted, TurnContext, EventMsg...), with an explicit persistence policy filter deciding which events are durable; resume replays the file, forking writes a new file that appends a distinct rollout id after the stable thread id. Auth is OAuth 2.0 + PKCE (S256) against https://auth.openai.com with a localhost:1455 callback and public client id app_EMoamEEZ73f0CkXaXp7hrann, tokens (id_token JWT with chatgpt_plan_type/account claims, access_token, refresh_token, optional derived platform api_key) stored in $CODEX_HOME/auth.json (0o600, optional OS keyring); ChatGPT-plan model traffic goes to https://chatgpt.com/backend-api/codex (Responses-compatible), API-key traffic to platform /v1/responses — and wire_api="chat" was removed outright (discussion #7782), leaving Responses as the only protocol, which validates Foundry's Responses-only backend plan. Config is ~/.codex/config.toml with precedence CLI flags > profile > trusted-project .codex/config.toml > user config > defaults, plus admin requirements.toml constraints, [projects."<path>"].trust_level, a [model_providers.<id>] table (name/base_url/env_key/wire_api/http_headers/retries) that is exactly the shape Foundry's swappable ModelBackend needs, and [mcp_servers.<id>] for MCP.

## Designs

### agent loop / turn lifecycle
- **How**: Two-queue architecture: Submission{id, op:Op} in, Event{id, msg:EventMsg} out over bounded async channels (capacity 512). A TurnInput op spawns a task; run_turn (codex-rs/core/src/session/turn.rs:155-602) loops: drain user input queued mid-turn → capture step context → build request input from full cloned history → run_sampling_request (streams Responses API events, dispatches tool calls, records outputs) → returns needs_follow_up. Loop continues while needs_follow_up (tool calls happened or pending input exists); breaks when the model produces a final message with no tool calls; TurnComplete event carries last_agent_message. Interrupt op aborts via CancellationToken → TurnAborted{reason}. No max-iteration cap anywhere (grep confirms no max_turns/max_iterations in core).
- **Takeaway**: COPY the shape: Foundry's loop should be exactly 'while model emits tool calls: execute, append outputs, resample', with an injectable event stream (typed events with a submission-correlated id) separating core from UI. ADAPT: add a configurable soft cap on consecutive tool-call rounds (codex relies on model quality + user interrupt; Foundry's corporate-gateway models may loop). COPY the mid-turn input queue (steering messages drain into the next sampling request instead of being rejected).

### streaming events & UI separation
- **How**: Core emits fine-grained typed events: TurnStarted, AgentMessage(+deltas), AgentReasoning, ExecCommandBegin/ExecCommandOutputDelta/ExecCommandEnd, PatchApplyBegin/End, ExecApprovalRequest, ApplyPatchApprovalRequest, TokenCount, TurnDiff (aggregated per-turn unified diff via TurnDiffTracker), Error, ShutdownComplete. Approval requests are events answered by later ExecApproval/PatchApproval ops carrying ReviewDecision — the loop parks on a oneshot until the decision arrives. The TUI, `codex exec` (non-interactive JSONL output), and app-server (JSON-RPC for IDE extensions) are all thin clients of this one protocol.
- **Takeaway**: COPY: define Foundry's event vocabulary now (turn_started, message_delta, tool_begin/delta/end, approval_request, token_count, turn_complete, error) as a versioned Python enum/dataclass layer, and make approvals asynchronous request/response over the same bus rather than a blocking input() inside the tool — this buys interrupt-during-approval and future GUI/IDE frontends for free.

### tool surface
- **How**: Current default set (core/src/tools/handlers/): exec_command (unified exec: cmd string, workdir, shell, login, tty/PTY, yield_time_ms 10s default — long commands return a session id, max_output_tokens ~10k default, plus approval params sandbox_permissions/justification/prefix_rule), write_stdin(session_id, chars) for interacting with running processes, apply_patch (freeform grammar tool or function form), update_plan (plan/step statuses), view_image, request_user_input, request_permissions, web_search (hosted), MCP tools, get_context_remaining, subagent/collab tools. Older canonical set was shell(command: Vec<String>, workdir, timeout_ms, with_escalated_permissions, justification) + apply_patch + update_plan + view_image. Notably absent: no read_file/list_files/grep function tools — the model does everything through the shell (prompt says 'prefer rg').
- **Takeaway**: ADAPT, don't copy blindly: codex can lean on shell-for-everything because its models are trained for it; Foundry's explicit list_files/search_text/read_file tools are the right call for gateway models not trained on codex conventions, and they make ALLOW policy trivial (reads auto-allowed). COPY exec_command's ergonomics: string command + workdir + timeout + output-token budget with middle-truncation, and the session-id pattern for long-running commands is worth a V2 slot. COPY update_plan — it is cheap and the visible-plan UX is high value.

### apply_patch grammar (V4A)
- **How**: Grammar (codex-rs/core/prompt_with_apply_patch_instructions.md:316-345, parser at apply-patch/src/parser.rs): Patch := '*** Begin Patch' {FileOp} '*** End Patch'; FileOp := AddFile('*** Add File: path' + '+' lines) | DeleteFile('*** Delete File: path') | UpdateFile('*** Update File: path' [ '*** Move to: newpath' ] {Hunk}); Hunk := '@@' [class/def header] then ' '/'-'/'+' lines, optional '*** End of File'. Rules: 3 lines context before/after, @@ headers (stackable) to disambiguate repeated snippets, relative paths ONLY, '+' prefix required even in Add File. No line numbers anywhere — application locates hunks via seek_sequence with decreasing strictness: exact → trailing-ws-insensitive → ws-insensitive → Unicode punctuation normalized (mirrors git-apply fuzz). Parser is deliberately lenient (PARSE_IN_STRICT_MODE=false, kept for gpt-4.1 quirks). Exposed two ways: (a) Lark-grammar-constrained custom tool for GPT-5 models (raw text, no JSON escaping), (b) as `apply_patch` first arg of shell for older models, intercepted in-process.
- **Takeaway**: COPY the full grammar verbatim including the fuzzy seek ladder — it exists because models emit stale context; a strict matcher will thrash. Chose over unified diff because models are bad at line numbers/offsets and JSON-escaping large diffs; V4A is line-number-free and self-delimiting. For Foundry: parse and apply in-process in Python (never shell out), accept the patch as the raw tool-call payload (freeform if the gateway supports custom tools, else a single JSON string arg), and normalize CRLF (codex has NormalizeToLf vs PreserveLineEndings modes — Windows needs the preserve option).

### shell/command execution on Windows
- **How**: Shell detection supports PowerShell (core/src/shell.rs); the exec_command tool description embeds Windows-specific safety guidance (shell_spec.rs:339: never compose destructive ops across shells, verify resolved absolute paths before recursive delete, Start-Process -WindowStyle Hidden). Output is captured with a token budget and middle-truncation (truncate_middle_with_token_budget). PTY via ConPTY; notably features.unified_exec was 'on by default except Windows' for a long time (config reference) because ConPTY was unreliable. Env passed through a shell_environment_policy filter.
- **Takeaway**: COPY the Windows guidance paragraphs into Foundry's run_command tool description nearly verbatim — they encode real Windows failure modes. COPY middle-truncation with an explicit budget and a note of how much was elided. AVOID PTY in V1 (codex itself gated it off on Windows initially); plain pipes + timeout is fine. ADAPT: give run_command an explicit shell parameter defaulting to PowerShell, and record exit code + duration in the tool output.

### approval policy flow (ALLOW/ASK/DENY)
- **How**: Three layers: (1) AskForApproval {untrusted, on-request(default), granular{sandbox_approval, rules, skill_approval, request_permissions, mcp_elicitations}, never} — 'on-failure' collapsed into on-request as an alias. (2) SafetyCheck::{AutoApprove, AskUser, Reject{reason}} computed per action (core/src/safety.rs): e.g. a patch fully inside writable roots auto-approves only if a sandbox can actually enforce it, else asks; under never/granular-off it Rejects with a reason string returned to the model so it can adapt. (3) execpolicy rules engine: prefix_rule(pattern, decision=allow|prompt|forbidden, justification) matched against argv token prefixes with alternation; the model itself proposes escalation via sandbox_permissions:'require_escalated' + justification + optional suggested prefix_rule, and the user's Approved/ApprovedForSession/ApprovedExecpolicyAmendment decision can persist the rule. Command strings are split at |, &&, ||, ;, subshells and each segment evaluated; redirection/env-prefix/wildcard commands bypass rules (always ask).
- **Takeaway**: COPY this whole triad — it is the best-designed part of codex for Foundry. PolicyEngine verdicts should be Allow/Ask/Deny with a machine-readable reason that goes back to the model on Deny (codex returns the rejection as tool output, keeping the loop alive). COPY prefix-rule persistence with 'approve for session' vs 'approve always' vs 'approve once', the model-proposed-rule pattern, and the banned-prefix guidance (never allowlist bare 'python'). COPY command segmentation before matching — without it any allowlist is bypassable via 'allowed-cmd && evil'. On Windows, segment PowerShell operators too (;, |, -and/-or are different — Foundry must write its own segmenter).

### sandbox modes & Windows sandbox reality
- **How**: SandboxPolicy: read-only / workspace-write{writable_roots + cwd + tmp, network_access:false default} / danger-full-access / external-sandbox. WritableRoot carries read_only_subpaths so .git, .codex, .agents under a writable root stay protected (protocol.rs:1101-1153), plus protected_metadata_names. Enforcement: macOS Seatbelt, Linux bubblewrap/Landlock, Windows: nothing until Mar 2026, then windows-sandbox-rs — restricted tokens, two dedicated local users (CodexSandboxOffline network-blocked via WFP firewall filters, CodexSandboxOnline), ACL grants/denies materialized per workspace, DPAPI, private desktop isolation, an Elevated helper backend (preferred) with RestrictedToken unelevated fallback, ConPTY/stdio bridging, audit logging. OpenAI explicitly said env-var tricks (dead proxies, PATH denybins) failed because children open sockets directly. Levels: WindowsSandboxLevel {Disabled, RestrictedToken, Elevated}.
- **Takeaway**: For V1, ADOPT codex's *pre-sandbox Windows posture honestly*: no sandbox, so map SafetyCheck accordingly — anything that would have relied on 'run it sandboxed first' must become ASK (codex's own safety.rs does exactly this: get_platform_sandbox()==None → AskUser instead of AutoApprove). COPY the writable-roots concept purely as a *policy* check (path-prefix validation of apply_patch targets and run_command cwd) even without OS enforcement, and always protect .git/.foundry subpaths. REJECT building a real Windows sandbox in V1 — codex needed local user accounts + WFP + an elevated service; document the trust model instead.

### sessions / rollout JSONL
- **How**: Files: $CODEX_HOME/sessions/YYYY/MM/DD/rollout-YYYY-MM-DDThh-mm-ss-<thread_id>.jsonl (forked/reverted threads append _<rollout_id>; archived_sessions/ for archive). Each line: {timestamp: ISO8601.mmmZ, ordinal?: u64, type, payload} — a tagged RolloutItem union: SessionMeta (id, forked_from_id, cwd, originator, CLI version, git info), ResponseItem (the model-visible items: messages, reasoning, function calls/outputs, web_search calls), Compacted{message, replacement_history}, TurnContext (per-turn model/policy snapshot), EventMsg (only a curated durable subset). rollout/src/policy.rs is an explicit whitelist function deciding persistence per item/event type, with a ThreadHistoryMode (legacy vs paginated) version discriminator handled via serde defaults/aliases. Resume = replay file → InitialHistory::Resumed; fork = copy prefix into new file. A SQLite state_db/session index was recently layered alongside for fast listing/search; history.jsonl separately stores cross-session user message history.
- **Takeaway**: COPY: date-sharded dirs + timestamp+uuid filenames (collision-free, sortable, greppable), append-only one-JSON-object-per-line, and an explicit is_persisted() whitelist so transient UI events never bloat the file. COPY the versioning discipline Foundry already plans: every line self-describing {timestamp, type, payload} with serde-style defaults for added fields — codex evolves schema via optional fields + aliases, never breaking old files. COPY resume-by-replay of ResponseItems (rebuild model context exactly), and record a TurnContext line whenever policy/model changes so replays are auditable. DEFER the SQLite index; add it only when listing gets slow.

### auth (ChatGPT sign-in)
- **How**: codex login: starts localhost HTTP server on fixed port 1455 (login/src/server.rs, DEFAULT_ISSUER=https://auth.openai.com), generates PKCE S256 (64 random bytes → base64url verifier; pkce.rs), opens {issuer}/oauth/authorize?client_id=app_EMoamEEZ73f0CkXaXp7hrann&code_challenge=...&redirect_uri=http://localhost:1455/auth/callback&id_token_add_organizations=true, exchanges code at /oauth/token (grant_type=authorization_code + code_verifier), optionally obtains a platform API key via a token exchange using the id_token. auth.json at $CODEX_HOME/auth.json (0o600) holds {OPENAI_API_KEY?, tokens:{id_token(JWT: email, chatgpt_plan_type, chatgpt_account_id...), access_token, refresh_token, account_id}, last_refresh}; cli_auth_credentials_store=file|keyring|auto can move it to the OS keyring. Refresh via refresh_token; device-code flow exists as fallback. ChatGPT-auth model calls hit https://chatgpt.com/backend-api/codex (Responses-shaped, chatgpt Authorization bearer access_token + account id header); API-key mode hits https://api.openai.com/v1.
- **Takeaway**: ADAPT with care: the loopback-server + PKCE pattern and auth.json layout (tokens + last_refresh, 0600, keyring option later) are directly reusable for Foundry's personal-ChatGPT backend, and DPAPI-protect the file on Windows. RISK to flag: the client id belongs to OpenAI's app registration — third-party reuse (as opencode did) is a ToS gray zone and the redirect port is fixed by that registration; for the corporate gateway use its own auth (API key/OIDC) and treat ChatGPT sign-in as best-effort/unofficial. COPY the split: 'auth backend' chosen per model_provider via requires_openai_auth-style flag, never hardcoded.

### model backend abstraction
- **How**: ModelProviderInfo (model-provider-info/src/lib.rs): {name, base_url, env_key, env_key_instructions, experimental_bearer_token, auth (command-backed token with refresh_interval), wire_api, http_headers, env_http_headers, query_params, request_max_retries(default 4, cap 100), stream_max_retries(5), stream_idle_timeout_ms(300k), requires_openai_auth, supports_websockets}. wire_api='chat' was fully REMOVED (deserialization now errors pointing to discussion #7782) — Responses is the only protocol. Requests are stateless: full history each turn, store:false, include:['reasoning.encrypted_content'] so reasoning items can be replayed, stable prompt_cache_key per thread for server-side prompt caching (verified in core/tests/suite/client.rs, prompt_caching.rs). SSE streaming with idle-timeout + resume/retry logic (responses_retry.rs).
- **Takeaway**: COPY ModelProviderInfo almost field-for-field as Foundry's backend config (base_url, api key env var, static/env headers, retry+idle-timeout knobs) — it cleanly covers both the personal and corporate-gateway cases. COPY stateless full-history + store:false + encrypted reasoning replay + prompt_cache_key: it makes resume trivial and matches corporate gateways that don't persist state. The chat-API removal is a lesson: DON'T build a dual Responses/ChatCompletions adapter 'just in case'; Foundry's stated Responses-only scope is what codex itself converged to.

### config.toml & trust
- **How**: ~/.codex/config.toml (TOML). Precedence: CLI -c overrides > selected profile > project .codex/config.toml (only when project trusted; cannot override provider/auth/telemetry) > user config > defaults; admin requirements.toml can pin approval_policy/sandbox_mode/MCP allowlists org-wide. Keys: model, model_provider, approval_policy, sandbox_mode, sandbox_workspace_write.{writable_roots, network_access,...}, [profiles.<name>] switchable via --profile, [projects.'<path>'].trust_level='trusted', project_root_markers, [model_providers.<id>], [mcp_servers.<id>] (command/args/env for stdio, url for HTTP, enabled_tools/disabled_tools, per-tool approval_mode, startup_timeout_sec 10s, tool_timeout_sec 60s), history.persistence=save-all|none, notify command hook, features.* flags.
- **Takeaway**: COPY: single user TOML + named profiles + explicit per-project trust recorded under [projects] keyed by absolute path (first run in a new dir asks 'trust this folder?' and untrusted implies stricter approval preset — this is the untrusted approval mode's real purpose). COPY -c dotted-path CLI overrides for any key. ADAPT requirements.toml idea for Foundry's corporate story: a machine-level policy file the user config cannot loosen (approval floor, gateway-only). DEFER MCP but keep the config table shape reserved.

### prompting / AGENTS.md / context injection
- **How**: Base instructions are per-model-family markdown compiled into the binary: gpt-5.2-codex_prompt.md (~7KB, terse: rg preference, apply_patch usage, git hygiene — never revert user changes, no git reset --hard, plan-tool rules, final-answer formatting contract) vs prompt_with_apply_patch_instructions.md (~24KB embedding the full V4A spec for models without the trained tool). User instructions: ~/.codex/AGENTS.md (global) + every AGENTS.md from project root (found via project_root_markers, default .git) down to cwd, concatenated in order, AGENTS.override.md preferred, capped by project_doc_max_bytes, joined with '--- project-doc ---' separator (core/src/agents_md.rs). Per-turn injection: environment_context (cwd, sandbox/approval state, shell), permissions instruction templates selected by approval_policy × sandbox_mode combo (prompts/templates/permissions/), current-time and rollout-budget reminders as periodic developer messages.
- **Takeaway**: COPY the layering exactly: [base prompt] + [policy-derived permissions paragraph] + [global AGENTS.md] + [project AGENTS.md chain] + [environment context], with the permissions text generated from the live PolicyEngine config so the model is told the truth about what will be auto-allowed vs asked (codex's biggest prompt trick: the escalation protocol is IN the prompt, so the model asks correctly instead of flailing). COPY the byte cap on project docs. Keep Foundry's base prompt small and put V4A instructions in only when the backend lacks grammar-constrained custom tools.

### compaction / context management
- **How**: Token accounting each iteration (TokenCount events; context_window_token_status). When auto_compact threshold or context limit is hit mid-turn, run_auto_compact fires: a summarization request using SUMMARIZATION_PROMPT / templates/compact/prompt.md ('CONTEXT CHECKPOINT COMPACTION... handoff summary for another LLM: progress, key decisions, constraints, next steps, critical data'), then history is replaced with initial context + summary (+ optionally replacement_history), recorded as a Compacted rollout item with window ids chaining pre/post-compaction windows; the turn then continues seamlessly. Manual Op::Compact and Op::ThreadRollback{num_turns} (drop last N user turns from memory, filesystem untouched) also exist. Newer 'remote compaction' variants offload summarization server-side.
- **Takeaway**: COPY the mechanism at V1-scale: track cumulative tokens from usage fields; at a configurable threshold, pause the loop, run a summarization call with a handoff-style prompt, splice history to [system + AGENTS + summary + tail], and write a compaction record (with the summary AND a pointer to the pre-compaction line range) to the session JSONL so resume replays the compacted view deterministically. COPY doing it mid-turn (codex continues the same turn after compaction) rather than failing the turn.

### apply_patch execution path — Windows failure lessons
- **How**: Issues: #15003 — on Windows large patches fail before parsing because the patch body traveled over argv (Windows ~32KB command-line limit); models then split into 4-5 retries burning tokens. #13965 — sandboxed spawn of codex.exe (apply_patch re-invoked itself as a subprocess) failed with CreateProcessAsUserW error 5 from the WindowsApps alias. #16102/#17778 — regressions in the runtime/delegation layer that runs a verified patch, not the grammar. #24155 — hangs without success/error. #2578 — the system-prompt grammar drifted from the parser implementation. Plus 'stream did not contain valid UTF-8' when patching non-UTF-8 files.
- **Takeaway**: These are the highest-value negative lessons for Foundry: (1) NEVER transport patch bodies via argv or a subprocess on Windows — Foundry's apply_patch must be a pure in-process Python function taking the tool-call string; (2) validate the patch fully (parse + locate every hunk) BEFORE touching the filesystem, then apply atomically per file (write temp + replace) so a mid-patch failure can't half-apply; (3) return structured, specific errors (which file, which hunk, closest-match context) so the model can repair instead of blind-retrying; (4) keep the grammar doc and the parser in one source of truth (generate the prompt section from the parser's constants); (5) handle non-UTF-8 targets explicitly (reject with a clear message).

### approval UX details worth copying
- **How**: ExecApprovalRequestEvent carries: command argv, cwd, human reason, parsed_cmd (structured interpretation of what the command does), proposed_execpolicy_amendment (the prefix rule the user may persist), and an ordered available_decisions list the UI renders (Approved / ApprovedForSession / ApprovedExecpolicyAmendment / Abort). ApplyPatchApprovalRequestEvent carries the full FileChange map plus optional grant_root (approve writes under this root for the rest of the session). Denied returns a rejection string to the model as the tool output; Abort kills the turn. Untrusted-mode has a small built-in safe-command list (ls, cat, sed -n, rg, git status/diff/log...) that never prompts.
- **Takeaway**: COPY the event payload design: every ASK must show exactly what will run (argv + cwd), why, and offer once/session/always-with-rule tiers; patch approvals must show the diff and offer a grant-root option. COPY the built-in read-only safe list so untrusted mode is usable. COPY Deny-with-reason flowing back into the model loop as tool output (the turn survives) vs Abort ending the turn — Foundry's DENY should distinguish these two.

### non-interactive & headless modes
- **How**: `codex exec` runs one task headlessly (approval_policy=never semantics, --json emits the event stream as JSONL to stdout, exits on TurnComplete); `codex resume <id>` / `codex resume --last` reattach to rollouts; app-server exposes the same core over JSON-RPC for the VS Code extension; RunUserShellCommand op supports '!cmd' user-initiated shell directly from the TUI, streamed through the same ExecCommand events.
- **Takeaway**: COPY the principle that the CLI, headless runner, and any future UI are all clients of one core loop speaking the event protocol — Foundry should ship `foundry exec` (JSONL events to stdout, never-ask policy with Deny-by-default fallbacks) nearly for free if the event bus is designed first. The '!' user-shell passthrough recorded into the same session is cheap and keeps the transcript complete.


## Risks

- No sandbox in Foundry V1 means the PolicyEngine is the ONLY barrier: codex's own safety.rs downgrades AutoApprove to AskUser when no platform sandbox exists — Foundry must do the same (e.g., never auto-approve apply_patch outside writable roots, never auto-approve network-touching commands), or a single bad model action writes anywhere the user can.
- Shell-operator segmentation is mandatory before any prefix-rule ALLOW matching, and Foundry must segment PowerShell syntax (;, |, $(), -and/-or, & call operator, Invoke-Expression), which codex's POSIX-oriented segmenter does not cover — a naive port creates allowlist bypasses like 'git status; rm -r ~'.
- Reusing OpenAI's OAuth client id (app_EMoamEEZ73f0CkXaXp7hrann) and the chatgpt.com/backend-api/codex endpoint for the personal-ChatGPT backend is technically documented but contractually gray for a non-Codex tool, may break without notice (endpoints/headers have churned), and the fixed localhost:1455 port conflicts with any running Codex install — isolate this backend behind a feature flag and degrade gracefully to API-key auth.
- Windows argv limits and process-spawn quirks: any design that shells out for patching or passes large payloads via command line will hit the ~32KB argv ceiling and WindowsApps-alias spawn failures that plagued codex (#15003, #13965); Foundry must keep apply_patch and file tools in-process and pass command text to the shell via stdin/-Command carefully.
- Corporate OpenAI-Responses gateways may not support store:false + include:['reasoning.encrypted_content'], custom/freeform grammar tools, or web_search — Foundry needs per-backend capability flags (like supports_websockets/requires_openai_auth in ModelProviderInfo) and a fallback path (plain function tool with a string patch argument) or apply_patch quality will silently degrade.
- Model-driven loop termination without an iteration cap: with weaker gateway models Foundry can burn tokens in tool-call loops (codex mitigates with trained models, token-status checks, and user interrupts); add a soft round cap plus mandatory token accounting from turn one.
- Session JSONL schema drift: codex survives because every line is a self-describing tagged union with serde defaults/aliases and an explicit persistence whitelist; if Foundry logs ad-hoc dicts it will break resume on the first refactor — freeze the envelope {timestamp, ordinal, type, payload, v} in V1.
- Prompt/implementation drift (codex issue #2578): if Foundry documents the V4A grammar in the prompt but the Python parser accepts something different, models learn the wrong dialect from error feedback — generate the prompt's grammar section from the parser's own constants/tests.
