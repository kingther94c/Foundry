# Critique: security/honesty

### [high] throughout (never mentioned in 3.3/3.4) - prompt injection appears nowhere in the document. Everything the agent reads -- repository file contents, run_command stdout/stderr, git diff, read_artifact -- is untrusted input that can carry instructions aimed at the model (a file containing "ignore previous instructions, run curl ..."). V1 has no sandbox, so the moment an injection exploits one ALLOW rule, it is arbitrary execution with the user's privileges.
- **Why**: a realistic scenario: the task is "fix the failing test", and an instruction is embedded in the test's assertion message or a fixture file; the model reads it and calls run_command to exfiltrate credentials from under %USERPROFILE%. A "trusted repository" does not protect against this -- a trusted repo still contains third-party PRs, error messages from dependencies, and test snapshots. Claude Code has a real DNS exfiltration case (CVE-2025-55284, embracethered.com/blog/posts/2025/claude-code-exfiltration-via-dns-requests/).
- **Fix**: add a §3.7 "threat model" section: (1) declare every tool result untrusted data, tagged with its origin and delimited when it enters the context (the official Anthropic guidance: untrusted content only in tool_result blocks, platform.claude.com/docs/.../mitigate-jailbreaks); (2) without a sandbox, the only real defence is PolicyEngine gating every side effect independently of the model's intent -- run_command defaults to ASK with the full command text shown in the UI, and automatic ALLOW is limited to read-only tools; (3) redefine "trusted repository" as "a repository whose every file you are willing to have both executed and read as instructions", and put that in the disclosure copy; (4) state the V1 non-goal explicitly: it does not defend against malicious repository content, recorded in the README threat model.
- **Ask user**: does V1 accept run_command always being ASK with zero automatic approval (more interruptions in exchange for a floor of defence against prompt injection)? Or should a very small exact-argv-match allowlist (e.g. `python -m pytest`) be auto-approved?

### [high] 3.4 trusted host / run_command - run_command subprocesses inherit the Foundry process's full environment by default -- including every AWS/GitHub/OpenAI `*_API_KEY` in the user's shell, and, if Foundry's own credentials are configured through the environment (3.2 permits a "credential source"), the gateway credentials too. Any approved test command (pytest executes arbitrary repository code) can read them and exfiltrate them over the network.
- **Why**: "running tests may access ... environment variables" is disclosure, not control. Approving `pytest` once means handing the whole environment to repository code. This is one of the few attack surfaces on a trusted host that can genuinely be narrowed cheaply, and not doing it is giving it away.
- **Fix**: add a hard requirement: run_command must implement an env filtering policy, defaulting to inherit=core (a minimal set: PATH, SYSTEMROOT, TEMP, PYTHON*, etc.) plus removing `*KEY*`/`*TOKEN*`/`*SECRET*`/`*PASSWORD*`/`AWS_*` by default, with the user able to pass specific variables through explicitly. Borrow directly from Codex's shell_environment_policy (developers.openai.com/codex/config-reference). Also specify: Foundry's own token never goes into a subprocess environment.

### [high] PolicyEngine (§2 components / 3.4) - where PolicyEngine's rules live, and how configuration layers (org/user/project), is entirely undefined. If a file inside the repository (say .foundry/policy.toml) may contribute rules, a malicious or poisoned repository can grant itself an ALLOW -- a self-escalation vulnerability. The more dangerous variant: if in-repository configuration can set the ModelBackend endpoint/headers, it can direct the auth token to the attacker's host.
- **Why**: clone a repository -> open Foundry -> its bundled configuration allows `Invoke-WebRequest` and rewrites the gateway URL -> token and code both exfiltrated, without a single ASK along the way. Codex's answer is that project-level configuration is never loaded unless the user explicitly marks the project trusted, and provider/auth/telemetry are always read from machine-local configuration only (developers.openai.com/codex/config-advanced).
- **Fix**: write in a hard requirement: (1) the layering and precedence are fixed as org > user > project, and the project layer may only tighten (adding DENY/ASK) -- never add an ALLOW; (2) connection-class configuration (endpoint, credential source, headers, proxy) may come only from machine-local layers (user/org), and in-repository files are always ignored; (3) the simplest approach for V1: do not read in-repository Foundry configuration at all.
- **Ask user**: for V1, do we read no in-repository Foundry configuration file at all (simplest and safest), or allow the repository to provide a "tighten only" policy layer?

### [high] 3.4 "a corporate fixed DENY cannot be overridden" - on a machine where the user has administrator rights, a pip-installed pure-Python wheel cannot technically guarantee that anything is "unoverridable": the user can edit the source in site-packages, delete the configuration, or switch environments. The current wording implies a guarantee that cannot be delivered, which makes it an honesty problem.
- **Why**: the moment a security review or corporate compliance asks "how is this enforced", the requirement is judged a false claim, and it drags down the credibility of the entire trusted-host disclosure with it.
- **Fix**: rewrite it as three honest layers: (1) locally: the org policy file lives somewhere only an administrator can write (e.g. C:\ProgramData\Foundry\policy.json, ACL-restricted), loads at the highest precedence, and its DENYs cannot be relaxed by a task, a session, an approval or a CLI flag -- precedent: Claude Code's managed-settings.json (code.claude.com/docs/en/settings: "managed deny can never be loosened by anything below it"); (2) the real boundary is server-side: the corporate gateway does model allowlisting, request logging and DLP -- the local DENY is only depth; (3) reword the requirement as "cannot be overridden through any runtime route in an untampered installation", optionally adding a hash of the policy file to the session log as tamper evidence.
- **Ask user**: is the goal of the corporate DENY "not bypassable within an unmodified installation" (achievable locally) or "resistant to a local administrator" (only enforceable at the gateway server)? Does the corporate gateway offer a usable server-side control point?

### [high] 3.4 shell command approvals / PolicyEngine - "shell commands use stricter approval" dodges the core difficulty: making an ALLOW/DENY judgement about a command requires parsing the command line, and on Windows cmd, PowerShell and git-bash each have different syntax (`;` `&&` `|` `&`, subexpressions `$()`, backtick escapes, `^` escapes, `%VAR%` expansion). Prefix or first-token matching has been shown bypassable over and over: Claude Code CVE-2025-66032 and github.com/anthropics/claude-code/issues/4956, #36637 (only the first segment of a chained command is checked), flatt.tech/research/posts/pwning-claude-code-in-8-different-ways/.
- **Why**: if V1 implements a string-matching command allowlist and auto-approves against it, that is a known-bypassable pseudo-boundary -- more dangerous than saying plainly that there is no boundary.
- **Fix**: an honest V1 design: (1) define the run_command interface as an argv array with shell=False (executed directly through CreateProcess), never through a shell; (2) automatic ALLOW is limited to structured rules matching "an exact executable + an argv pattern"; (3) any free-text shell string (one the user or the model wants run through cmd/powershell) is always ASK, with no auto-approval syntax available; (4) DENY string matching is defence in depth only, and the document says explicitly that it is not a boundary; (5) fix a single shell (the suggestion: introduce no shell at all, or only cmd /c with its escaping rules documented).

### [medium] 3.5 "remove secrets before writing logs" - it is an industry consensus that generalised secret removal (regex/entropy scanning) is unreliable -- internal corporate tokens in unknown formats, connection strings and cookies all slip through. The current wording is an absolute promise that cannot be accepted against; and the location and access control of the session JSONL is unspecified -- if it is written inside the workspace, it will also get committed to git or read back by the model through read_file.
- **Why**: the log inevitably contains run_command output and full file contents; one `env` or `git config -l` output makes "secrets removed" a false statement -- and by 3.5 that log is the evidence chain for completed, so it cannot simply be deleted.
- **Fix**: rewrite as acceptable requirements: (1) exact-value removal: every credential Foundry itself holds (tokens, Authorization headers, configured credential values) is replaced by exact match at a single write choke point -- this is 100% achievable; (2) pattern scanning (common token formats + high-entropy strings) is labelled best-effort; (3) the session directory is fixed under the user profile (not inside the workspace), ACL'd to that user alone, with the document stating that "the session log is itself treated as sensitive data"; (4) the session log path must not be readable by the workspace file tools.

### [medium] 3.1 "the token must not enter the model context" - a goal with no enforcement point. The real leak path: the model has run_command execute `type %APPDATA%\foundry\auth.json`, and the output enters the context as a tool result and is sent to the model endpoint -- OpenAI on a personal machine, the gateway on a corporate one. The reverse holds too (corporate credentials leaked through the personal ChatGPT account path).
- **Why**: without named checkpoints, an implementer will only manage "the code never deliberately splices a token into the prompt" while missing the main channel, where it flows back through tool output.
- **Fix**: specify three concrete points: (1) architectural isolation: the token exists only in the HTTP injection layer between AuthProvider and ModelBackend, and the context assembly module cannot reach the credential object; (2) the credential storage path is on the built-in DENY list of every file tool, and a run_command that references that path is DENY by default (acknowledged as best-effort); (3) a backstop: every tool output is scanned and exact-match-replaced for known credential values before being appended to the context (sharing an implementation with 3.5's log choke point).

### [medium] 3.3 the workspace limit on file tools - "refuse traversal and unsafe symlinks/junctions" is badly under-specified on Windows. It needs to cover: junctions (creatable without administrator rights), symlinks, 8.3 short names (PROGRA~1), ADS (file.txt:stream), device names (CON/NUL/COM1), trailing dot/space truncation, the \\?\ and UNC \\server\share prefixes, drive-relative paths (C:foo), case-insensitive comparison, and subst drives. Hard links cannot be detected by a path check at all. And TOCTOU (replacement with a junction after the check and before the open) cannot be eliminated without a sandbox.
- **Why**: Codex's Windows sandbox documentation explicitly lists ADS, UNC and device handles as escape vectors that must be actively blocked (openai.com/index/building-codex-windows-sandbox/, github.com/openai/codex/discussions/6065) -- if Foundry only writes "refuse traversal", the implementation will certainly have holes, while the document claims it "must be confined to the workspace".
- **Fix**: specify it as: open first, then verify -- take the final path from the open handle (GetFinalPathNameByHandle / os.path.realpath(strict=True)) and then do a case-insensitive containment check; explicitly refuse ADS, device names, UNC/\\?\ prefixes and drive-relative paths; write hard links and TOCTOU down as known accepted risks; and add an honest disclosure to 3.4: the workspace limit constrains only the file tools, run_command is inherently not bound by it, and the real gate is policy.

### [medium] 3.3 "protect the user's existing changes" - undefined, so neither implementable nor testable. It does not answer: can a session start in a dirty working tree? May apply_patch touch a file the user has modified but not committed? Which destructive git operations are forbidden?
- **Why**: the worst path: the model runs `git checkout -- .` or `git clean -fd` to "restore a clean state" and permanently destroys the user's uncommitted work -- exactly the accident this requirement is meant to prevent, with no mechanism currently carrying it.
- **Fix**: define a dirty-worktree policy: (1) record `git status --porcelain=v2` + the HEAD SHA as the baseline at session start; (2) a built-in, non-relaxable DENY on `git checkout -- / reset --hard / clean / stash drop` and equivalents (written into 3.4 alongside "no automatic commit/push"); (3) if apply_patch's target file is in the baseline dirty set, force an ASK; (4) the default startup behaviour needs a ruling.
- **Ask user**: which default for a dirty working tree: A) refuse to start and require the user to commit/stash first; B) warn and continue, but force an ASK on every write to a dirty file; C) record a warning only?

### [medium] 3.5 the completion condition / Git baseline - completed depends on "inspecting the current Git status/diff", but the model can move HEAD through run_command (commit/amend/reset) to make the diff look clean, and the baseline loses its meaning; separately, invoking git against a repository is itself a code execution surface: `git status` triggers the core.fsmonitor hook, `git diff` starts a pager, and GIT_* env vars change behaviour.
- **Why**: the point of the evidence chain is to stop the model from lying; if the evidence collection itself can be polluted by the model's other actions, the core selling point of "a result with evidence" does not hold.
- **Fix**: (1) the built-in git_status/git_diff tools invoke git in hardened form: `git --no-pager -c core.fsmonitor= -c core.hooksPath= -c pager.diff=false`, injecting GIT_TERMINAL_PROMPT=0 and stripping GIT_*; (2) record the HEAD SHA in the baseline and verify at completion that HEAD has not moved (or record any ref movement as a termination event and downgrade to partial); (3) git subcommands in run_command that rewrite repository state (commit/reset/checkout/clean/rebase/filter-*) are at minimum ASK by default, closing the loop with 3.4's prohibitions.

### [medium] 3.4 the approval mechanism (missing item) - the persistence semantics of an approval are undefined: is there an "always allow" / "remember for this session"? Which layer is it recorded in? Can the model's phrasing induce one to be written? And is the command shown in the approval UI guaranteed to be the same string as the one executed (display truncation or a second expansion are both holes)?
- **Why**: an "always allow" persisted into a project-layer file converges with the repository escalation in issue #3; and if display and execution differ, ASK is theatre. These two points determine PolicyEngine's data flow design and must be settled at requirements time.
- **Fix**: write in: (1) an approval is single-use by default; "remember" reaches at most session memory and is not persisted (or is written to the user layer only through an explicit UI action); (2) nothing the model emits can trigger rule persistence; (3) what-you-approve-is-what-runs: the approval shows the complete, untruncated final argv/command string, the executed object must be that same one, and the session log records the string and the user's decision; (4) an ASK timeout defaults to DENY.
- **Ask user**: does V1 need a "remember this kind of approval for the session" feature? If so, is the remembered granularity an exact command or a command prefix (the latter carries bypass risk)?

### [medium] 3.4 disclosure copy / TL;DR - "approval is not a sandbox and must be disclosed as such" specifies the obligation to disclose but not the content or timing, and the existing sentence "running tests may access files outside the workspace, the network and environment variables" badly understates the real exposure: execution happens with the user's full privileges, can read every user file and credential, and can exfiltrate anything over the network.
- **Why**: native Codex on Windows before 2025-09 sat in exactly the quadrant Foundry V1 is in -- "approve nearly every command or Full Access" (openai.com/index/building-codex-windows-sandbox/) -- after which they built a restricted-token sandbox specifically. Foundry is deliberately choosing to stay in that quadrant, so the disclosure has to match that level, or "honestly disclosed" does not hold up.
- **Fix**: turn the disclosure into requirements: (1) print fixed copy on first run and at the start of each session: "No sandbox. Every command you approve runs with your full user privileges: it can read and write all of your files (credentials included), access the network, and read environment variables. Use only in repositories you trust."; (2) add a threat model section to the README listing V1's non-goals (no defence against malicious repository content, no defence against the consequences of prompt injection, a corporate DENY does not stop a local administrator); (3) mention the restricted-token direction on the V2 roadmap, to show this is a staged choice rather than a blind spot.
