# Critique: architecture/delivery

### [high] §3.1 / delivery order - making "finish ChatGPT authentication first" the opening milestone is an ordering error: it is the single most uncertain item in the project, and nothing else depends on it. There is an official Sign-in-with-ChatGPT flow (developers.openai.com/codex/auth.md: browser OAuth via a localhost:1455 callback; device-code requires a workspace admin to enable it explicitly), but a third-party harness using ChatGPT subscription OAuth is "tolerated" rather than promised under the ToS (github.com/openai/codex/discussions/8338), and there are known failures of the localhost callback on Windows (community.openai.com/t/codex-cli-login-fails-on-windows-.../1381736). Draft 3.1 says itself that it will "mark it blocked if no supported route exists" -- so the first milestone ships with its own failure plan, and yet the entire skeleton is queued behind it.
- **Why**: if the OAuth spike gets stuck for 2-4 weeks (the callback blocked by the corporate network, an unclear ToS conclusion, refresh semantics needing to be reverse-engineered), the loop, tools, policy and session make zero progress -- and those are Foundry's actual assets. Worst case: auth is judged blocked, and the project stalls without a single runnable thing.
- **Fix**: reorder the milestones: M0 = a walking skeleton (CLI -> AgentRuntime -> 2 tools (read_file/list_files) -> PolicyEngine -> JSONL), with an ordinary OpenAI API key behind it -- it shares the Responses protocol with the corporate Gateway, so 90% of the code carries straight over to 3.2; demote ChatGPT OAuth to a parallel spike with a timebox (a week, say) and explicit exit conditions. Add an explicit milestone sequence to the document (M0 skeleton -> M1 all tools + policy -> M2 corporate Gateway -> M3 ChatGPT auth -> M4 hardening).
- **Ask user**: do you agree to make the first runnable milestone "a walking skeleton driven by an API key (or the corporate Gateway)", with ChatGPT login demoted to a parallel, timeboxed spike?

### [high] §3.2 / §3.3 apply_patch - the document never asks which model IDs the corporate Gateway actually exposes, yet implicitly assumes "Responses-compatible is enough". apply_patch's patch syntax (V4A) is a proprietary format trained into the GPT family: the official documentation lists only GPT-5.1/5.2/5.4/5.5 as supporting it (developers.openai.com/api/docs/guides/tools-apply-patch); even Azure-hosted GPT-4.1 produces broken patches now that Codex v0.80.0 no longer injects the format description (github.com/openai/codex/issues/14046). If the corporate Gateway is a Responses facade in front of Claude/Gemini/internal models, V4A patch output will be malformed (the Claude family is trained toward str_replace-style editing).
- **Why**: apply_patch is V1's only file-writing tool -- if it fails against the only model available at work, the entire corporate path fails, and that would only surface at M2 integration, with the rework reaching the tool schema, the loop prompt and the test set.
- **Fix**: (a) make "obtain the Gateway's model list + whether it supports the built-in apply_patch tool type + parallel tool calls + streaming event differences" a Day-1 discovery deliverable; (b) design the edit tool per model profile: the format (V4A / str-replace / unified diff) is an attribute of the ModelBackend's model profile, the ToolExecutor is responsible only for uniform validation and writing to disk, and the format must not be burned into the tool definition; (c) whichever format is used, the system prompt must inject the format description explicitly rather than relying on "the model just knows".
- **Ask user**: which model IDs does the corporate Gateway expose, specifically? Are they native OpenAI models, or is it a Responses facade in front of non-GPT models such as Claude or Gemini? Can we get the Gateway's protocol-difference documentation?

### [high] §2 component list - offline test/replay facilities are missing: ModelBackend lists only two real backends, the component list has no record/replay mechanism of any kind, and there is no test strategy for the loop. The agent loop is the most complex state machine in the project, and as designed it can only be integration-tested with a real token or corporate Gateway credentials.
- **Why**: CI cannot run offline (which contradicts 3.6's offline delivery philosophy), tests are not reproducible, and it burns subscription quota; worse is the timing of any remedy: adding replay after the loop is written means the request construction (prompt assembly, tool schema serialisation, truncation) is already scattered everywhere and cannot be intercepted, leaving only a refactor. Codex itself implements session recording and replay/resume with a JSONL rollout (codex-rs/core/src/rollout/ in github.com/openai/codex), which shows this has to be a day-one interface constraint.
- **Fix**: define ModelBackend as three implementations: OpenAI / CorporateGateway / ReplayBackend (reading recorded request-response JSONL fixtures); require the SessionStore events (or a side-channel recording file) to be complete enough to rebuild every model request byte for byte. Write it into the acceptance criteria: every loop/policy/tool test must pass on a machine with no network and no credentials.

### [high] §2 / §3.4 the ASK flow - the UI event stream and approval channel components are missing. PolicyEngine returns ASK, but the component diagram has no mechanism at all for delivering an approval request to the user and getting a decision back; nor is it defined how streaming output reaches the CLI -- there is no interface between AgentRuntime and the CLI.
- **Why**: without a typed event stream (model_delta / tool_begin / tool_end / approval_request / token_usage / termination), the CLI can only couple directly into the runtime's internals, and future reuse by an IDE or a service is empty talk; and in non-interactive contexts (scripts, CI) the semantics of ASK are entirely undefined -- does it block, time out, or pass? That is a hole on a security boundary.
- **Fix**: define an AgentEvent union type and a single event sink/observer interface, with the CLI as nothing but a subscriber; model approval as an asynchronous request/response event pair; mandate that in non-interactive mode ASK -> DENY (fail-closed) and that this is written to the session events.

### [high] §2 / §3.3 no ContextManager - there is no context/prompt management component. 3.3 caps rounds, counts, time and output size, but nobody owns the context window: the behaviour when a long session overflows is undefined; who assembles the system prompt per backend/model is undefined; "output size" has no per-tool semantics -- whether read_file paginates, the maximum hit count for search_text, and how run_command's interleaved stdout/stderr is truncated and what is kept (head+tail?) are all missing. Another concrete Windows landmine: in a Chinese-locale environment subprocess output is GBK/cp936, and without a defined decoding strategy, mojibake enters the model context on day one.
- **Why**: "the events SessionStore records" is not "the context sent to the model", and if those two concepts are not separated, replay, truncation, future compaction and 3.5's auditing all become impossible; the first task whose npm test emits 2MB of output will blow up the loop or burn the budget.
- **Fix**: add a ContextManager component that owns the transcript->model-context projection, per-tool truncation rules (a byte ceiling + an explicit [truncated] marker + the full output written to disk for read_artifact to retrieve), and an overflow policy (V1 may do nothing more than "terminate + reason=context_exhausted", but it has to be written down); specify subprocess output decoding: UTF-8 first, falling back to cp936, with errors=replace.

### [high] §3.2 / §3.3 error handling - there is no error taxonomy and no retry/backoff policy. "Error conversion" gets one clause in ModelBackend, but there is no shared taxonomy: retryable (429 + Retry-After, 5xx, network flakiness) / auth (a mid-stream 401 -> trigger an AuthProvider refresh and retry once) / fatal (context_length_exceeded, a content refusal) / policy denial -- which errors belong to which class, and what the response is, is entirely undefined.
- **Why**: without it, AgentRuntime cannot decide "retry or terminate", 3.3's "repeated failure must terminate in bounded time" cannot be implemented, and the two backends will each invent their own exception hierarchy, filling the loop with isinstance branches; on top of that, two concurrent Foundry instances refreshing the same refresh token (the rotation case) will knock each other's login out, so the AuthProvider contract has to state locking/single-flight semantics.
- **Fix**: define a FoundryError hierarchy (TransientError/AuthError/FatalError/PolicyDenied); require the backend contract to map the provider's original error into that hierarchy while preserving the original payload for logging; put retry (exponential backoff + an attempt ceiling + respecting Retry-After) in AgentRuntime, not in each backend; require AuthProvider.refresh to single-flight within the process and take a file lock against multi-instance races.

### [high] §2 the concurrency model - asyncio or a synchronous loop was never decided. Streaming responses, Ctrl+C cancellation, subprocess timeouts and a model's parallel tool calls all press on this choice, and it determines every interface signature (does ModelBackend.stream() return an iterator or an async iterator; is ASK approval a blocking callback or an await; is cancellation a CancelledError or a polled flag).
- **Why**: this is foundation that cannot be retrofitted: converting from sync to async after every interface is written means rewriting every component; deciding up front costs a few lines of signature. On Windows, Python 3.12's default ProactorEventLoop already supports asyncio subprocesses, so there is no technical obstacle.
- **Fix**: decide now and write it into the interface documentation. The suggestion: an asyncio core (streaming, cancellation and timeouts express naturally), with synchronously implemented tools wrapped in asyncio.to_thread; if the team insists on all-synchronous, then state that streaming uses generators, cancellation uses cooperative polling, and concurrent tool calls are serialised -- either is fine, but one has to be chosen and written down.

### [medium] §3.3 cancellation and subprocesses - "cancel/timeout must clean up subprocesses" is a goal, not a design. Windows has no process-group SIGKILL: the cmd/pwsh that run_command starts spawns children of its own, Popen.kill() only kills the direct child, and orphans (a hung node or pytest) keep holding file locks and polluting the workspace. Nobody owns the cancellation propagation chain either (CLI Ctrl+C -> runtime -> interrupt the in-flight HTTP stream -> kill the process tree -> record cancelled in the session).
- **Why**: the first cancelled npm test leaves orphan processes and locked files, the next task's apply_patch fails outright, and the user stops believing the "cleanup" promise.
- **Fix**: mandate that run_command manages the child process tree with a Win32 Job Object (JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE), with taskkill /F /T /PID as a backstop; make the cancellation propagation path explicitly owned by AgentRuntime; add an acceptance test: cancel a command that is running multi-level subprocesses, and the system is left with no orphans.

### [medium] §3.3 parallel tool calls - parallel tool calls are not mentioned at all. A Responses API model can return several tool calls in one round, and the draft's loop description is written entirely in the singular; what to do when one call in a batch is ASK (block them all? run the ALLOW ones first?) is also undefined.
- **Why**: if the wire protocol layer does not accept N calls in one round, the first time a real model calls concurrently it falls into the "malformed" branch and is refused, leaving the loop incompatible with mainstream model behaviour.
- **Fix**: specify it explicitly for V1: the protocol layer accepts N tool calls; the execution layer runs them serially in order, each passing through PolicyEngine independently; the next round only begins once every result has been fed back by call_id. Write this into the loop specification and the replay test fixtures.

### [medium] §3.5 SessionStore - "versioned JSONL" is a name with no mechanism: where the version lives (a file header record vs. per event), the event type discriminator, and the compatibility policy for a newer binary reading an older session are all missing. There is a bigger hidden scope question: does V1 support session resume? Codex's rollout JSONL explicitly serves resume (codex-rs/core/src/rollout/), and if Foundry does not resume, SessionStore is just an audit log and the schema can be loose; if it does resume, the schema has to be able to rebuild the full model context -- the two differ by several times the effort, and it was never decided.
- **Why**: with no evolution rule for the schema, the first field change makes every historical session unreadable; and resume or not directly determines how deeply SessionStore and ContextManager couple, which is a scope question, not an implementation detail.
- **Fix**: record {schema_version, foundry_version, session_id, git_baseline} in a first-line header; give every event a type discriminator; the evolution rule is add-only, never change or delete, and readers skip unknown event types; and put resume explicitly in or out of V1.
- **Ask user**: does V1 need session resume (continuing the same session after an interruption)? It decides whether SessionStore is a pure audit log or the source of truth that can rebuild the model context, and the effort differs greatly.

### [medium] §3.6 the dependency budget - "prefer the standard library and few dependencies" is not a list. None of the forced choices have been made: the HTTP+SSE stack (stdlib urllib cannot do streaming SSE, so httpx or equivalent is needed), Windows credential storage (keyring -> pulls in the pywin32 binary wheel), the CLI framework, schema validation (pydantic pulls in the pydantic-core platform binary). Offline installation means the internal-wheel-dir must contain cp312/win_amd64 wheels for every transitive dependency. Separately, 3.2 lists TLS/proxy configuration options but does not cover the reality of a corporate TLS-intercepting proxy: certifi's default CA bundle will fail the handshake, so the system certificate store (truststore) or a configurable CA bundle must be supported.
- **Why**: one transitive dependency with a platform binary missing a wheel and the offline install fails on the spot; the CA problem makes the corporate path SSLError on its very first connection to the Gateway -- and both are delivery killers that only surface at the last moment.
- **Fix**: deliver a requirements.lock (pinned versions + hashes) together with an automatic check that every package in the lock file has a cp312-win_amd64 (or pure py3) wheel in the internal-wheel-dir; write "support truststore or a configurable CA bundle + corporate proxies (with the NTLM/PAC cases confirmed)" into 3.2 as a hard requirement.

### [medium] §3.3 read_artifact - read_artifact is the only one of the 8 tools with no semantic definition: what an "artifact" is (run_command's full output after it was truncated and written to disk? build products? test reports?), where it is stored, who registers it, and where the boundary with read_file lies (is it subject to the workspace limit?) are all blank.
- **Why**: an undefined tool cannot have a schema written for it, cannot be classified by policy, and cannot be tested; and if it can read paths outside the workspace, it is also an unaudited back door through 3.3's file boundary rules.
- **Fix**: the recommended definition is: read the complete raw output that ToolExecutor wrote into the session directory because it exceeded the output ceiling, indexed by artifact_id -- which pairs naturally with ContextManager's truncation policy and never leaves the session directory; if there is no such use case, remove it from V1.
- **Ask user**: what is read_artifact actually meant to read? The full output that run_command wrote to disk after truncation, or some other artifact? If there is no clear use case, do you agree to move it out of V1?

### [medium] §3.5 the completion condition - the completed gate is not machine-enforceable: "every validation claim has a real command and exit code" needs a claim schema -- the model's validation claim has to cite a command event id in SessionStore, or checking it is left to human eyeballs; and a purely read-only task (explaining code, a review, answering a question) has neither a diff nor a verification command, so under the current wording it can never return completed.
- **Why**: a gate that cannot be enforced automatically degrades into a gentlemen's agreement at the prompt level, which is exactly the "the model says it verified" problem this document wants to avoid; and forcing read-only tasks to return partial pollutes the status semantics.
- **Fix**: define a ValidationClaim{claim_text, command_event_id, exit_code} structure, and only allow completed once the runtime has cross-checked it against the event stream; add a completed(no_changes) path for side-effect-free tasks, where a clean git status satisfies the gate.

### [low] §3.6 packaging structure - one wheel or a core+cli split was not decided. If the runtime becomes entangled with console/CLI dependencies, splitting it later for an IDE plugin or a service is expensive.
- **Why**: two wheels in V1 complicates offline installation and version alignment for zero benefit; but with no boundary at all, CLI code will seep into the runtime over time.
- **Fix**: keep a single wheel in V1, but enforce an import layering: foundry.core (every runtime component) must not import foundry.cli, fixed in place with import-linter or a simple CI check; splitting later then costs nothing.
