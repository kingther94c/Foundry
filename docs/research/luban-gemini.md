# Luban + gemini-cli

## Summary

Both references are real and highly relevant. (A) HashtagYJM/luban is a small (2 stars, 182 commits) but substantive terminal coding agent written in pure-stdlib Python 3.11+, installable as an offline wheel via `pip install --no-index` — almost exactly Foundry's distribution model. Its ~20-module flat package (luban/agent.py, tools.py, permissions.py, sessions.py, audit.py, memory.py, skills.py, providers/) demonstrates a working stdlib-only design for the agent loop (tool_use loop with truncation recovery, orphan-tool_use sanitization, prompt-cache breakpoints), a deny>allow>default fnmatch permission engine with read-only-tools-default-ALLOW / mutators-default-ASK, one-JSON-file-per-session storage with atomic writes and human-sortable IDs, an append-only audit.jsonl, a pluggable `client_local.py` model backend with runtime capability probing/graceful degradation, and explicit Windows support (UTF-8 pinning, .bat shim, platform-aware shell conventions). It is inspiration-grade, not battle-tested, but it is the closest existing proof that Foundry's constraints (Python, offline wheel, Windows, swappable backends, no sandbox but honest) compose into a working product.

(B) google-gemini/gemini-cli is the battle-tested reference for architecture. The monorepo separates packages/cli (terminal UI) from packages/core (model client, prompt construction, tool registry, scheduler, policy) plus sdk/a2a-server/vscode-ide-companion/test-utils. Tools follow a DeclarativeTool→ToolInvocation split (validate via build(), then execute()), with `shouldConfirmExecute()` returning typed confirmation payloads (edit-with-diff, exec, mcp, info, plus newer ask_user/exit_plan_mode/sandbox_expansion) and a rich outcome enum (ProceedOnce / ProceedAlways / ProceedAlwaysAndSave / ProceedAlwaysServer / ProceedAlwaysTool / ModifyWithEditor / Cancel). A dedicated policy engine (packages/core/src/policy) issues ALLOW/DENY/ASK_USER via priority-numbered rules (toolName wildcard + argsPattern regex, defaultDecision=ASK_USER), and a scheduler (packages/core/src/scheduler) runs an explicit state machine (Validating → AwaitingApproval → Scheduled → Executing → Success/Error/Cancelled), parallelizing read-only tools while serializing mutators, with confirmations routed over a MessageBus so core stays UI-free. Shell safety = prefix allowlists `run_shell_command(git)`, deny-first exclude lists, and automatic splitting of `&&`/`||`/`;` chains with every segment validated. Checkpointing = shadow git repo per project hash + conversation/tool-call JSON, restored via /restore; trusted-folders gate all project-supplied config; sessions live in `~/.gemini/tmp/<project_hash>/chats/` with retention policies; telemetry is OpenTelemetry with a local file exporter and a logPrompts privacy toggle. On Windows it executes shell via `powershell.exe -NoProfile -Command`, and its "native Windows sandbox" (icacls Low Mandatory Level with *persistent* filesystem integrity changes) is a cautionary tale supporting Foundry's honest no-sandbox V1.

Bonus skims: sst/opencode's standout is its permission config ergonomics — nested pattern maps with last-match-wins (`"bash": {"*":"ask","git *":"allow","rm *":"deny"}`) and per-agent overrides. block/goose's standout is MCP as the *sole* tool abstraction with 15+ swappable providers — architecturally elegant but wrong for Foundry V1's offline stdlib constraint; keeping Foundry's internal tool interface MCP-shaped keeps the door open cheaply.

## Designs

### core/frontend package separation
- **How**: gemini-cli splits packages/cli (terminal UI, input, themes, display) from packages/core (model client in core/src/core/client.ts + geminiChat.ts, prompt construction, tool registry, scheduler, policy engine), plus separate sdk, a2a-server, vscode-ide-companion, devtools, test-utils packages. Core never imports UI; user-facing confirmation is routed over an event bus (packages/core/src/confirmation-bus/message-bus.ts) so headless/ACP/IDE frontends reuse the same core.
- **Takeaway**: Adapt: Foundry ships one wheel but should enforce the same boundary as subpackages (foundry.core: loop/tools/policy/session/backends; foundry.cli: prompt_toolkit-or-plain-stdio rendering). Core raises typed ConfirmationRequest objects through a callback/queue interface, never calls input() directly. This buys headless mode, testability, and a future GUI for free.

### tool abstraction (validate-then-execute)
- **How**: gemini-cli's packages/core/src/tools/tools.ts defines DeclarativeTool (a builder: build(params) validates and returns a ToolInvocation) separate from ToolInvocation (a validated, ready-to-execute call with execute() and shouldConfirmExecute()). Tools carry a Kind enum (Read, Edit, Delete, Move, Search, Execute, Fetch, ...) with MUTATOR_KINDS vs READ_ONLY_KINDS driving policy defaults and parallelism.
- **Takeaway**: Copy in Python: Tool.validate(input) -> Invocation dataclass; invalid params fail before any confirmation UI (maps to gemini-cli's INVALID_TOOL_PARAMS). Tag each Foundry tool with a kind: read-only (list_files, search_text, read_file, read_artifact, git_status, git_diff) default-ALLOW; mutators (apply_patch, run_command) default-ASK. Luban independently converged on exactly this read-only-ALLOW/mutator-ASK default (luban/permissions.py), validating it for V1.

### confirmation flow (shouldConfirmExecute)
- **How**: shouldConfirmExecute(abortSignal) returns Promise<ToolCallConfirmationDetails | false>. Details are typed variants — edit (with diff), exec (with command), mcp, info — each carrying an onConfirm(outcome) callback. Outcomes: ProceedOnce, ProceedAlways, ProceedAlwaysAndSave, ProceedAlwaysServer, ProceedAlwaysTool, ModifyWithEditor, Cancel. Persistent outcomes call updatePolicy() to write dynamic allowlist rules; ModifyWithEditor lets the user edit the proposed diff/command before approval (scheduler/tool-modifier.ts).
- **Takeaway**: Copy the typed-confirmation + outcome-enum pattern. Foundry's ASK path should return a dataclass (PatchConfirmation with rendered diff, CommandConfirmation with exact command line) and accept outcomes {once, always_session, always_saved, modify, cancel}. Distinguishing 'always for this session' from 'always and save to config' is important on a trusted host — session-scoped grants are the safer default.

### policy engine rules
- **How**: gemini-cli (packages/core/src/policy/types.ts, policy-engine.ts, toml-loader.ts): PolicyDecision = ALLOW | DENY | ASK_USER; PolicyRule = {toolName ('*' wildcard), argsPattern (regex), decision, priority (higher wins, default 0)}; defaultDecision = ASK_USER; approval modes are implemented as high-priority rules (PRIORITY_YOLO_ALLOW_ALL = 998, magic fractional priorities like 1.03 for subagent tools). Luban (luban/permissions.py) is simpler: deny > allow > default, fnmatch glob rules '<tool>' or '<tool>:<pattern>' matched against a per-tool target key (command for run_command, path for file tools); malformed rules never match and cannot crash; config lives only in ~/.luban/config.toml.
- **Takeaway**: Adopt gemini-cli's three-decision vocabulary (Foundry already has ALLOW/ASK/DENY) but reject its numeric-priority scheme — the magic numbers (1.03, 998) show how priority arithmetic rots. Use luban's fixed precedence deny > allow > default with fnmatch patterns per tool-specific target, plus opencode's config ergonomics (nested last-match-wins pattern maps). Copy luban's rule that malformed rules silently never match, and that an --auto/yolo flag still respects DENY rules.

### shell command allowlisting
- **How**: gemini-cli: prefix-matched allowlist entries like run_shell_command(git) (allows 'git status', 'git log'); tools.exclude blocklist is always checked first and overrides allows; chained commands are automatically split on '&&', '||', ';' and every segment validated — one disallowed segment blocks the whole command; command-substitution safety has dedicated tests (packages/core/src/policy/shell-substitution.test.ts, shell-safety.test.ts). On Windows commands run via `powershell.exe -NoProfile -Command`; elsewhere `bash -c`.
- **Takeaway**: Copy deny-first + prefix allowlist + chain splitting. But adapt hard for Windows: gemini-cli's splitting logic targets POSIX operators, and Python's shlex is POSIX-only — PowerShell adds `;`, pipelines, subexpressions `$( )`, backtick escapes, and cmd.exe adds `&`. Foundry should pick ONE shell (recommend cmd.exe or a fixed powershell -NoProfile invocation), write a conservative tokenizer for it, and route any command containing substitution/chaining metacharacters to ASK even when a prefix rule says ALLOW. Never let an allowlist fast-path bypass metacharacter checks.

### tool-call scheduler state machine
- **How**: packages/core/src/scheduler/scheduler.ts (+ state-manager.ts, tool-executor.ts, confirmation.ts): lifecycle Validating → (AwaitingApproval if ASK_USER) → Scheduled → Executing → Success/Error/Cancelled. checkPolicy() maps ALLOW→schedule immediately, DENY→synthesized error result to the model (no execution), ASK_USER→AwaitingApproval. Read-only tools batch and run in parallel; mutators (edit tools, wait_for_previous:true) force sequential execution. Denial of one call cascades cancelAllQueued() for the batch; cancelAll() marks everything 'Operation cancelled by user'. Confirmations flow over MessageBus TOOL_CONFIRMATION_REQUEST/RESPONSE.
- **Takeaway**: Adopt the explicit state machine even though V1 is single-threaded: record each tool call's state transitions into the versioned JSONL session (validating/awaiting/executing/终 states + policy decision + outcome). This gives replay/debugging/audit for free and makes a later parallel executor a drop-in. Copy DENY-becomes-tool_result-error semantics — the model must be told why a call was blocked so the loop can continue. Defer parallelism itself; keep read-only-parallel as a V2 option.

### checkpointing / undo
- **How**: gemini-cli (docs/cli/checkpointing.md): before any approved filesystem-mutating tool executes, it commits a snapshot to a shadow git repo at ~/.gemini/history/<project_hash> (separate --git-dir, never touches the user's repo), and writes conversation history + the pending tool call as JSON under ~/.gemini/tmp/<project_hash>/checkpoints. /restore reverts files AND conversation AND re-presents the original tool call. Disabled by default; opt-in via settings.json.
- **Takeaway**: Adapt: Foundry already ships git tools; a shadow-git checkpoint (git --git-dir=%USERPROFILE%\.foundry\history\<hash> --work-tree=<project> add -A && commit) before each apply_patch/run_command is cheap, works offline, and is the single best compensating control for a no-sandbox V1. Record the checkpoint commit hash in the JSONL turn record so /restore can pair file state with conversation state. Keep it opt-in-by-default off for huge repos (perf), but recommend on.

### trusted folders / config provenance
- **How**: gemini-cli (docs/cli/trusted-folders.md): first run in a folder prompts trust folder / trust parent / don't trust, persisted centrally in ~/.gemini/trustedFolders.json. Untrusted folders run in restricted safe mode: project settings ignored, env not loaded, MCP servers not connected, auto-accept disabled, memory/custom commands not loaded. CI bypass via --skip-trust flag. Luban is even stricter: 'Project repos cannot grant permissions — rules live only in home config', and its own config files (client_local.py, tools_local.py, audit.jsonl) are off-limits to file tools.
- **Takeaway**: Copy both halves. For a trusted-HOST-but-untrusted-REPO threat model this is the highest-value control Foundry can ship without a sandbox: (1) permission grants live ONLY in the user-home policy file, never in the repo; (2) any project-level config (project memory file, project skills) loads only after a one-time trust prompt recorded in %USERPROFILE%\.foundry\trusted.json; (3) Foundry's own config/policy/audit files are deny-by-default targets for apply_patch.

### session store
- **How**: Luban (luban/sessions.py, paths.py): one JSON file per session in ~/.luban/sessions (never inside the project), header {id, project, created, updated, model, title} + messages; atomic_write_text (temp+rename) so a crash never leaves a half-written session; IDs are 'YYYY-MM-DD-HHMM-<2 hex bytes>' (sortable, human-readable); resolve() accepts list index, full ID, or case-insensitive title fragment, prefers current-project matches, and raises AmbiguousSession instead of guessing. gemini-cli stores chats under ~/.gemini/tmp/<project_hash>/chats with retention settings (default 30 days, maxAge/maxCount/minRetention) and a /resume session browser.
- **Takeaway**: Foundry's versioned JSONL is already a step past both (luban has no schema versioning — a real gap it admits). Copy: atomic writes via temp-file+os.replace (works on NTFS), sortable timestamp IDs, storage under user home keyed by project-path hash (never in-repo), resolve-by-index/id/fragment with explicit ambiguity errors, and gemini-cli's retention knobs. Session records will contain tool outputs that may embed secrets — see risks.

### swappable model backends
- **How**: Luban requires ~/.luban/client_local.py exposing build_client() returning anything Anthropic-shaped (.messages.create/.messages.stream), overridable via LUBAN_CLIENT_LOCAL env var; credentials stay user-owned, never in projects. Its agent (luban/agent.py) probes backend capabilities at runtime and degrades gracefully: if cache TTL is rejected retry without caching; if block-form system prompts fail fall back to plain concatenation. goose decouples via 15+ provider adapters behind one interface.
- **Takeaway**: Copy capability probing + graceful degradation — corporate OpenAI-Responses gateways reliably diverge from the real API (missing streaming modes, no caching, stricter schemas), so Foundry's ModelBackend protocol should be minimal (create_turn/stream_turn + a capabilities() probe cached per session) and every optional feature must have a documented fallback path. Keep backend config + credentials in user home only. Reject luban's 'user writes a Python file' plug for the corporate backend (config-driven instead), but it's a fine escape hatch for the personal backend.

### agent loop robustness
- **How**: luban/agent.py: run_turn() loops on stop_reason=='tool_use'; handles 'pause_turn' resumes up to MAX_PAUSE_RESUMES; on max_tokens truncation mid-tool-call it strips the incomplete tool_use block, injects a TRUNCATION_NUDGE message, and retries up to MAX_TRUNCATION_RETRIES; sanitize_history() strips stranded/unanswered tool_use blocks before each call; real token usage is read from API responses (estimates had under-counted ~36%); prompt-cache breakpoints separate the stable system prefix from volatile state (memory/journal) so frequent memory writes don't invalidate the conversation cache.
- **Takeaway**: Copy truncation recovery and history sanitization verbatim in spirit — orphaned tool_use/tool_result pairs are the #1 cause of hard API 400s in hand-rolled loops, and Foundry's versioned JSONL replay makes sanitize-on-load essential. Copy real-usage accounting from response metadata. Adapt the cache-breakpoint idea only if a backend's capabilities() reports prompt caching. Add an explicit max-turns cap (luban lacks one — only retry caps bound its loop).

### audit trail
- **How**: Luban logs every tool call including denials to append-only ~/.luban/audit.jsonl: timestamp, project, tool, target, decision, error flag; file tools are hard-coded unable to modify it. gemini-cli's OpenTelemetry layer logs tool calls with function name, args, duration, success, and user decision (accept/reject/modify), defaulting to a local file exporter (.gemini/telemetry.log) with a logPrompts privacy toggle.
- **Takeaway**: Copy luban's audit.jsonl exactly for V1 — it is the honest compensating control for no-sandbox: every ALLOW/ASK-outcome/DENY appended with the PolicyEngine decision and the resolved target (command line or path). Adapt gemini-cli's event taxonomy (tool name, args-digest, duration, decision, outcome) but skip OTel entirely — offline corp environment means local JSONL only, prompts excluded by default.

### MCP integration (future-proofing)
- **How**: gemini-cli (docs/tools/mcp-server.md): per-server config {command|url|httpUrl, args, env with $VAR expansion, cwd, timeout, trust, includeTools/excludeTools (exclude wins), headers}; discovered tools are namespaced mcp_{server}_{tool}; schemas sanitized for API compatibility; trust:true bypasses confirmation; otherwise dynamic 'always allow this tool' / 'always allow this server' allowlists (ProceedAlwaysTool/ProceedAlwaysServer outcomes); OAuth tokens in ~/.gemini/mcp-oauth-tokens.json; failed servers marked DISCONNECTED without killing startup.
- **Takeaway**: Reject for V1 (offline, stdlib-only), but two cheap future-proofing moves now: (1) make Foundry's internal tool result type MCP-shaped (list of typed content blocks: text/image/resource) so a later MCP bridge is mechanical — goose proves the whole tool layer can be MCP; (2) design PolicyEngine rule targets so server-scoped rules ('mcp:github:*') fit the existing tool:pattern grammar rather than needing a parallel trust system.

### sandboxing posture on Windows
- **How**: gemini-cli sandboxes via macOS Seatbelt profiles or Docker/Podman containers (project mounted at identical absolute path). Its Windows 'native sandbox' sets Low Mandatory Level with icacls on writable files — and those integrity-level changes PERSIST on the filesystem after the session, requiring manual `icacls ... /setintegritylevel Medium` cleanup. Container sandboxing is the only clean cross-platform story.
- **Takeaway**: Foundry's honest no-sandbox V1 is vindicated: gemini-cli's icacls approach shows Windows half-sandboxes leave persistent side effects and false confidence — avoid replicating it. Compensate with the stack this report assembles (deny-first policy, chain-split shell validation, trust-gated project config, shadow-git checkpoints, append-only audit). Document a V2 path (Docker/WSL2 container with identical-path mount, or Windows AppContainer/restricted-token job objects) but do not fake isolation in V1.

### permission config ergonomics (opencode)
- **How**: sst/opencode (opencode.ai/docs/permissions): permissions are a nested map resolving to allow/ask/deny; global wildcard then per-tool overrides; per-tool object syntax with glob patterns evaluated LAST-MATCH-WINS ('bash': {'*':'ask','git *':'allow','rm *':'deny'}); per-agent overrides; --auto mode approves everything not explicitly denied.
- **Takeaway**: Adopt this config shape for Foundry's policy file — it is markedly more readable than gemini-cli's priority numbers and maps 1:1 onto ALLOW/ASK/DENY. One caution: last-match-wins ordering in JSON relies on key order; Foundry (TOML/JSON in user home) should either document ordering semantics explicitly or keep luban's fixed deny>allow>default precedence with the nested syntax as sugar.

### memory/skills as plain files (luban, secondary)
- **How**: Luban loads project memory from LUBAN.md/CLAUDE.md/AGENTS.md, keeps personal memory tiers in home (~/.luban/SOUL.md, USER.md, memory/*.md facts, journal/), and skills as plain markdown (flat <name>.md or <name>/SKILL.md, project > personal precedence) where 'the model sees each skill's name and description and loads the full instructions itself when relevant'.
- **Takeaway**: Adapt minimally for V1: read a FOUNDRY.md/AGENTS.md project memory file (gated behind the trusted-folder prompt, since it is repo-supplied prompt input) and defer personal memory/skills. The name+description-only lazy loading pattern is the right token-budget design if skills are added later.


## Risks

- Prompt injection with no sandbox: repo files, tool outputs, and web/gateway responses are untrusted input that can steer run_command on a trusted host. Compensating controls are mandatory in V1: deny-first policy checked before allowlists, chain-splitting/metacharacter checks on every shell command, project config gated behind trust-on-first-use, permission grants never loadable from the repo (luban's rule), shadow-git checkpoints, and an append-only audit log.
- Windows shell parsing is the weakest link: Python's shlex is POSIX-only, and PowerShell/cmd metacharacters (';', '|', '&', '$( )', backticks, '^') can smuggle commands past prefix-matched allowlists. gemini-cli's splitter targets POSIX operators; Foundry must build a conservative tokenizer for its one chosen shell and route anything ambiguous to ASK — or allowlist rules become a false sense of safety.
- Shadow-git checkpointing cannot revert non-filesystem effects (pip installs, registry changes, network calls made by run_command) and may mislead users into over-trusting /restore; it is also potentially slow on large repos and NTFS (file locking, long-path issues) — gemini-cli ships it disabled by default for a reason.
- Session JSONL and audit.jsonl will capture secrets that flow through tool output (env dumps, tokens in command output, file contents). Stored under the user profile with 30-day-style retention they become a data-exfiltration and compliance liability in a corporate environment; Foundry needs retention limits, no prompts-in-telemetry by default, and ideally output redaction hooks.
- Corporate gateway drift: OpenAI-Responses-'compatible' gateways diverge (streaming modes, tool-call schemas, caching, token-usage fields). Without luban-style capability probing and graceful degradation, the loop breaks in ways users can't diagnose offline. Every optional backend feature needs a tested fallback.
- Policy-engine complexity rot: gemini-cli's numeric priorities (PRIORITY_SUBAGENT_TOOL=1.03, PRIORITY_YOLO_ALLOW_ALL=998) show how layered priority arithmetic becomes unmaintainable. Keep Foundry's model at fixed deny>allow>default precedence with well-tested pattern matching; resist adding priority numbers.
- Agent-loop failure modes seen in the wild: orphaned tool_use/tool_result pairs cause hard API 400s on resume (mitigate with sanitize-on-load), mid-tool-call max_tokens truncation corrupts history (mitigate with strip+nudge+retry), and luban's lack of a max-turns cap shows runaway-loop risk — Foundry should cap turns per user message.
- Provenance hygiene: gemini-cli is Apache 2.0 and luban's license was not verified during this research — Foundry is design-learning only (mandated), so copy patterns, never text or code; verify luban's LICENSE before borrowing anything verbatim, and note luban (2 stars) is inspiration, not battle-tested precedent.
- gemini-cli's docs and source layout churn rapidly (docs/architecture.md deleted, scheduler moved from core/src/core to core/src/scheduler within months); any Foundry design doc citing its paths should pin a commit hash.
