# Critique: product/scope

### [high] throughout / TL;DR - the document never states the real driving constraint (the motivation) behind Foundry's existence. Why not just use Codex CLI? Codex already supports ChatGPT login and can be pointed at any OpenAI-compatible endpoint (i.e. the corporate Gateway) through model_providers in config.toml, and it is Apache-2.0 open source. The only hint in the document is §3.6's "does not require installing a Node.js or Rust toolchain" (Codex CLI is a Rust binary) and the offline wheel install, which suggests the real constraint may be "the corporate environment forbids installing unapproved external agent binaries / forbids outbound calls", or audit compliance, or personal learning.
- **Why**: a different driving constraint means completely different V1 priorities: if it is corporate compliance, then the Gateway path + PolicyEngine + JSONL auditing are the core and the personal ChatGPT path is nice-to-have (or even cuttable); if it is learning, both the scope discipline and the meaning of the "no forking" clause change; if it is offline installation, packaging and dependency pinning become first-class. As written, both paths are called "the priority" with no basis for a ruling, so effort gets spread evenly and the hardest part (reverse-engineering a compliant ChatGPT login) may eat the entire budget.
- **Fix**: add a "Why Foundry / non-goals" section at the top: state the real constraint in one sentence (for example "corporate machines may not install or run Codex or any external coding agent, and everything must go through the internal Gateway and leave an audit log"), and explicitly rank the two paths from it.
- **Ask user**: what is Foundry's actual driving constraint -- is the company forbidding the installation of external agents such as Codex? Is everything required to go through the internal Gateway with an audit trail? Is it an offline environment with no Node or Rust? Or is this a personal learning project? (The answer decides whether the personal path or the corporate path is M1.)

### [high] §2 V1 scope / §3.4 approvals - the interaction model is entirely undefined: is Foundry an interactive session (a TUI/REPL where the user answers ASK mid-run and adds instructions), a one-shot headless runner (`foundry run "task"` runs to completion and prints a report), or both? §3.4's ASK approvals and §3.3's cancel imply interactivity, but §2's "accept a well-defined engineering task ... return a result with evidence" is one-shot phrasing. The comparison points have a clear product shape for both: Codex has an interactive TUI and a non-interactive `codex exec` mode (for CI/pipelines), see learn.chatgpt.com/docs/codex/cli.
- **Why**: this is the most upstream product decision and it touches nearly every component: when unattended, does ASK block, auto-DENY, or exit as blocked? Where does streaming output render? What are Ctrl+C cancellation semantics? How is the result returned (a final stdout message? a JSON report? an exit code mapping of completed/partial/blocked/failed/cancelled?). Until it is settled, neither the PolicyEngine nor the SessionStore interfaces can be frozen.
- **Fix**: pick one explicitly for V1 (suggestion: an interactive CLI session as the primary form, with ASK answered through a stdin prompt; if there is a headless mode, specify that ASK is always treated as DENY and terminates as blocked). Also add an "output contract" section: the mapping from the five termination states to process exit codes, and the structure of the final result (including evidence: the command + exit code + a diff summary).
- **Ask user**: is V1 an interactive CLI session, a one-shot headless runner, or both? If there is a headless mode, should ASK auto-deny and exit as blocked, or block waiting for a person?

### [high] throughout (missing section) - the CLI surface and the configuration story are entirely absent: there are no subcommands (run? login? logout? resume? status?), no flags, no configuration file format or location (TOML/JSON? %APPDATA%\foundry or ~/.foundry on Windows?), no configuration precedence (CLI flag > env > project config > user config?), and no UX for switching between the personal and corporate backends (auto-detection? `--backend corporate`? named profiles?). For comparison: Codex uses ~/.codex/config.toml plus a project-level .codex/config.toml (loaded only when the project is trusted), with model, approval_policy (untrusted/on-request/never), and named profiles (learn.chatgpt.com/docs/config-file/config-basic).
- **Why**: §3.2 lists 8 configuration items for the corporate Gateway (endpoint, headers, TLS, proxy...) without saying where they are written, in what format, or how they stay separate between a personal machine and a corporate one. Without a profile/switching mechanism, "both sides share one loop and only the connection layer changes" is just a slogan -- the very first demo gets stuck on "how do I tell Foundry which model to use".
- **Fix**: add §3.7 "CLI and configuration": define the subcommand set (at least login/logout/run/resume/status), the configuration file format and location, the precedence chain, and the profile mechanism (two built-in profiles, personal and corporate, each bundling backend + model + policy presets).
- **Ask user**: what format and location for the configuration file (suggestion: TOML, %APPDATA%\foundry\config.toml plus a repository-level override)? How is personal/corporate mode switched -- a machine-level default profile, or specified on each command line? Should the personal profile be forbidden from appearing on a corporate machine?

### [high] §3.3 the agent loop and tools (missing) - context management is entirely absent: no requirement describes how file contents enter the model context (does read_file have a line/byte ceiling, or pagination?), how run_command output is truncated before entering the context, what happens as the context window approaches its limit (compaction/summarisation? outright failure?), or how token growth across the rounds of a long task is controlled. §3.3 caps "output size", but that is a per-tool output ceiling, not a context budget. The comparison points treat this as core: Codex has /compact and automatic compaction (learn.chatgpt.com/docs/codex/cli), and Claude Code has compaction too.
- **Why**: this is the first wall V1 will hit: in a medium-sized repository, reading three large files plus one full test output is enough to blow the context, the model starts truncating and forgetting, and "a result with evidence" becomes meaningless. If it is not in the requirements, implementers will improvise individually, and it is very hard to retrofit (it affects the tool interfaces: truncation markers and artifact spillover both need room reserved at the interface layer).
- **Fix**: add hard requirements: (a) every tool output has a byte ceiling plus an explicit truncation marker; (b) output that exceeds it is written to disk as an artifact the model can page through with read_artifact (which incidentally gives read_artifact a reason to exist); (c) track token usage per round; (d) define the over-limit behaviour -- V1 need not do automatic compaction, but it must terminate cleanly as partial/failed and record termination reason=context_exhausted in the JSONL, rather than letting the request 400.
- **Ask user**: does V1 need automatic context compaction (compaction/summarisation), or is "over the limit means a clean failure reported as partial" acceptable, with compaction pushed to V2?

### [high] §3.3 V1 tools - read_artifact appears in the mandatory tool list but is never defined: what is an artifact? Who produces it (run_command's overflow output? a test report file? build products? a slice of the session log)? Where is it stored, what is its lifetime, how is it addressed (id? path?)? The tool set also carries an unstated assumption: there is no write_file/create_file tool, which means a new file can only be created through apply_patch -- and the document does not say whether apply_patch supports creating, deleting or renaming files, nor does it define the patch format.
- **Why**: an undefined tool cannot be implemented, cannot have policy rules written for it (is read_artifact ALLOW, or does it depend on where the artifact came from?), and cannot be tested. If apply_patch cannot create files, the basic "modify the repository" task (add a test file) is simply impossible; and if it can, the patch format (unified diff? Codex's custom apply_patch format?) is the product decision that determines whether a model can emit it reliably.
- **Fix**: write a definition for read_artifact (suggestion: an artifact is output produced by a tool within this session that exceeded the context budget and was written to disk, addressed by artifact_id, read-only, stored alongside the session directory); and add a capability boundary for apply_patch: it supports creating, modifying and deleting files, using format X (noting where the design was borrowed from, e.g. openai/codex's apply_patch tool).
- **Ask user**: what does the "artifact" in read_artifact mean -- the on-disk file of a tool's overflow output, task products (test reports / build output), or both?

### [high] throughout (missing section) - there are no V1 success criteria, acceptance tests, or eval story at all. "How do we know it works" has no answer whatsoever: no representative task set (golden tasks), no end-to-end acceptance scenario (such as "fix a failing test in repository X and produce evidence that it passes"), no smoke test matrix across the two backend paths plus the offline install, and no negative tests distilled from "lessons borrowed from others' failures" (malformed tool calls, retry loops, traversal attack samples).
- **Why**: §3 is entirely behavioural constraints (must not..., must...) with not one line of "what counts as done". Without an acceptance definition, V1's "done" is a feeling and will slide indefinitely; and without a task set there is no way to regression-test prompt or loop changes, so every change is made blind.
- **Fix**: add §4 "V1 acceptance": (a) 5-10 fixed acceptance scenarios (by task type: fix a bug, add a test, a small refactor, a read-only question), each specifying the expected termination state and evidence; (b) install acceptance: a clean Windows + Python 3.12, installed with pip --no-index, completing a task; (c) a negative case list (an out-of-bounds tool call is refused, a DENY cannot be overridden, a timeout cleans up subprocesses).
- **Ask user**: which categories should V1's representative acceptance task set cover (fix a bug / add a test / refactor / read-only code Q&A)? Which real repository does acceptance run against -- a corporate repository or a public sample one?

### [high] §1 / §3.1 / §3.2 (no ordering) - there is no milestone/roadmap, and the two "priorities" fight each other: §3.1 says "finish browser-based ChatGPT login first", §3.2 says "support a Responses-compatible Gateway first". Worse, the document admits the ChatGPT path may be blocked entirely ("if bounded research finds no supported route, mark it blocked") -- ChatGPT OAuth (auth.openai.com + a localhost:1455 callback, credentials in ~/.codex/auth.json) was designed for Codex, and third-party reuse is highly questionable under the ToS (see learn.chatgpt.com/docs/auth and the community discussions). And yet the document has no fallback plan for after it is blocked (using an OpenAI API key would need a separate question to be permitted).
- **Why**: V1's critical path contains a component the document itself annotates as "there may be no supported route", with no ordering and no Plan B. If the ChatGPT path is blocked the whole personal path dies -- possibly after the team has already burned weeks on browser login. The highest-risk unknown should be spiked first, not listed as an equal "priority" alongside the Gateway path that is known to work.
- **Fix**: add §5 milestones: M0 = the skeleton + the Gateway path completing one acceptance task end to end (no technical unknowns); M1 = a time-boxed ChatGPT login spike (a week, say) producing a feasible/blocked verdict; and put the blocked contingency (an OpenAI API key as the personal path substitute) into the document for approval now, rather than asking when it happens.
- **Ask user**: if bounded research confirms there is no supported third-party route for ChatGPT login, should the personal path downgrade to an OpenAI API key, be cut entirely in favour of the corporate Gateway alone, or should all of V1 wait? And: which is M1, the corporate Gateway or ChatGPT login?

### [medium] §3.4 / §2 PolicyEngine - "a corporate fixed DENY cannot be overridden by a task or by a temporary approval" -- but the origin, format, distribution and tamper-resistance of that policy are entirely undefined. Where are policy rules written (hard-coded? a configuration file?)? How do corporate and personal rules layer? On a trusted host (where the user is a local administrator) the user can edit the configuration file or even the source, so "cannot be overridden" is not technically enforceable; it can only be honest UI plus an audit trail. For comparison: Codex separates the user's config.toml from an administrative requirements.toml (which can force allow_managed_hooks_only and similar, ignoring user and project config), see the learn.chatgpt.com/docs/config-file series.
- **Why**: as written, this is an unimplementable requirement: without a design that separates a "managed policy file" from "user configuration", an unoverridable DENY has nowhere to live; and if the company genuinely intends to rely on it for compliance, it has to be stated clearly that this is policy-by-honesty (it prevents mistakes, not malice), or it over-promises to the company -- contradicting the document's own honesty principle that "approval is not a sandbox and must be disclosed as such".
- **Fix**: define the policy configuration model: a managed layer (pushed by the company, in its own file, loaded at Foundry startup and not overridable by user configuration) and a user layer; and state the threat model honestly in the document -- a managed DENY prevents accidents, not deliberate circumvention by a local administrator.
- **Ask user**: who writes and distributes the corporate fixed DENY rules (a managed file pushed by IT? bundled with the wheel?)? Do you accept the honest positioning of "prevents accidents only, not deliberate circumvention by a local administrator"?

### [medium] §3.5 SessionStore - the product side of sessions is all "record" and no "use": there is no resume/continue requirement (can work continue after an interruption, a cancel, or a crash?), no session list/show command, and no location or retention policy for session files. "Versioned JSONL" implies it can be replayed, but nothing in the document consumes it. For comparison: Codex has codex resume (listing/searching past sessions by repository).
- **Why**: for a task with multiple approvals that may run for tens of minutes, having everything discarded when the process dies will produce an immediate demand for resume; and whether resume is in V1 directly determines how SessionStore is written (a pure append-only audit log vs. event sourcing that can rebuild in-flight state), and converting the former into the latter later is a rewrite.
- **Fix**: rule on it now: either state explicitly for V1 that "the JSONL is audit and evidence only, with no resume" (written into the non-goals), or list resume as a requirement and add a state-rebuilding requirement to SessionStore; either way, add the session storage location (e.g. %LOCALAPPDATA%\foundry\sessions\<id>\) and a foundry sessions list command.
- **Ask user**: does V1 need session resume (continuing a task after an interruption), or is the JSONL audit evidence only, with resume explicitly deferred to V2?

### [medium] §2 / §3.3 / §3.5 the definition of workspace - how "in the specified repository" gets specified is never said: is workspace the current working directory? a --workspace flag? must it be a git repository (§3.5 requires recording a Git baseline at session start, which implies "a non-git directory cannot run" without saying so)? In a monorepo, is the workspace the repository root or a subdirectory (which affects the boundary check in the file tools and the noise in git_status)? Is a task spanning two repositories explicitly unsupported?
- **Why**: the workspace boundary is the reference point for the file tools' security checks (refusing traversal and junctions), and without a defined reference point §3.3's security requirements cannot be tested; the hard dependency on a Git baseline should likewise be promoted to an explicit precondition (refuse and report an error on a non-git directory), or implementers will improvise a range of half-measures.
- **Fix**: add a definition: the workspace is a single directory, either passed explicitly or defaulting to cwd, which must lie inside a git repository (otherwise startup refuses with a clear error); V1 is single-workspace, a subdirectory may be the workspace in a monorepo but git commands act on the containing repository; multi-repository tasks are a non-goal.
- **Ask user**: does V1 require the workspace to be a git repository (refusing a non-git directory outright)? May a subdirectory be the workspace inside a monorepo?

### [medium] §2 / §3.2 / §3.3 (missing) - the document says "Foundry must define its own interfaces first, then implement them independently", but the most central internal interface -- a unified, provider-agnostic representation of messages / tool calls / tool results -- is never listed as a deliverable. Model-side product decisions are missing too: which models are targeted and supported? Who owns the system prompt, where does it live, how is it iterated? Does the tool schema use the Responses API's function calling, or a custom format that is then converted? Is streaming a hard requirement or optional?
- **Why**: that intermediate representation is the precondition for "two backends sharing one loop"; without freezing it first, the ChatGPT path and the Gateway path will each grow a private format and the loop will fork in practice -- which is exactly the breeding ground for the "second loop" the document forbids. The system prompt is half of an agent product, and if it is not in the requirements nobody will give it version management and regression testing.
- **Fix**: list these explicitly among §2's deliverables: (a) Foundry's internal conversation/tool-call intermediate representation (documentation + type definitions), with both ModelBackends doing nothing but converting between it and the wire protocol; (b) the system prompt as a version-managed asset (packaged with the wheel), with changes required to pass the acceptance task set; (c) a statement of V1's target model list and whether streaming is required.

### [medium] §3.3 / §3.5 (missing) - token/cost budget UX is absent: §3.3 caps rounds, counts, time and output size, but not tokens; no requirement records each model call's usage (prompt/completion tokens) into the JSONL or summarises it at the end; and there is no product behaviour for 429/rate limits (the personal ChatGPT path has plan limits, and a corporate Gateway usually has quotas or billing) -- how many retries? what backoff? in what state does it terminate when over the limit, and how is the user told?
- **Why**: hitting plan limits on the personal path and quotas on the corporate path is a daily certainty, and undefined behaviour shows up as "hangs doing nothing" or a silent failure; and without usage records, cost attribution on the corporate path and "why is this so slow/expensive" cannot be answered -- a gap for a runtime whose selling point is auditability.
- **Fix**: add hard requirements: record usage into the JSONL on every model call; include total tokens and call counts in the final report; bound the retry count and backoff policy for 429/5xx; terminate as blocked (with reason=rate_limited) under sustained throttling rather than waiting forever; and an optional per-task token ceiling configuration item.

### [medium] §2 / §3.5 (missing) - there is no repository instruction file mechanism (the equivalent of Codex's AGENTS.md or Claude Code's CLAUDE.md), which produces a concrete hole: §3.5 requires "every validation claim has a real command and exit code", but does not say who decides the verification command -- the user in the task? a repository declaration ("this repository's test command is pytest -q")? or the model guessing? When the model guesses wrong (running pytest on a project that uses unittest), "verification with an exit code" becomes compliant but meaningless evidence.
- **Why**: the quality of the evidence in "a result with evidence" depends entirely on whether the verification command is the right one, and that is the product's core promise; without an instruction file mechanism, the user must dictate the build/test commands for every task, which is terrible UX -- and policy (which commands are pre-ALLOWed) loses its repository-level mounting point too.
- **Fix**: add a minimal repository instruction file to V1 (such as FOUNDRY.md, or a [project] section in foundry.toml) declaring the build/test/lint commands and any caveats, injected into the context at startup; validation claims preferentially match the commands declared there.
- **Ask user**: should V1 support a repository-level instruction/configuration file (declaring test and build commands, like AGENTS.md)? Which command governs verification -- the one specified in the task, the one declared by the repository, or the model's own choice?
