# Foundry decision log

> Format: one number per decision. **Status**: `confirmed` (the user ruled) /
> `provisional` (proposed by Claude, awaiting the user) / `overturned`.
> An overturned decision is never deleted; its status changes and it links to

## D-001 A wholly independent runtime: no forking, no calling into an existing coding agent
- **Date**: 2026-08-29 · **Status**: confirmed
- **Decision**: Foundry owns all of the code and interfaces for its agent loop, tools, policy, providers and sessions. It may study the public source of Codex, Claude Code, gemini-cli and others for design ideas, but it does not fork them, vendor them, or call them at runtime.
- **Rationale**: the corporate environment does not permit installing official agent products (only the corporate Gateway's API is available); and the project has a learning purpose of its own (understanding agent runtime design thoroughly).

## D-002 Python 3.12 + an offline wheel install
- **Date**: 2026-08-29 · **Status**: confirmed
- **Decision**: pin Python 3.12; build a standard wheel; the target installation is `python -m pip install --no-index --find-links <internal-wheel-dir> foundry`; dependencies are version-pinned with hashes; no Node.js or Rust toolchain is required.
- **Rationale**: software sources on corporate machines are restricted (JFrog Artifactory, with Node/Rust availability case by case); Python plus an internal wheel directory is the most certainly workable distribution channel.

## D-003 V1 is a trusted host and claims no sandbox
- **Date**: 2026-08-29 · **Status**: confirmed
- **Decision**: V1 is for trusted repositories only. Approval (policy) is a behavioural constraint, not a security boundary, and both the documentation and the CLI's first run must disclose this plainly.
- **Rationale**: a real sandbox on Windows (AppContainer / Job Object restrictions and the like) is expensive and easily gives a false sense of security; honest disclosure beats a half-built sandbox.

## D-004 The interactive terminal session comes first; headless follows
- **Date**: 2026-08-29 · **Status**: confirmed (the user's first round of answers)
- **Decision**: V1's core form is an interactive terminal session: conversation, streaming output, and side-effecting actions approved on the spot (ASK). A one-shot headless mode (something like `foundry exec`) comes in a later version.
- **Architectural constraint**: the UI and AgentRuntime are decoupled from day one -- the runtime exposes only an event stream plus an approval callback interface, and the terminal UI is merely its first consumer. Headless mode is then just a different consumer that "answers approvals automatically", with no change to the loop.

## D-005 ChatGPT login stays the highest priority
- **Date**: 2026-08-29 · **Status**: **overturned -> [D-009]** (the feasibility study confirmed it was blocked, and the user switched to an API key)
- **Decision**: browser-based ChatGPT login for the personal path remains the first hard requirement.
- **Rationale (the gist of the user's own words)**: the development environment has no OpenAI API key, so nothing can be verified through the API; the ChatGPT subscription is the only real model access available, and real E2E verification depends on that login working.
- **Risk and mitigation**: this remains the most uncertain item in the project (third-party use of a ChatGPT subscription may have no supported route, see [OQ-5](open-questions.md)). Mitigations:
  1. the bulk of runtime development does not depend on a real model -- a **mock / record-replay ModelBackend** must come first, so the loop, tools, policy and session are all testable offline;
  2. evaluate a **local OpenAI-compatible endpoint** (LM Studio / Ollama and the like) as a dev-only backend for smoke tests (see [OQ-8](open-questions.md));
  3. decide the fallback ladder only once the feasibility study produces evidence, rather than quietly downgrading.

## D-006 The corporate Gateway is multi-model (including non-OpenAI models such as Claude)
- **Date**: 2026-08-29 · **Status**: confirmed (the user's first round of answers)
- **Decision**: the Gateway hosts models from several vendors. The draft's assumption of "support OpenAI Responses-compatible first" **does not hold as the only assumption**.
- **Architectural constraints**:
  1. the internal message / tool call / streaming event types must be a **provider-agnostic specification of our own**, with a narrow adapter per protocol (Chat Completions / Responses / Anthropic Messages / a Gateway-specific protocol);
  2. the tool surface (especially the edit tool's format) must not be nailed to an OpenAI-specific format (such as V4A apply_patch); it needs to be configurable per model family, or to use a neutral format (see [OQ-7](open-questions.md));
  3. the Gateway's specific protocol, authentication and model list await the user's confirmation (see [OQ-6](open-questions.md)).

## D-009 The personal path is an OpenAI platform API key; ChatGPT login is marked blocked-with-evidence
- **Date**: 2026-08-29 · **Status**: confirmed (the user's second round of answers, on the feasibility evidence)
- **Decision**: research ([research/auth.md](research/auth.md)) confirmed that a non-Codex third-party tool has no supported way to run inference on a ChatGPT subscription -- the official "Sign in with ChatGPT" grants identity, not inference; the Codex subscription endpoint has an originator allowlist (a non-Codex client gets 403), so using it requires impersonating Codex, which violates both OpenAI's ToS and this project's charter, and has led to bans before. ## D-010 The edit format is a model-neutral anchored search/replace envelope
- **Date**: 2026-08-29 · **Status**: confirmed (the user's second round of answers)
- **Decision**: apply_patch uses an "envelope (Add/Delete/Update File) + anchored-text search/replace hunks" format (no line numbers), with the patch passed as a single opaque string argument; small files get a whole-file escape hatch; the format description goes explicitly into the system prompt.
- **Rationale**: the Gateway is multi-model (Claude included), Codex's V4A is a GPT-private trained format (the official support list is GPT-5.x only) and Claude mangles it; Claude Code, OpenHands and aider all converged independently on anchored text replacement; aider measured a 9x reduction in error rate from a lenient application gradient. The alternative of "two formats by model family" was rejected (it doubles the test surface), leaving an `edit_format` downgrade field in the per-model profile.

## D-011 Dirty working tree = warn and continue + a forced ASK on writes to dirty files
- **Date**: 2026-08-29 · **Status**: confirmed (the user's second round of answers)
- **Decision**: record a baseline at session start (the HEAD SHA + the list of dirty files); force an ASK for apply_patch on any file already dirty in the baseline; destructive commands such as `git checkout -- / reset --hard / clean / stash drop` go into a built-in, non-relaxable DENY (the circuit breaker).

## D-012 The session schema is replayable from day one; the resume feature is deferred to V2
- **Date**: 2026-08-29 · **Status**: confirmed (the user's second round of answers)
- **Decision**: the JSONL records enough to rebuild every model request byte for byte (which is also the basis of ReplayBackend testing); the feature layer of `foundry resume` (listing / selection / state validation) is deferred to V2.
- **Update (2026-11-03)**: the feature landed -> [D-035].

## D-013 PolicyEngine = a six-step pipeline + a deny-wins merge rule + a circuit breaker
- **Date**: 2026-08-29 · **Status**: confirmed (the user's third round, confirmed as a batch)
- **Decision**: `pre_tool callback -> DENY -> ASK -> mode baseline -> ALLOW -> interactive approval (headless = DENY)`; rules concatenate across layers, and deny-from-anywhere wins; a fixed precedence order, rejecting numeric priorities; a "can't parse -> ASK" safety valve; a hard-coded circuit breaker (.git, ~/.foundry, destructive commands).

## D-014 The dependency budget: stdlib first, with only rich at runtime (+ optional prompt_toolkit)
- **Date**: 2026-08-29 · **Status**: confirmed (the user's third round, confirmed as a batch)
- **Decision**: HTTP/SSE written on the stdlib (switching to the Windows system certificate store means zero configuration, and a corporate MITM proxy needs none); DPAPI and Job Objects through ctypes; no httpx/requests/keyring/psutil/pydantic/textual. The rationale and the rejected comparison are in [design.md](design.md) §11.

## D-015 read_artifact = retrieving over-limit tool output from disk
- **Date**: 2026-08-29 · **Status**: confirmed (the user's third round, confirmed as a batch)
- **Decision**: an artifact is the complete original text of a tool output from this session that exceeded the context budget and was written to disk, addressed by artifact_id, read-only, confined to the session directory. It pairs with the ContextManager truncation policy.

## D-016 The concurrency model is an asyncio core
- **Date**: 2026-08-29 · **Status**: confirmed (the user's third round, confirmed as a batch)
- **Decision**: streaming, cancellation and timeouts are expressed with asyncio (the Windows ProactorEventLoop supports subprocesses); synchronous tool bodies are wrapped in `asyncio.to_thread`. Interface signatures are frozen on that basis -- converting from sync to async afterwards is a rewrite.

## D-017 The finish tool is the only channel that produces a termination state and ValidationClaims
- **Date**: 2026-08-29 · **Status**: confirmed (the user's third round, confirmed as a batch; the mechanism was added after adversarial review found it missing)
- **Decision**: the V1 tool surface goes from 8 to 9: `finish{status, summary, claims:[{claim_text, command_event_id}]}`; the runtime verifies (the event exists, the exit code matches, the git check, HEAD has not moved) before emitting a Termination; a mismatch downgrades to `partial`. An ordinary turn in an interactive session ends normally without calling finish; a session closed with no finish is recorded as `cancelled`/`partial` depending on context.
- **Rationale**: a machine-enforceable completed gate with no structured production channel degrades into a gentlemen's agreement over free text -- and the acceptance item "forgery is refused" would have nothing to be implemented on.

## D-018 The single shell for run_command is Windows PowerShell 5.1 (powershell.exe -NoProfile)
- **Date**: 2026-08-29 · **Status**: confirmed (the user's third round, OQ-13)
- **Decision**: zero extra dependencies, preinstalled on all Windows. The segmenter is written for 5.1 syntax (`;`, the pipe `|`; **no `&&`/`||`**); the system prompt tells the model explicitly that "5.1 has no `&&`, use `;` instead"; a model that misuses them gets a clear parse error it can correct itself. Rejected: cmd (models are less fluent in it), Git Bash (its installation cannot be assumed), pwsh 7 (needs ~100MB of offline distribution, against the dependency budget).

## D-025 The breaker table covers every git subcommand that moves HEAD; `git clean -n` is an exception
- **Date**: 2026-08-30 · **Status**: confirmed (review round six)
- **Background**: the system prompt said by hand that "git commit/push/rebase/merge are always refused and cannot be approved", yet `git pull` -- which performs exactly that merge -- walked straight past the breaker table. A user writing one `run_command`/`git *` allow rule auto-approves it; and because it moves HEAD, `_finalize` then downgrades the whole run to `partial`, so **a session that ran an "allowed" command can never report completed**. The same holds for `cherry-pick` / `revert` / `am`, while `git apply` bypasses apply_patch's read-first requirement, dirty-file guard and anchor resolution.
- **Decision**: `HISTORY_MOVING_GIT` gains pull / cherry-pick / revert / am; `git apply` is listed separately (with a reason pointing at apply_patch). In the other direction, `git clean -n|--dry-run` only lists and deletes nothing, and was previously refused as "destroys uncommitted work" -- which is false for it, and it is precisely the model's only way to "look before asking", so it is exempted per reading (a flag the naive reading cannot see unlocks nothing).
- **Preventing a repeat**: that paragraph of the prompt is generated by `categorical_denials()` from the breaker table's constants; `test_prompt_matches_breaker.py` asserts alignment in both directions. A hand-written list drifts, and this one did.

## D-026 `command_timeout_s` is a ceiling rather than a default, shipped equal to the tool's own ceiling
- **Date**: 2026-08-30 · **Status**: confirmed (review round six)
- **Decision**: the key had type checking, range checking, provenance, and "the repository can only tighten" protection -- and no code read it. It now reaches the tool layer through `ToolContext.max_command_timeout_s` and is clamped in `RunCommand.execute`; the tool keeps its own lower default (120s), and the configuration item ships at the tool's ceiling (600s), so **the out-of-the-box behaviour is unchanged** while operations or a repository lowering it really takes effect, with the timeout message explaining why it was clamped.
- **In the same batch**: `session_retention_days` still has no implementation ([OQ-19](open-questions.md)) and is annotated in the code as reserved -- deleting a user's session logs on a default they never chose is not something to do casually.

## D-027 The event stream is redacted as a stream (keeping a lookback window), not event by event
- **Date**: 2026-08-30 · **Status**: confirmed (found by the clean-room check)
- **Background**: redaction.py declares three sinks, and the event one was never implemented -- the journal wrote `[redacted]` while `foundry exec --json` printed the same credential verbatim to stdout. After field-by-field redaction was added, the clean-room end-to-end still caught a leak: the model's text arrives **streamed in chunks**, the credential fell across two `MessageDelta`s, neither fragment matched, and the renderer reassembled it on screen.
- **Decision**: `EventSink` retains a tail whose length is "the longest credential Foundry actually holds" -- which is exactly the removal scope this module promises -- and releases it when the next chunk arrives or the stream ends. A **pattern** match longer than that tail can still be missed across chunks; pattern scanning is already labelled best-effort, and that positioning does not change.
- **Lesson**: a cross-layer property has to be verified across layers. The unit tests saw a clean event stream; the terminal showed plaintext.

## D-028 The connection class for a proxy tunnel must follow the **target's** scheme; a TLS-fronted proxy is refused explicitly
- **Date**: 2026-09-01 · **Status**: confirmed (the proxy path audit that the live endpoint prompted)
- **Background**: when choosing a connection class for an https target, `_connect` looked at the **proxy's** scheme. An ordinary `HTTP_PROXY=http://proxy:8080` therefore built a plain `HTTPConnection` and called `set_tunnel`, and `HTTPConnection.connect()` stops once CONNECT is sent -- it never calls `wrap_socket`. The result: **the API key, the prompt and the entire conversation crossed the tunnel in plaintext**, readable by the proxy and every hop after it. Reproduced against a real socket: the first byte into the tunnel is `'P'`, not `0x16`. The default `base_url` is `https://api.openai.com/v1`, so this is **the default path on any machine with a proxy configured**.
- **Decision**: the connection class follows the target's scheme -- an https target always uses `HTTPSConnection(proxy, context=...)` + `set_tunnel(origin)`, i.e. a plaintext CONNECT to the proxy and then TLS to the origin. The stdlib's `set_tunnel` cannot express "TLS to the proxy as well", so an `https://` proxy raises a `ConfigError` explaining the limitation rather than being quietly treated as one of the two. The non-tunnel branch (an http target through a proxy) now returns `Proxy-Authorization` to the request.
- **Preventing a repeat**: the test must **capture the bytes and look at them** -- assert the first byte into the tunnel is `0x16`, and that the canary is not in the plaintext. Asserting "it connected to the proxy host" does not count: the version that leaked satisfied that assertion too.

## D-030 Evidence must come **after** the change it claims to verify
- **Date**: 2026-09-01 · **Status**: confirmed (subsystem audit)
- **Background**: `verify_claims` only asked "is this command's exit code right", never "did it run after the change being verified". So: the model runs the tests green -> edits the code -> does not run them again -> finish cites the green run from **before** the edit. The exit code matches perfectly, and so a session that **verified nothing** reported `completed`.
- **Decision**: the runtime records the journal ordinal of the last change that successfully modified the workspace, and the gate refuses any claim numbered earlier than it. A change means a mutator tool (`apply_patch` and the like); `run_command` does not count -- the command is the source of the evidence itself.
- **Note**: this is a hole **in the project's core promise** that survived six rounds of adversarial review. Those rounds all attacked the segmenter and patching; the "ordering" dimension of the evidence chain had never been examined. There is now an end-to-end regression.

## D-029 A single BLOCKED does not end the REPL session
- **Date**: 2026-09-01 · **Status**: confirmed
- **Decision**: a dropped stream or an unreachable gateway ends **this round**, not the session. Previously any `outcome.status is not None` broke out, so one bit of network flakiness cost the user the whole conversation context -- while the comment on the code that raised it said "transient, so it will retry", and in fact no layer retries (the deltas are already on screen, and the round cannot be replayed). The comment now tells the truth, and BLOCKED prints a message and continues.

## D-031 Observation masking starts under context pressure, not after a fixed number of rounds
- **Date**: 2026-10-11 · **Status**: confirmed (found by running Foundry on its own repository)
- **Background**: every tool output older than the last 5 rounds was masked, whatever the context held. Given a real task in this repository (make `tool_end` carry its duration and exit code), Foundry read `runtime.py`, `command.py` and `tests/test_runtime.py`, had them masked five rounds later, and read them again -- about thirty re-reads in forty rounds. It hit the round budget with the source half-changed and no test written, while the context never passed 21k tokens of a 128k window. Masking saved nothing there and cost a round per re-read; it also rewrote the prefix every round, which defeats a provider's prompt cache.
- **Decision**: the projection is the full transcript until it would pass half the backend's window (`mask_above_fraction`). Past that, tool outputs are masked oldest first and only until it fits again; the last `mask_after_turns` rounds are never masked. Masking itself is unchanged, and so is the evidence for it in [design.md](design.md); what changed is when it applies.
- **Note**: none of the 1400-odd tests could see this. They script the model, and a scripted model never needs to look at something twice.

## D-032 A native Anthropic Messages adapter, on the wire protocol, replaying response content verbatim
- **Date**: 2026-10-13 · **Status**: confirmed (live; see docs/research/anthropic-messages.md)
- **Background**: Foundry reached Claude through Anthropic's OpenAI-compatible endpoint, which has no prompt caching. Building `examples/earnings_pm` it sent 1.69M input tokens with nothing read from cache, while the earnings agent itself, on the native API, read 398k of its 443k input tokens from cache.
- **Decision**: a fourth adapter, `anthropic_messages`, written against the Messages wire protocol over `httpc` rather than the `anthropic` SDK: `foundry.core` imports no third-party package, and the SDK's HTTP stack would break the offline dependency budget. Each response's content is replayed **verbatim** through a new opaque IR block (an additive IR change): thinking signatures bind the conversation prefix, and the API adds fields -- `tool_use.caller` appeared in the first capture -- that an adapter rebuilding blocks field by field would drop. Every request sets top-level `cache_control`; the system prompt, tools and history are byte-stable round to round, so each round reads the last from cache.
- **Masking and thinking**: observation masking (D-031) rewrites old tool results under context pressure, which invalidates every later thinking block, and on an account created on or after 2026-08-31 replaying one is a 400. Requests therefore set `thinking.block_binding.prefix_mismatch_behavior = "drop_block"`: the API drops the invalidated blocks and reports each in `input_transformations`, which the runtime shows as a warning. Degrading beats failing a session at the moment its context is fullest.
- **Fallbacks on by default**: `fallbacks = "default"` re-runs a safety-classifier decline on Anthropic's recommended model inside the same call. Foundry's own repository is full of breaker tables and bypass tests, exactly the content a cyber classifier can misread. After a mid-output fallback only the declined attempt's text is kept; its thinking and tool calls are neither replayed nor run. `fallbacks = "off"` disables it.
- **Credentials**: the protocol has its own variable (`ANTHROPIC_API_KEY`) and vault field, and its own default base URL, decided from config provenance: an OpenAI key never reaches Anthropic, and an Anthropic key never reaches the OpenAI default host.

## D-033 Foundry runs from its source tree; the wheel stays the distribution
- **Date**: 2026-10-31 · **Status**: confirmed (the user chose to keep the src layout and add a launcher)
- **Background**: a clone needed `pip install` for three reasons only: the src layout (nothing put `src/` on `sys.path`), the `foundry` command (an exe pip generates) and the tests (no path setting). Nothing in the package depends on being installed: the version is a literal, the system prompt loads through `importlib.resources` from the source tree, and no code reads install metadata. An editable install, meanwhile, writes a `.pth` that points at one checkout: on the development machine it pointed at the `blueprint` worktree, so `python -m pytest` in every other worktree tested that worktree's code, silently.
- **Decision**: pytest gets `pythonpath = ["src"]` (and ResearchOS's gets `../tools`); `run-foundry.py` at the root (stdlib only) puts `src/` first on `sys.path` and calls `foundry.__main__.main`; `foundry.cmd` wraps it, so a clone on `PATH` gives a `foundry` command in any repository; `foundry doctor` prints the directory the code was imported from. A CI job runs every suite and the CLI with only the dependencies installed. The launcher is not named `foundry.py`: at the root it would shadow the wheel when the offline-install job runs `python -m foundry` there.
- **Unchanged**: [D-002]. The corporate machine still gets a wheel from an internal directory, installed with `--no-index`, and the offline-install job still proves that path. The src layout stays: flattening it would move the source under every repository-relative link and leave `test_architecture_config.py` scanning an empty directory, where `rglob` finds nothing and the test passes.
- **Note**: D-002 and requirements §7 say the wheelhouse is hash-pinned and installed with `--require-hashes`, but there is no lock file, `build_wheelhouse.py` downloads from the unpinned `requirements.in`, and CI installs without `--require-hashes` -> [OQ-20](open-questions.md).

## D-034 Each branch records its delta from main in DELTA.md
- **Date**: 2026-10-31 · **Status**: confirmed (the user asked for an in-repo record of every branch's changes from main, emptied on main)
- **Background**: branches land on main by fast-forward, one per piece of work, mostly from worktrees under `.claude/worktrees/`. Nothing recorded, while a branch was open, what it changed and why; that lived in chat transcripts, and was lost when they were.
- **Decision**: `DELTA.md` at the root is tracked. On main it is an empty template; on a branch it holds hand-written notes (Summary, Changes, Decisions and open points, Verification) above a generated list of the files that differ from main. `scripts/delta.py` (stdlib only) does `refresh`, `check` and `reset`. The Claude Code hooks refresh it when a session starts and, when a turn ends, send the agent back once if the notes are missing or behind later commits. CI fails main unless the file is the template, and a branch with commits unless the Summary is written. Landing is `reset --commit` and then the fast-forward: that last commit restores the template and carries the notes in its message, so main's history keeps them.
- **Rejected**: an untracked file (it would not travel with the branch to CI or to a reviewer); a file per branch under `docs/` (main would accumulate them); regenerating the notes from commit messages (the point is the why, which the file list cannot give).

## D-035 A recorded session can be resumed from its journal
- **Date**: 2026-11-03 · **Status**: confirmed (the user chose session resume as the next Foundry feature)
- **Background**: [D-012] made the journal complete enough to rebuild every request and deferred the feature. A session ended by Ctrl+C, a budget, `finish` or a dropped connection could only be started again from nothing, losing its context and the files it had read.
- **Decision**: `foundry resume [session] [task]` and `foundry exec --resume <session> [task]` continue a session in its own journal (`last`, the newest session of the workspace, by default). The conversation is rebuilt from the journal alone. Every message is taken from the first `model_request` that carries it: history only grows, masking rewrites content but never drops a message, and the newest rounds are never masked. What follows the last request comes from three additive records -- `user_input`, `tool_reply`, and `model_response.opaque` -- and `model_request.turn` gives the rounds, so a resumed session masks exactly what the original would. A tool call with no recorded result is given one that says what is known: a finish that was accepted, with the status it produced; a call never run, with the reason the session stopped; a call interrupted while it ran, outcome unknown. A `resumed` record starts the new run, ordinals continue, and the session's artifacts resolve again.
- **What a resume may not weaken**: HEAD must be the commit the session started on, or the resume is refused -- its evidence and its account of what it changed are relative to that commit. Evidence starts over: commands from before the resume cannot back a finish claim, every file is read again before it is patched, and approvals given for the session are not carried over. Files that changed since the session started, other than those it patched itself, join the dirty-file guard and are named to the model. The restored text is the journal's redacted copy. One writer per session: each store holds an operating-system lock on `sessions/<id>/lock`, which a crashed process releases. Also refused: a journal from a newer schema or IR, another workspace, a journal whose requests do not continue one another, a context that is already full. A refused resume writes nothing.
- **Termination**: a journal may hold several terminations -- one per run, plus one for each blocked turn an interactive session went on past (that session now also records how it finally ended; it used to stop at the blocked one). Its status is the last one's, unless a `resumed` record follows it: a resumed run that has not ended reads as `interrupted`, never as the previous run's outcome. Every record is now flushed when written (the evidence types are also synced), so a killed process loses nothing it had recorded.
- **Rejected**: carrying the command evidence and the list of files read across a resume (sound only when the workspace is provably unchanged, which needs a fingerprint of it at every termination); a `message` record for every history append (the requests already hold every message, and with the request fold older journals resume by the same path, their missing results answered as above).
- **Deferred**: that fingerprint and the evidence it would let a resume keep; continuing after HEAD moved (re-baselining); resume counts in `foundry report`.

## D-036 A session's patches can be undone
- **Date**: 2026-11-04 · **Status**: confirmed (the next Foundry feature after resume, from the V2 candidates)
- **Background**: nothing but git could take back what a session changed, and git cannot tell the session's edits from the user's: checking out a file the user had edited before the session discards that work too, and a file the session created has to be found and deleted by hand. The roadmap listed "shadow-git checkpoint/undo".
- **Decision**: `apply_patch` records, for each file it changes, an exact copy of what the file held before (an artifact) and a digest of what it wrote, in its `tool_result` record (`changes`; the model never sees them). `foundry undo [session] [--last] [--yes] [--dry-run]`, and `/undo` in a session for its newest patch, put the earlier content back, newest change first, and write an `undo` record, so nothing is undone twice. A file is put back only while it holds exactly what the session wrote: an edit made since, by the user or by a command, leaves it alone, along with everything the session did to it before, and undo names it. A change between two of the session's patches stops undo there, so the file returns to what that change left. A move is reverted whole or not at all. Each file is checked again just before it is written, the write goes through the workspace's containment rules, and the kept copy must match its digest.
- **What it may not weaken**: content holding a credential Foundry knows is never kept -- artifacts are redacted, and a redacted copy written back would corrupt the file -- so such a file cannot be undone, and undo says why. After `/undo` the model is told which files changed back, it reads each one again before patching it, and commands run before the undo can no longer back a finish claim; a session resumed after `foundry undo` is told the same. `foundry undo` takes the session's lock, so a session another process has open is refused (`/undo` works there); a refused or declined undo writes nothing.
- **Rejected**: a shadow git repository (another `.git` for the tools to be kept out of, and its snapshots hold the user's changes too, so restoring one discards them); `git stash` or `checkout` (the same problem, and the stash is shared by every worktree); undoing commands (nothing records which files a command touched, so the files changed since the session started that no patch touched are listed as not undone instead).
- **Deferred**: redo; undoing back to a chosen patch rather than the newest one or all of them; removing directories a patch created.

## D-037 The model keeps a plan the user can see (`update_plan`)
- **Date**: 2026-11-04 · **Status**: confirmed (the user picked it as the next Foundry feature, from the V2 candidates)
- **Background**: [requirements.md](requirements.md) §5.2 froze V1 at nine tools and named a visible plan as the first V2 candidate; codex ships `update_plan` and Claude Code a todo list for the same reason. On a long task the user saw a stream of tool calls and no account of where the work was going or how far it had got, and plan mode asked the model to "produce the plan" with nowhere to put one but prose.
- **Decision**: a tenth tool, `update_plan {explanation?, plan: [{step, status}]}`, read-only and allowed by a built-in rule in every mode, plan mode included. Each call replaces the whole plan: at most 20 steps of at most 200 characters, each `pending`, `in_progress` or `completed`, at most one `in_progress`; an empty plan clears it. The plan belongs to the session, as the model's history does -- the model still sees every call it made, since masking never touches a call's arguments. The runtime keeps it; a `plan_updated` event carries it to the CLI, which draws it as a checklist in place of the tool's begin and end lines, and to `exec --json`; `/plan` in a session shows it again; the call's `tool_result` record keeps it (`plan`), so a resumed session restores it and shows it. The model's reply gives only the counts. The system prompt says when to use it (several steps; tick a step in the same turn as the work, not in a round of its own), and plan mode's paragraph now points at it.
- **What it may not weaken**: the plan is the model's own account, so it is never evidence, in either direction. `finish` adds the steps not marked completed to its summary, and warns when such a finish is `completed`, but changes no status over them: a step the model forgot to tick is not a failed task, and ticking every step proves nothing was done. Its text is model output shown to a person, so each step is reduced to one line of plain text when the call is validated (line breaks, control and format characters such as escape sequences and bidi overrides removed) and escaped when drawn, and the event sink now scrubs strings nested inside an event, not only its top-level fields -- a credential in a step used to reach every subscriber while the journal's copy was scrubbed.
- **Rejected**: downgrading `completed` while steps are open (it would turn a bookkeeping slip into a failed task, and a model could clear its plan first); per-step ids and partial updates (a whole plan per call is what codex does, and there is nothing to keep in step); a plan per task that resets with each new task (a resumed or continued task would lose the plan its history still shows).
- **Deferred**: approving a plan in plan mode from the session (switching the mode mid-session changes the system prompt the permissions paragraph is part of; landed as D-038); plan counts in `foundry report`.

## D-038 A plan is approved with `/approve`, which ends plan mode
- **Date**: 2026-11-06 · **Status**: confirmed (the user asked for it as the next Foundry feature, the follow-up D-037 deferred)
- **Background**: plan mode refused every edit and command "until the user approves your plan", and nothing could approve one: the user had to end the session and start another in a different mode, losing the context the plan was built in.
- **Decision**: `/approve`, typed in an interactive session in plan mode, shows the plan (or says the model set none) and asks one question: `(y)es`, ask before each edit -- `default` mode; `(e)dits` apply without asking -- `accept_edits`; anything else, or no answer, keeps planning and changes nothing. On approval the policy's mode changes, the system prompt's permissions paragraph is built again from it (`prompts.system_prompt`), a `mode_change` record `{from, to, by, reason}` is written and synced, and the next turn starts at once with a note that says plan mode is over, what the new mode allows (the paragraph's own line, `prompts.mode_line`), and to carry the plan out. Every `policy_decision` now records the `mode` it was made in, since the rules' digest does not cover it.
- **What it may not weaken**: only the user can approve -- the command is read from the user's own prompt, and nothing the model writes or a tool prints reaches the REPL's commands; the model is told how the user approves, not given a way to. The model is never told rules that no longer hold. Approval moves only to the two interactive modes, never `dont_ask`, and the dirty-file guard, the breaker, and every DENY rule apply exactly as before. A resume starts in the configured mode, as it starts every grant over ([D-035]): an approval is the user's decision about that run, and the resumed model is told the switch did not carry over.
- **Rejected**: approving by a tool the model calls (the model would grant itself the permissions plan mode withholds); keeping the old system prompt and telling the model only in the note (the system prompt would contradict it, on the paragraph whose whole purpose is to be true); `/approve` only arming the mode for the user's next message (approving the plan is the instruction to carry it out, and Claude Code continues the same way).
- **Deferred**: consulting where plan mode came from -- a managed `mode` is not a floor today (a user config overrides it), so there is nothing for `/approve` to defer to; if managed policy ever pins the mode, `/approve` must refuse it.

## D-039 Slash commands, custom prompts, and a read-only review
- **Date**: 2026-11-06 · **Status**: confirmed (the first step of the user's goal to make Foundry work "basically like codex"; the V2 candidate "skills and slash commands")
- **Background**: the interactive prompt knew five words (`/exit`, `/quit`, `/undo`, `/plan`, `/approve`), each an `if` in one loop, and sent anything else -- a mistyped `/udno` included -- to the model as a task. codex's prompt has a command set users rely on (`/status`, `/diff`, `/init`, `/review`, `/new`, custom prompts), and nothing in Foundry could show what the session had changed or how full its context was without leaving it.
- **Decision**: the REPL moves to `cli/repl.py` with a command table. A line is a command only when it starts with `/name` followed by whitespace or the end (`/usr/bin/python fails` is a task); an unknown name is reported, not sent. Built-ins: `/help`; `/status` (session, model, mode, tokens, context fill, plan, changed files); `/diff` (every uncommitted change, each marked as this session's or from before it, the tracked diff with control sequences stripped, new files with their size); `/plan`; `/approve`; `/undo`; `/review [focus]`; `/init` (asks the model to write FOUNDRY.md, refused if FOUNDRY.md or AGENTS.md exists); `/new` (closes this session's journal and starts a fresh session in the same workspace); `/exit`, `/quit`. A command that takes no arguments refuses them. Custom prompts are Markdown files named after their command, with optional `description` / `argument-hint` front matter and `$ARGUMENTS`, `$1`..`$9` (quotes respected) and `$$`; arguments are appended when the text has no placeholder. They come from `~/.foundry/prompts/` and, only in a trusted workspace, from `.foundry/prompts/` -- built-ins win over both, the user's over the repository's -- and a repository that has that folder now gets the trust question.
- **`/review` changes nothing**: it is not left to the prompt. While the review turn runs, the policy's `read_only` reason refuses every mutator, in every mode -- `accept_edits` included -- and is cleared afterwards even when the turn fails. Building it showed that **plan mode was weaker than documented**: its refusal sat at step 4, after the ASK rules, so in plan mode a patch to a file with uncommitted changes, or a command that could not be parsed, was put to the user -- who could approve it -- instead of refused. Plan mode and read-only tasks now refuse at step 2, with the DENY rules, before any ASK.
- **What it may not weaken**: commands come only from the user's typed line; the model, tool output and repository text never reach the table, and the model cannot add a prompt (writing under `.foundry/` is refused by the breaker). A repository's prompt is text the user sends as their own instruction, so it is read only where the user trusts the repository, is marked as the repository's when used, and is capped at 24 KB like FOUNDRY.md. `/new` starts every grant and all evidence over, as a new session does.
- **Rejected**: sending unknown commands to the model (a typo would start a paid turn); `/review` as a prompt alone (an `accept_edits` session would apply whatever "fix" the model decided on); custom prompts that run code or set the mode (a prompt is text; anything that changes permissions stays a built-in).
- **Deferred**: `/compact` (with summarised compaction, next); `/model` and `/mode` mid-session; prompt arguments by name (`$KEY=value`).

## D-040 Compaction by summary, before the context runs out
- **Date**: 2026-11-06 · **Status**: confirmed (the second step of the codex-parity order; the V2 candidate "LLM summarisation compaction", for which the `Compacted` record was reserved)
- **Background**: masking (D-031) stubs old tool output but never the last five rounds, so a task whose recent rounds alone filled the window -- a few large reads -- still ended `partial(context window exhausted)`, and a long interactive session could only be thrown away. The masking evidence (arXiv 2508.21433) stands, and masking stays first; it just cannot be the last step.
- **Decision**: at the top of each round, once the projection, after masking, is past 80% of the window and the history holds model output, the runtime asks the model for a handoff summary (`prompts/compact.md`: the task, what is done, the checks run, the current state, next steps, decisions and dead ends). The request is the conversation as projected plus that instruction, with the same tools (a history with tool calls is refused without them); a tool call in the reply is ignored and its text is the summary. The history becomes the user's own messages -- newest first within a tenth of the window, the first that does not fit cut down, then put back in order, earlier summaries left out -- followed by the summary, capped at 15% of the window, with the current plan appended, all stamped with the current round. `/compact [focus]` does the same on request. `runtime.auto_compact = false` turns the automatic one off. The journal records the summary request and response with `purpose: "compact"`, its token usage, and a `compacted` record (synced) holding the new history, its reason (`auto` or `user`), and the estimated tokens before and after; the report counts compactions and leaves them out of rounds.
- **What it may not weaken**: the summary is model output and is scrubbed by the redactor before it enters the history, as tool output is. Every file read before the compaction must be read again before it is patched -- its contents are no longer in context -- and the summary says so. Command evidence is untouched: a claim can still cite a command run before the compaction, and staleness after a change still applies. A failure (no reply, an error, an empty summary) leaves the conversation exactly as it was, says so, and stops automatic compaction for the rest of the task, so a broken gateway is not paid for every round; masking and the clean termination still apply. A Ctrl+C during the summary cancels the task. Resume follows a compaction: the fold skips the summary request and response and resets the history at the `compacted` record, so the rebuilt conversation is byte for byte the live one, and a crash between the summary and its record resumes from before it.
- **Rejected**: compacting at a fixed number of rounds (it would summarise while masking alone was enough, and every summary loses detail); summarising only the tool output (the reasoning between calls is what a handoff needs); keeping the last few rounds verbatim next to the summary (they are what filled the window); a separate, cheaper model for the summary (a second backend to configure and trust).
- **Deferred**: compacting in the middle of a round's tool calls; showing the summary to the user (it is in the journal); a configurable threshold.

## D-041 Instructions in layers: the user's own, then the repository's from its top down
- **Date**: 2026-11-06 · **Status**: confirmed (the third step of the codex-parity order; extends D-019)
- **Background**: only a `FOUNDRY.md` (or `AGENTS.md`) at the workspace root was read. Started in a package of a larger repository, Foundry missed the repository's own notes; and a user had nowhere to keep instructions for every session ("answer in English", "prefer small commits") except by repeating them. codex reads a global `AGENTS.md` and then every `AGENTS.md` from the repository's root down to the working directory.
- **Decision**: the system prompt's instructions are the user's own `FOUNDRY.md` or `AGENTS.md` from the Foundry folder (the one holding `config.toml`), then the repository's, one per directory (`FOUNDRY.md` over `AGENTS.md`), from the repository's top -- the nearest directory at or above the workspace holding `.git`, a worktree's own included -- down to the workspace, top first, with a sentence saying the later, more specific one wins. Outside a repository only the workspace itself is read, so a loose folder never picks up notes from wherever it sits; directories below the workspace are not read. One file reads exactly as before. The repository's files share the 24 KB budget, top first: a file past it is named and left out. `/status` names the files the session loaded.
- **What it may not weaken**: the repository's files, the ones above the workspace included, are read only where the user trusts the workspace, and any of them now raises the trust question. The user's own file needs no trust -- it is theirs, like `config.toml` -- and is capped like the rest. Nothing here changes what the instructions are: guidance, never authority to bypass approvals.
- **Rejected**: reading files below the working directory as the model enters them (instructions that change mid-task with what the model happens to open; a later step if it is wanted); reading up past the repository's top (a home directory's notes are not the project's); a separate budget per file (a deep tree could fill the window with instructions).
- **Deferred**: `FOUNDRY.override.md`-style per-user overrides inside a repository; a setting to change the file names.

## D-042 Settings on the command line: -m, --mode, -c, --profile, exec -o
- **Date**: 2026-11-06 · **Status**: confirmed (the fourth step of the codex-parity order)
- **Background**: requirements section 4.3 put CLI flags at the top of configuration and named a profile layer, but there were no such flags -- trying another model meant editing `config.toml` -- and no profiles. `foundry exec` always ran in `dont_ask`, so an unattended run could edit nothing without ALLOW rules, and a script had no clean way to read what the run concluded.
- **Decision**: `run`, `resume`, `exec` and `record` take `-m/--model`, `--mode`, `-c/--config key=value` (repeatable) and `--profile`; `foundry -m x ...` with a flag first means `run`. A `-c` key is `backend.<key>`, `runtime.<key>` or a bare key from either table; its value is read as TOML and as plain text when it is not one, so `-c model=gpt-5` needs no quotes; an unknown key is an error, not a setting nobody reads. Profiles are `[profiles.<name>]` tables in the user's own `config.toml`, holding `backend`, `runtime` and `permissions` like the file itself, chosen by `--profile`, `FOUNDRY_PROFILE` or a top-level `profile = "..."`, in that order, and applied between the user's settings and the repository's, as section 4.3 always said; the profile's name is recorded in the session header. `exec --mode` takes `dont_ask` (the default whatever the files say), `plan` or `accept_edits`: an unattended run that may apply patches inside the workspace but still runs no command a rule does not allow, which is the closest Foundry comes to codex's `--full-auto`. In those modes the permissions paragraph adds that nobody can approve and that the run ends with `finish`. `exec -o/--output-last-message FILE` writes the run's last word -- the finish summary, or the final reply, or why it stopped -- scrubbed like the journal.
- **What it may not weaken**: secrets stay out of command lines, which other processes can read: `-c` refuses `api_key` and `headers`. Profiles come only from the user's own file; a repository's `profiles` table is never read, so it cannot redirect the endpoint by name. The repository layer still comes after a profile and can still only tighten. `exec` never takes its mode from configuration, only from `--mode`, and `default` is not offered there (nobody can answer its questions). `/new` builds the next session with the same flags.
- **Rejected**: a bare word as an implicit task (`foundry fix it`): a mistyped subcommand would start a paid run; `-c` for permission rules (rules belong in a file the user can read back); `exec --mode` choices that ask (they would all be refusals).
- **Deferred**: `--add-dir` (Foundry has one workspace root); `-c` lists for permission rules; a `/model` command mid-session.

## D-043 An MCP client over stdio, under the same policy
- **Date**: 2026-11-06 · **Status**: confirmed (the fifth step of the codex-parity order; V1 only aligned the IR with MCP's shapes)
- **Background**: codex, Claude Code and most other agents take tools from MCP servers -- a team's docs search, an issue tracker, a database -- and Foundry could only offer its own ten. The IR's content blocks were shaped after MCP from the start, so the work was the client and the policy, not the conversation.
- **Decision**: `[mcp_servers.<name>]` tables (`command`, `args`, `env`, `env_vars`, `startup_timeout_s`, `tool_timeout_s`, `read_only`, `enabled`) in the user's own `config.toml` or a profile. At session start every enabled server is started at once, over stdio: JSON-RPC 2.0, one message per line, protocol `2025-06-18`, `initialize` then `notifications/initialized`, then `tools/list` (paged, at most 100 tools a server) if the server has the tools capability. Each tool is offered as `mcp__<server>__<tool>` (letters, digits, `_` and `-`, at most 64 characters, a digest keeping long names apart), with the server's description and argument schema (an object schema, at most 16 KB; an empty object when it gives none); a name already taken is not offered. A call checks the required arguments, sends `tools/call`, and renders the result's text -- naming the content it cannot show (images, audio, binary resources) rather than dropping it -- truncated like a command's output with the full text kept as an artifact; `isError` makes it an error for the model. The server's own requests get an answer -- `ping`, and "not offered" to everything else (no sampling, roots or elicitation) -- and its notifications and any stray log lines on stdout are ignored. Rules may name tools by pattern (`mcp__docs__*`), matched case-sensitively; their arguments, as canonical JSON, are what a rule's pattern matches. `/status` lists the servers; each one's tools, or why it is not available, are journaled as a `capability_probe` record and shown at start.
- **What it may not weaken**: a server is a program, so only the user's own files can name one; a repository's config that tries is refused outright. Every MCP tool is a mutator to the policy: refused in plan mode and during `/review`, asked about otherwise, denied in `dont_ask` and headless runs, unless a rule allows it -- a server's own "read-only" hints are not trusted, since a read-only fetch is exactly how data leaves. Only `read_only = true` in the user's entry makes its tools read-only, which offers them in plan mode and `/review`, still asking first. The server gets the environment a command gets, with credential-shaped variables removed; a secret reaches it only by name through `env_vars`. It runs under a job object, and the session's end closes its input, then ends it and everything it started. A server that fails to start, hangs, or dies costs a warning or an error result, never the session; a call that hangs times out, and Ctrl+C reaches it. Its output is untrusted content, scrubbed before the model sees it like any tool's.
- **Rejected**: trusting `readOnlyHint` (see above); the HTTP transports (a server reachable over the network is a connection setting with its own trust questions -- later, if wanted); starting servers on first use (a slow server would stall the first turn that needs it, and its tools must be in the first request anyway); letting servers sample the model (a server could then spend the user's tokens on prompts of its own).
- **Deferred**: streamable HTTP servers; resources and prompts (`resources/list`, `prompts/list`); `notifications/tools/list_changed`; showing images once `view_image` lands.
