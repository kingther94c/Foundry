## D-001 A wholly independent runtime: no forking, no calling into an existing coding agent
- **Date**: 2026-08-29 · **Status**: confirmed
- **Decision**: Foundry owns all of the code and interfaces for its agent loop, tools, policy, providers and sessions. It may study the public source of Codex, Claude Code, gemini-cli and others for design ideas, but it does not fork them, vendor them, or call them at runtime.
- **Rationale**: the corporate environment does not permit installing official agent products (only the corporate Gateway's API is available); and the project has a learning purpose of its own (understanding agent runtime design thoroughly).

## D-002 Python 3.12 + an offline wheel install
- **Date**: 2026-08-29 · **Status**: confirmed
- **Decision**: pin Python 3.12; build a standard wheel; the target installation is `python -m pip install --no-index --find-links <internal-wheel-dir> foundry`; dependencies are version-pinned with hashes; no Node.js or Rust toolchain is required.
- **Rationale**: software sources on corporate machines are restricted (JFrog Artifactory, with Node/Rust availability case by case); Python plus an internal wheel directory is the most certainly workable distribution channel.

## D-003 V1 is a trusted host and claims no sandbox
- **Date**: 2026-08-29 · **Status**: confirmed
- **Decision**: V1 is for trusted repositories only. Approval (policy) is a behavioural constraint, not a security boundary, and both the documentation and the CLI's first run must disclose this plainly.
- **Rationale**: a real sandbox on Windows (AppContainer / Job Object restrictions and the like) is expensive and easily gives a false sense of security; honest disclosure beats a half-built sandbox.

## D-004 The interactive terminal session comes first; headless follows
- **Date**: 2026-08-29 · **Status**: confirmed (the user's first round of answers)
- **Decision**: V1's core form is an interactive terminal session: conversation, streaming output, and side-effecting actions approved on the spot (ASK). A one-shot headless mode (something like `foundry exec`) comes in a later version.
- **Architectural constraint**: the UI and AgentRuntime are decoupled from day one -- the runtime exposes only an event stream plus an approval callback interface, and the terminal UI is merely its first consumer. Headless mode is then just a different consumer that "answers approvals automatically", with no change to the loop.

## D-005 ChatGPT login stays the highest priority
- **Date**: 2026-08-29 · **Status**: **overturned -> [D-009]** (the feasibility study confirmed it was blocked, and the user switched to an API key)
- **Decision**: browser-based ChatGPT login for the personal path remains the first hard requirement.
- **Rationale (the gist of the user's own words)**: the development environment has no OpenAI API key, so nothing can be verified through the API; the ChatGPT subscription is the only real model access available, and real E2E verification depends on that login working.
- **Risk and mitigation**: this remains the most uncertain item in the project (third-party use of a ChatGPT subscription may have no supported route, see [OQ-5](open-questions.md)). Mitigations:
  1. the bulk of runtime development does not depend on a real model -- a **mock / record-replay ModelBackend** must come first, so the loop, tools, policy and session are all testable offline;
  2. evaluate a **local OpenAI-compatible endpoint** (LM Studio / Ollama and the like) as a dev-only backend for smoke tests (see [OQ-8](open-questions.md));
  3. decide the fallback ladder only once the feasibility study produces evidence, rather than quietly downgrading.

## D-006 The corporate Gateway is multi-model (including non-OpenAI models such as Claude)
- **Date**: 2026-08-29 · **Status**: confirmed (the user's first round of answers)
- **Decision**: the Gateway hosts models from several vendors. The draft's assumption of "support OpenAI Responses-compatible first" **does not hold as the only assumption**.
- **Architectural constraints**:
  1. the internal message / tool call / streaming event types must be a **provider-agnostic specification of our own**, with a narrow adapter per protocol (Chat Completions / Responses / Anthropic Messages / a Gateway-specific protocol);
  2. the tool surface (especially the edit tool's format) must not be nailed to an OpenAI-specific format (such as V4A apply_patch); it needs to be configurable per model family, or to use a neutral format (see [OQ-7](open-questions.md));
  3. the Gateway's specific protocol, authentication and model list await the user's confirmation (see [OQ-6](open-questions.md)).

## D-009 The personal path is an OpenAI platform API key; ChatGPT login is marked blocked-with-evidence
- **Date**: 2026-08-29 · **Status**: confirmed (the user's second round of answers, on the feasibility evidence)
- **Decision**: research ([research/auth.md](research/auth.md)) confirmed that a non-Codex third-party tool has no supported way to run inference on a ChatGPT subscription -- the official "Sign in with ChatGPT" grants identity, not inference; the Codex subscription endpoint has an originator allowlist (a non-Codex client gets 403), so using it requires impersonating Codex, which violates both OpenAI's ToS and this project's charter, and has led to bans before. ## D-010 The edit format is a model-neutral anchored search/replace envelope
- **Date**: 2026-08-29 · **Status**: confirmed (the user's second round of answers)
- **Decision**: apply_patch uses an "envelope (Add/Delete/Update File) + anchored-text search/replace hunks" format (no line numbers), with the patch passed as a single opaque string argument; small files get a whole-file escape hatch; the format description goes explicitly into the system prompt.
- **Rationale**: the Gateway is multi-model (Claude included), Codex's V4A is a GPT-private trained format (the official support list is GPT-5.x only) and Claude mangles it; Claude Code, OpenHands and aider all converged independently on anchored text replacement; aider measured a 9x reduction in error rate from a lenient application gradient. The alternative of "two formats by model family" was rejected (it doubles the test surface), leaving an `edit_format` downgrade field in the per-model profile.

## D-011 Dirty working tree = warn and continue + a forced ASK on writes to dirty files
- **Date**: 2026-08-29 · **Status**: confirmed (the user's second round of answers)
- **Decision**: record a baseline at session start (the HEAD SHA + the list of dirty files); force an ASK for apply_patch on any file already dirty in the baseline; destructive commands such as `git checkout -- / reset --hard / clean / stash drop` go into a built-in, non-relaxable DENY (the circuit breaker).

## D-012 The session schema is replayable from day one; the resume feature is deferred to V2
- **Date**: 2026-08-29 · **Status**: confirmed (the user's second round of answers)
- **Decision**: the JSONL records enough to rebuild every model request byte for byte (which is also the basis of ReplayBackend testing); the feature layer of `foundry resume` (listing / selection / state validation) is deferred to V2.
- **Update (2026-11-03)**: the feature landed -> [D-035].

## D-013 PolicyEngine = a six-step pipeline + a deny-wins merge rule + a circuit breaker
- **Date**: 2026-08-29 · **Status**: confirmed (the user's third round, confirmed as a batch)
- **Decision**: `pre_tool callback -> DENY -> ASK -> mode baseline -> ALLOW -> interactive approval (headless = DENY)`; rules concatenate across layers, and deny-from-anywhere wins; a fixed precedence order, rejecting numeric priorities; a "can't parse -> ASK" safety valve; a hard-coded circuit breaker (.git, ~/.foundry, destructive commands).

## D-014 The dependency budget: stdlib first, with only rich at runtime (+ optional prompt_toolkit)
- **Date**: 2026-08-29 · **Status**: confirmed (the user's third round, confirmed as a batch)
- **Decision**: HTTP/SSE written on the stdlib (switching to the Windows system certificate store means zero configuration, and a corporate MITM proxy needs none); DPAPI and Job Objects through ctypes; no httpx/requests/keyring/psutil/pydantic/textual. The rationale and the rejected comparison are in [design.md](design.md) §11.

## D-015 read_artifact = retrieving over-limit tool output from disk
- **Date**: 2026-08-29 · **Status**: confirmed (the user's third round, confirmed as a batch)
- **Decision**: an artifact is the complete original text of a tool output from this session that exceeded the context budget and was written to disk, addressed by artifact_id, read-only, confined to the session directory. It pairs with the ContextManager truncation policy.

## D-016 The concurrency model is an asyncio core
- **Date**: 2026-08-29 · **Status**: confirmed (the user's third round, confirmed as a batch)
- **Decision**: streaming, cancellation and timeouts are expressed with asyncio (the Windows ProactorEventLoop supports subprocesses); synchronous tool bodies are wrapped in `asyncio.to_thread`. Interface signatures are frozen on that basis -- converting from sync to async afterwards is a rewrite.

## D-017 The finish tool is the only channel that produces a termination state and ValidationClaims
- **Date**: 2026-08-29 · **Status**: confirmed (the user's third round, confirmed as a batch; the mechanism was added after adversarial review found it missing)
- **Decision**: the V1 tool surface goes from 8 to 9: `finish{status, summary, claims:[{claim_text, command_event_id}]}`; the runtime verifies (the event exists, the exit code matches, the git check, HEAD has not moved) before emitting a Termination; a mismatch downgrades to `partial`. An ordinary turn in an interactive session ends normally without calling finish; a session closed with no finish is recorded as `cancelled`/`partial` depending on context.
- **Rationale**: a machine-enforceable completed gate with no structured production channel degrades into a gentlemen's agreement over free text -- and the acceptance item "forgery is refused" would have nothing to be implemented on.

## D-018 The single shell for run_command is Windows PowerShell 5.1 (powershell.exe -NoProfile)
- **Date**: 2026-08-29 · **Status**: confirmed (the user's third round, OQ-13)
- **Decision**: zero extra dependencies, preinstalled on all Windows. The segmenter is written for 5.1 syntax (`;`, the pipe `|`; **no `&&`/`||`**); the system prompt tells the model explicitly that "5.1 has no `&&`, use `;` instead"; a model that misuses them gets a clear parse error it can correct itself. Rejected: cmd (models are less fluent in it), Git Bash (its installation cannot be assumed), pwsh 7 (needs ~100MB of offline distribution, against the dependency budget).

## D-025 The breaker table covers every git subcommand that moves HEAD; `git clean -n` is an exception
- **Date**: 2026-08-30 · **Status**: confirmed (review round six)
- **Background**: the system prompt said by hand that "git commit/push/rebase/merge are always refused and cannot be approved", yet `git pull` -- which performs exactly that merge -- walked straight past the breaker table. A user writing one `run_command`/`git *` allow rule auto-approves it; and because it moves HEAD, `_finalize` then downgrades the whole run to `partial`, so **a session that ran an "allowed" command can never report completed**. The same holds for `cherry-pick` / `revert` / `am`, while `git apply` bypasses apply_patch's read-first requirement, dirty-file guard and anchor resolution.
- **Decision**: `HISTORY_MOVING_GIT` gains pull / cherry-pick / revert / am; `git apply` is listed separately (with a reason pointing at apply_patch). In the other direction, `git clean -n|--dry-run` only lists and deletes nothing, and was previously refused as "destroys uncommitted work" -- which is false for it, and it is precisely the model's only way to "look before asking", so it is exempted per reading (a flag the naive reading cannot see unlocks nothing).
- **Preventing a repeat**: that paragraph of the prompt is generated by `categorical_denials()` from the breaker table's constants; `test_prompt_matches_breaker.py` asserts alignment in both directions. A hand-written list drifts, and this one did.

## D-026 `command_timeout_s` is a ceiling rather than a default, shipped equal to the tool's own ceiling
- **Date**: 2026-08-30 · **Status**: confirmed (review round six)
- **Decision**: the key had type checking, range checking, provenance, and "the repository can only tighten" protection -- and no code read it. It now reaches the tool layer through `ToolContext.max_command_timeout_s` and is clamped in `RunCommand.execute`; the tool keeps its own lower default (120s), and the configuration item ships at the tool's ceiling (600s), so **the out-of-the-box behaviour is unchanged** while operations or a repository lowering it really takes effect, with the timeout message explaining why it was clamped.
- **In the same batch**: `session_retention_days` still has no implementation ([OQ-19](open-questions.md)) and is annotated in the code as reserved -- deleting a user's session logs on a default they never chose is not something to do casually.

## D-027 The event stream is redacted as a stream (keeping a lookback window), not event by event
- **Date**: 2026-08-30 · **Status**: confirmed (found by the clean-room check)
- **Background**: redaction.py declares three sinks, and the event one was never implemented -- the journal wrote `[redacted]` while `foundry exec --json` printed the same credential verbatim to stdout. After field-by-field redaction was added, the clean-room end-to-end still caught a leak: the model's text arrives **streamed in chunks**, the credential fell across two `MessageDelta`s, neither fragment matched, and the renderer reassembled it on screen.
- **Decision**: `EventSink` retains a tail whose length is "the longest credential Foundry actually holds" -- which is exactly the removal scope this module promises -- and releases it when the next chunk arrives or the stream ends. A **pattern** match longer than that tail can still be missed across chunks; pattern scanning is already labelled best-effort, and that positioning does not change.
- **Lesson**: a cross-layer property has to be verified across layers. The unit tests saw a clean event stream; the terminal showed plaintext.

## D-028 The connection class for a proxy tunnel must follow the **target's** scheme; a TLS-fronted proxy is refused explicitly
- **Date**: 2026-09-01 · **Status**: confirmed (the proxy path audit that the live endpoint prompted)
- **Background**: when choosing a connection class for an https target, `_connect` looked at the **proxy's** scheme. An ordinary `HTTP_PROXY=http://proxy:8080` therefore built a plain `HTTPConnection` and called `set_tunnel`, and `HTTPConnection.connect()` stops once CONNECT is sent -- it never calls `wrap_socket`. The result: **the API key, the prompt and the entire conversation crossed the tunnel in plaintext**, readable by the proxy and every hop after it. Reproduced against a real socket: the first byte into the tunnel is `'P'`, not `0x16`. The default `base_url` is `https://api.openai.com/v1`, so this is **the default path on any machine with a proxy configured**.
- **Decision**: the connection class follows the target's scheme -- an https target always uses `HTTPSConnection(proxy, context=...)` + `set_tunnel(origin)`, i.e. a plaintext CONNECT to the proxy and then TLS to the origin. The stdlib's `set_tunnel` cannot express "TLS to the proxy as well", so an `https://` proxy raises a `ConfigError` explaining the limitation rather than being quietly treated as one of the two. The non-tunnel branch (an http target through a proxy) now returns `Proxy-Authorization` to the request.
- **Preventing a repeat**: the test must **capture the bytes and look at them** -- assert the first byte into the tunnel is `0x16`, and that the canary is not in the plaintext. Asserting "it connected to the proxy host" does not count: the version that leaked satisfied that assertion too.

## D-030 Evidence must come **after** the change it claims to verify
- **Date**: 2026-09-01 · **Status**: confirmed (subsystem audit)
- **Background**: `verify_claims` only asked "is this command's exit code right", never "did it run after the change being verified". So: the model runs the tests green -> edits the code -> does not run them again -> finish cites the green run from **before** the edit. The exit code matches perfectly, and so a session that **verified nothing** reported `completed`.
- **Decision**: the runtime records the journal ordinal of the last change that successfully modified the workspace, and the gate refuses any claim numbered earlier than it. A change means a mutator tool (`apply_patch` and the like); `run_command` does not count -- the command is the source of the evidence itself.
- **Note**: this is a hole **in the project's core promise** that survived six rounds of adversarial review. Those rounds all attacked the segmenter and patching; the "ordering" dimension of the evidence chain had never been examined. There is now an end-to-end regression.

## D-029 A single BLOCKED does not end the REPL session
- **Date**: 2026-09-01 · **Status**: confirmed
- **Decision**: a dropped stream or an unreachable gateway ends **this round**, not the session. Previously any `outcome.status is not None` broke out, so one bit of network flakiness cost the user the whole conversation context -- while the comment on the code that raised it said "transient, so it will retry", and in fact no layer retries (the deltas are already on screen, and the round cannot be replayed). The comment now tells the truth, and BLOCKED prints a message and continues.

## D-031 Observation masking starts under context pressure, not after a fixed number of rounds
- **Date**: 2026-10-11 · **Status**: confirmed (found by running Foundry on its own repository)
- **Background**: every tool output older than the last 5 rounds was masked, whatever the context held. Given a real task in this repository (make `tool_end` carry its duration and exit code), Foundry read `runtime.py`, `command.py` and `tests/test_runtime.py`, had them masked five rounds later, and read them again -- about thirty re-reads in forty rounds. It hit the round budget with the source half-changed and no test written, while the context never passed 21k tokens of a 128k window. Masking saved nothing there and cost a round per re-read; it also rewrote the prefix every round, which defeats a provider's prompt cache.
- **Decision**: the projection is the full transcript until it would pass half the backend's window (`mask_above_fraction`). Past that, tool outputs are masked oldest first and only until it fits again; the last `mask_after_turns` rounds are never masked. Masking itself is unchanged, and so is the evidence for it in [design.md](design.md); what changed is when it applies.
- **Note**: none of the 1400-odd tests could see this. They script the model, and a scripted model never needs to look at something twice.

## D-032 A native Anthropic Messages adapter, on the wire protocol, replaying response content verbatim
- **Date**: 2026-10-13 · **Status**: confirmed (live; see docs/research/anthropic-messages.md)
- **Background**: Foundry reached Claude through Anthropic's OpenAI-compatible endpoint, which has no prompt caching. Building `examples/earnings_pm` it sent 1.69M input tokens with nothing read from cache, while the earnings agent itself, on the native API, read 398k of its 443k input tokens from cache.
- **Decision**: a fourth adapter, `anthropic_messages`, written against the Messages wire protocol over `httpc` rather than the `anthropic` SDK: `foundry.core` imports no third-party package, and the SDK's HTTP stack would break the offline dependency budget. Each response's content is replayed **verbatim** through a new opaque IR block (an additive IR change): thinking signatures bind the conversation prefix, and the API adds fields -- `tool_use.caller` appeared in the first capture -- that an adapter rebuilding blocks field by field would drop. Every request sets top-level `cache_control`; the system prompt, tools and history are byte-stable round to round, so each round reads the last from cache.
- **Masking and thinking**: observation masking (D-031) rewrites old tool results under context pressure, which invalidates every later thinking block, and on an account created on or after 2026-08-31 replaying one is a 400. Requests therefore set `thinking.block_binding.prefix_mismatch_behavior = "drop_block"`: the API drops the invalidated blocks and reports each in `input_transformations`, which the runtime shows as a warning. Degrading beats failing a session at the moment its context is fullest.
- **Fallbacks on by default**: `fallbacks = "default"` re-runs a safety-classifier decline on Anthropic's recommended model inside the same call. Foundry's own repository is full of breaker tables and bypass tests, exactly the content a cyber classifier can misread. After a mid-output fallback only the declined attempt's text is kept; its thinking and tool calls are neither replayed nor run. `fallbacks = "off"` disables it.
- **Credentials**: the protocol has its own variable (`ANTHROPIC_API_KEY`) and vault field, and its own default base URL, decided from config provenance: an OpenAI key never reaches Anthropic, and an Anthropic key never reaches the OpenAI default host.

## D-033 Foundry runs from its source tree; the wheel stays the distribution
- **Date**: 2026-10-31 · **Status**: confirmed (the user chose to keep the src layout and add a launcher)
- **Background**: a clone needed `pip install` for three reasons only: the src layout (nothing put `src/` on `sys.path`), the `foundry` command (an exe pip generates) and the tests (no path setting). Nothing in the package depends on being installed: the version is a literal, the system prompt loads through `importlib.resources` from the source tree, and no code reads install metadata. An editable install, meanwhile, writes a `.pth` that points at one checkout: on the development machine it pointed at the `blueprint` worktree, so `python -m pytest` in every other worktree tested that worktree's code, silently.
- **Decision**: pytest gets `pythonpath = ["src"]` (and ResearchOS's gets `../tools`); `run-foundry.py` at the root (stdlib only) puts `src/` first on `sys.path` and calls `foundry.__main__.main`; `foundry.cmd` wraps it, so a clone on `PATH` gives a `foundry` command in any repository; `foundry doctor` prints the directory the code was imported from. A CI job runs every suite and the CLI with only the dependencies installed. The launcher is not named `foundry.py`: at the root it would shadow the wheel when the offline-install job runs `python -m foundry` there.
- **Unchanged**: [D-002]. The corporate machine still gets a wheel from an internal directory, installed with `--no-index`, and the offline-install job still proves that path. The src layout stays: flattening it would move the source under every repository-relative link and leave `test_architecture_config.py` scanning an empty directory, where `rglob` finds nothing and the test passes.
- **Note**: D-002 and requirements §7 say the wheelhouse is hash-pinned and installed with `--require-hashes`, but there is no lock file, `build_wheelhouse.py` downloads from the unpinned `requirements.in`, and CI installs without `--require-hashes` -> [OQ-20](open-questions.md).

## D-034 Each branch records its delta from main in DELTA.md
- **Date**: 2026-10-31 · **Status**: confirmed (the user asked for an in-repo record of every branch's changes from main, emptied on main)
- **Background**: branches land on main by fast-forward, one per piece of work, mostly from worktrees under `.claude/worktrees/`. Nothing recorded, while a branch was open, what it changed and why; that lived in chat transcripts, and was lost when they were.
- **Decision**: `DELTA.md` at the root is tracked. On main it is an empty template; on a branch it holds hand-written notes (Summary, Changes, Decisions and open points, Verification) above a generated list of the files that differ from main. `scripts/delta.py` (stdlib only) does `refresh`, `check` and `reset`. The Claude Code hooks refresh it when a session starts and, when a turn ends, send the agent back once if the notes are missing or behind later commits. CI fails main unless the file is the template, and a branch with commits unless the Summary is written. Landing is `reset --commit` and then the fast-forward: that last commit restores the template and carries the notes in its message, so main's history keeps them.
- **Rejected**: an untracked file (it would not travel with the branch to CI or to a reviewer); a file per branch under `docs/` (main would accumulate them); regenerating the notes from commit messages (the point is the why, which the file list cannot give).

## D-035 A recorded session can be resumed from its journal
- **Date**: 2026-11-03 · **Status**: confirmed (the user chose session resume as the next Foundry feature)
- **Background**: [D-012] made the journal complete enough to rebuild every request and deferred the feature. A session ended by Ctrl+C, a budget, `finish` or a dropped connection could only be started again from nothing, losing its context and the files it had read.
- **Decision**: `foundry resume [session] [task]` and `foundry exec --resume <session> [task]` continue a session in its own journal (`last`, the newest session of the workspace, by default). The conversation is rebuilt from the journal alone. Every message is taken from the first `model_request` that carries it: history only grows, masking rewrites content but never drops a message, and the newest rounds are never masked. What follows the last request comes from three additive records -- `user_input`, `tool_reply`, and `model_response.opaque` -- and `model_request.turn` gives the rounds, so a resumed session masks exactly what the original would. A tool call with no recorded result is given one that says what is known: a finish that was accepted, with the status it produced; a call never run, with the reason the session stopped; a call interrupted while it ran, outcome unknown. A `resumed` record starts the new run, ordinals continue, and the session's artifacts resolve again.
- **What a resume may not weaken**: HEAD must be the commit the session started on, or the resume is refused -- its evidence and its account of what it changed are relative to that commit. Evidence starts over: commands from before the resume cannot back a finish claim, every file is read again before it is patched, and approvals given for the session are not carried over. Files that changed since the session started, other than those it patched itself, join the dirty-file guard and are named to the model. The restored text is the journal's redacted copy. One writer per session: each store holds an operating-system lock on `sessions/<id>/lock`, which a crashed process releases. Also refused: a journal from a newer schema or IR, another workspace, a journal whose requests do not continue one another, a context that is already full. A refused resume writes nothing.
- **Termination**: a journal may hold several terminations -- one per run, plus one for each blocked turn an interactive session went on past (that session now also records how it finally ended; it used to stop at the blocked one). Its status is the last one's, unless a `resumed` record follows it: a resumed run that has not ended reads as `interrupted`, never as the previous run's outcome. Every record is now flushed when written (the evidence types are also synced), so a killed process loses nothing it had recorded.
- **Rejected**: carrying the command evidence and the list of files read across a resume (sound only when the workspace is provably unchanged, which needs a fingerprint of it at every termination); a `message` record for every history append (the requests already hold every message, and with the request fold older journals resume by the same path, their missing results answered as above).
- **Deferred**: that fingerprint and the evidence it would let a resume keep; continuing after HEAD moved (re-baselining); resume counts in `foundry report`.

## D-036 A session's patches can be undone
- **Date**: 2026-11-04 · **Status**: confirmed (the next Foundry feature after resume, from the V2 candidates)
- **Background**: nothing but git could take back what a session changed, and git cannot tell the session's edits from the user's: checking out a file the user had edited before the session discards that work too, and a file the session created has to be found and deleted by hand. The roadmap listed "shadow-git checkpoint/undo".
- **Decision**: `apply_patch` records, for each file it changes, an exact copy of what the file held before (an artifact) and a digest of what it wrote, in its `tool_result` record (`changes`; the model never sees them). `foundry undo [session] [--last] [--yes] [--dry-run]`, and `/undo` in a session for its newest patch, put the earlier content back, newest change first, and write an `undo` record, so nothing is undone twice. A file is put back only while it holds exactly what the session wrote: an edit made since, by the user or by a command, leaves it alone, along with everything the session did to it before, and undo names it. A change between two of the session's patches stops undo there, so the file returns to what that change left. A move is reverted whole or not at all. Each file is checked again just before it is written, the write goes through the workspace's containment rules, and the kept copy must match its digest.
- **What it may not weaken**: content holding a credential Foundry knows is never kept -- artifacts are redacted, and a redacted copy written back would corrupt the file -- so such a file cannot be undone, and undo says why. After `/undo` the model is told which files changed back, it reads each one again before patching it, and commands run before the undo can no longer back a finish claim; a session resumed after `foundry undo` is told the same. `foundry undo` takes the session's lock, so a session another process has open is refused (`/undo` works there); a refused or declined undo writes nothing.
- **Rejected**: a shadow git repository (another `.git` for the tools to be kept out of, and its snapshots hold the user's changes too, so restoring one discards them); `git stash` or `checkout` (the same problem, and the stash is shared by every worktree); undoing commands (nothing records which files a command touched, so the files changed since the session started that no patch touched are listed as not undone instead).
- **Deferred**: redo; undoing back to a chosen patch rather than the newest one or all of them; removing directories a patch created.

## D-037 The model keeps a plan the user can see (`update_plan`)
- **Date**: 2026-11-04 · **Status**: confirmed (the user picked it as the next Foundry feature, from the V2 candidates)
- **Background**: [requirements.md](requirements.md) §5.2 froze V1 at nine tools and named a visible plan as the first V2 candidate; codex ships `update_plan` and Claude Code a todo list for the same reason. On a long task the user saw a stream of tool calls and no account of where the work was going or how far it had got, and plan mode asked the model to "produce the plan" with nowhere to put one but prose.
- **Decision**: a tenth tool, `update_plan {explanation?, plan: [{step, status}]}`, read-only and allowed by a built-in rule in every mode, plan mode included. Each call replaces the whole plan: at most 20 steps of at most 200 characters, each `pending`, `in_progress` or `completed`, at most one `in_progress`; an empty plan clears it. The plan belongs to the session, as the model's history does -- the model still sees every call it made, since masking never touches a call's arguments. The runtime keeps it; a `plan_updated` event carries it to the CLI, which draws it as a checklist in place of the tool's begin and end lines, and to `exec --json`; `/plan` in a session shows it again; the call's `tool_result` record keeps it (`plan`), so a resumed session restores it and shows it. The model's reply gives only the counts. The system prompt says when to use it (several steps; tick a step in the same turn as the work, not in a round of its own), and plan mode's paragraph now points at it.
- **What it may not weaken**: the plan is the model's own account, so it is never evidence, in either direction. `finish` adds the steps not marked completed to its summary, and warns when such a finish is `completed`, but changes no status over them: a step the model forgot to tick is not a failed task, and ticking every step proves nothing was done. Its text is model output shown to a person, so each step is reduced to one line of plain text when the call is validated (line breaks, control and format characters such as escape sequences and bidi overrides removed) and escaped when drawn, and the event sink now scrubs strings nested inside an event, not only its top-level fields -- a credential in a step used to reach every subscriber while the journal's copy was scrubbed.
- **Rejected**: downgrading `completed` while steps are open (it would turn a bookkeeping slip into a failed task, and a model could clear its plan first); per-step ids and partial updates (a whole plan per call is what codex does, and there is nothing to keep in step); a plan per task that resets with each new task (a resumed or continued task would lose the plan its history still shows).
- **Deferred**: approving a plan in plan mode from the session (switching the mode mid-session changes the system prompt the permissions paragraph is part of; landed as D-038); plan counts in `foundry report`.

## D-038 A plan is approved with `/approve`, which ends plan mode
- **Date**: 2026-11-06 · **Status**: confirmed (the user asked for it as the next Foundry feature, the follow-up D-037 deferred)
- **Background**: plan mode refused every edit and command "until the user approves your plan", and nothing could approve one: the user had to end the session and start another in a different mode, losing the context the plan was built in.
- **Decision**: `/approve`, typed in an interactive session in plan mode, shows the plan (or says the model set none) and asks one question: `(y)es`, ask before each edit -- `default` mode; `(e)dits` apply without asking -- `accept_edits`; anything else, or no answer, keeps planning and changes nothing. On approval the policy's mode changes, the system prompt's permissions paragraph is built again from it (`prompts.system_prompt`), a `mode_change` record `{from, to, by, reason}` is written and synced, and the next turn starts at once with a note that says plan mode is over, what the new mode allows (the paragraph's own line, `prompts.mode_line`), and to carry the plan out. Every `policy_decision` now records the `mode` it was made in, since the rules' digest does not cover it.
- **What it may not weaken**: only the user can approve -- the command is read from the user's own prompt, and nothing the model writes or a tool prints reaches the REPL's commands; the model is told how the user approves, not given a way to. The model is never told rules that no longer hold. Approval moves only to the two interactive modes, never `dont_ask`, and the dirty-file guard, the breaker, and every DENY rule apply exactly as before. A resume starts in the configured mode, as it starts every grant over ([D-035]): an approval is the user's decision about that run, and the resumed model is told the switch did not carry over.
- **Rejected**: approving by a tool the model calls (the model would grant itself the permissions plan mode withholds); keeping the old system prompt and telling the model only in the note (the system prompt would contradict it, on the paragraph whose whole purpose is to be true); `/approve` only arming the mode for the user's next message (approving the plan is the instruction to carry it out, and Claude Code continues the same way).
- **Deferred**: consulting where plan mode came from -- a managed `mode` is not a floor today (a user config overrides it), so there is nothing for `/approve` to defer to; if managed policy ever pins the mode, `/approve` must refuse it.

## D-039 Slash commands, custom prompts, and a read-only review
- **Date**: 2026-11-06 · **Status**: confirmed (the first step of the user's goal to make Foundry work "basically like codex"; the V2 candidate "skills and slash commands")
- **Background**: the interactive prompt knew five words (`/exit`, `/quit`, `/undo`, `/plan`, `/approve`), each an `if` in one loop, and sent anything else -- a mistyped `/udno` included -- to the model as a task. codex's prompt has a command set users rely on (`/status`, `/diff`, `/init`, `/review`, `/new`, custom prompts), and nothing in Foundry could show what the session had changed or how full its context was without leaving it.
- **Decision**: the REPL moves to `cli/repl.py` with a command table. A line is a command only when it starts with `/name` followed by whitespace or the end (`/usr/bin/python fails` is a task); an unknown name is reported, not sent. Built-ins: `/help`; `/status` (session, model, mode, tokens, context fill, plan, changed files); `/diff` (every uncommitted change, each marked as this session's or from before it, the tracked diff with control sequences stripped, new files with their size); `/plan`; `/approve`; `/undo`; `/review [focus]`; `/init` (asks the model to write FOUNDRY.md, refused if FOUNDRY.md or AGENTS.md exists); `/new` (closes this session's journal and starts a fresh session in the same workspace); `/exit`, `/quit`. A command that takes no arguments refuses them. Custom prompts are Markdown files named after their command, with optional `description` / `argument-hint` front matter and `$ARGUMENTS`, `$1`..`$9` (quotes respected) and `$$`; arguments are appended when the text has no placeholder. They come from `~/.foundry/prompts/` and, only in a trusted workspace, from `.foundry/prompts/` -- built-ins win over both, the user's over the repository's -- and a repository that has that folder now gets the trust question.
- **`/review` changes nothing**: it is not left to the prompt. While the review turn runs, the policy's `read_only` reason refuses every mutator, in every mode -- `accept_edits` included -- and is cleared afterwards even when the turn fails. Building it showed that **plan mode was weaker than documented**: its refusal sat at step 4, after the ASK rules, so in plan mode a patch to a file with uncommitted changes, or a command that could not be parsed, was put to the user -- who could approve it -- instead of refused. Plan mode and read-only tasks now refuse at step 2, with the DENY rules, before any ASK.
- **What it may not weaken**: commands come only from the user's typed line; the model, tool output and repository text never reach the table, and the model cannot add a prompt (writing under `.foundry/` is refused by the breaker). A repository's prompt is text the user sends as their own instruction, so it is read only where the user trusts the repository, is marked as the repository's when used, and is capped at 24 KB like FOUNDRY.md. `/new` starts every grant and all evidence over, as a new session does.
- **Rejected**: sending unknown commands to the model (a typo would start a paid turn); `/review` as a prompt alone (an `accept_edits` session would apply whatever "fix" the model decided on); custom prompts that run code or set the mode (a prompt is text; anything that changes permissions stays a built-in).
- **Deferred**: `/compact` (with summarised compaction, next); `/model` and `/mode` mid-session; prompt arguments by name (`$KEY=value`).

## D-040 Compaction by summary, before the context runs out
- **Date**: 2026-11-06 · **Status**: confirmed (the second step of the codex-parity order; the V2 candidate "LLM summarisation compaction", for which the `Compacted` record was reserved)
- **Background**: masking (D-031) stubs old tool output but never the last five rounds, so a task whose recent rounds alone filled the window -- a few large reads -- still ended `partial(context window exhausted)`, and a long interactive session could only be thrown away. The masking evidence (arXiv 2508.21433) stands, and masking stays first; it just cannot be the last step.
- **Decision**: at the top of each round, once the projection, after masking, is past 80% of the window and the history holds model output, the runtime asks the model for a handoff summary (`prompts/compact.md`: the task, what is done, the checks run, the current state, next steps, decisions and dead ends). The request is the conversation as projected plus that instruction, with the same tools (a history with tool calls is refused without them); a tool call in the reply is ignored and its text is the summary. The history becomes the user's own messages -- newest first within a tenth of the window, the first that does not fit cut down, then put back in order, earlier summaries left out -- followed by the summary, capped at 15% of the window, with the current plan appended, all stamped with the current round. `/compact [focus]` does the same on request. `runtime.auto_compact = false` turns the automatic one off. The journal records the summary request and response with `purpose: "compact"`, its token usage, and a `compacted` record (synced) holding the new history, its reason (`auto` or `user`), and the estimated tokens before and after; the report counts compactions and leaves them out of rounds.
- **What it may not weaken**: the summary is model output and is scrubbed by the redactor before it enters the history, as tool output is. Every file read before the compaction must be read again before it is patched -- its contents are no longer in context -- and the summary says so. Command evidence is untouched: a claim can still cite a command run before the compaction, and staleness after a change still applies. A failure (no reply, an error, an empty summary) leaves the conversation exactly as it was, says so, and stops automatic compaction for the rest of the task, so a broken gateway is not paid for every round; masking and the clean termination still apply. A Ctrl+C during the summary cancels the task. Resume follows a compaction: the fold skips the summary request and response and resets the history at the `compacted` record, so the rebuilt conversation is byte for byte the live one, and a crash between the summary and its record resumes from before it.
- **Rejected**: compacting at a fixed number of rounds (it would summarise while masking alone was enough, and every summary loses detail); summarising only the tool output (the reasoning between calls is what a handoff needs); keeping the last few rounds verbatim next to the summary (they are what filled the window); a separate, cheaper model for the summary (a second backend to configure and trust).
- **Deferred**: compacting in the middle of a round's tool calls; showing the summary to the user (it is in the journal); a configurable threshold.

## D-041 Instructions in layers: the user's own, then the repository's from its top down
- **Date**: 2026-11-06 · **Status**: confirmed (the third step of the codex-parity order; extends D-019)
- **Background**: only a `FOUNDRY.md` (or `AGENTS.md`) at the workspace root was read. Started in a package of a larger repository, Foundry missed the repository's own notes; and a user had nowhere to keep instructions for every session ("answer in English", "prefer small commits") except by repeating them. codex reads a global `AGENTS.md` and then every `AGENTS.md` from the repository's root down to the working directory.
- **Decision**: the system prompt's instructions are the user's own `FOUNDRY.md` or `AGENTS.md` from the Foundry folder (the one holding `config.toml`), then the repository's, one per directory (`FOUNDRY.md` over `AGENTS.md`), from the repository's top -- the nearest directory at or above the workspace holding `.git`, a worktree's own included -- down to the workspace, top first, with a sentence saying the later, more specific one wins. Outside a repository only the workspace itself is read, so a loose folder never picks up notes from wherever it sits; directories below the workspace are not read. One file reads exactly as before. The repository's files share the 24 KB budget, top first: a file past it is named and left out. `/status` names the files the session loaded.
- **What it may not weaken**: the repository's files, the ones above the workspace included, are read only where the user trusts the workspace, and any of them now raises the trust question. The user's own file needs no trust -- it is theirs, like `config.toml` -- and is capped like the rest. Nothing here changes what the instructions are: guidance, never authority to bypass approvals.
- **Rejected**: reading files below the working directory as the model enters them (instructions that change mid-task with what the model happens to open; a later step if it is wanted); reading up past the repository's top (a home directory's notes are not the project's); a separate budget per file (a deep tree could fill the window with instructions).
- **Deferred**: `FOUNDRY.override.md`-style per-user overrides inside a repository; a setting to change the file names.

## D-042 Settings on the command line: -m, --mode, -c, --profile, exec -o
- **Date**: 2026-11-06 · **Status**: confirmed (the fourth step of the codex-parity order)
- **Background**: requirements section 4.3 put CLI flags at the top of configuration and named a profile layer, but there were no such flags -- trying another model meant editing `config.toml` -- and no profiles. `foundry exec` always ran in `dont_ask`, so an unattended run could edit nothing without ALLOW rules, and a script had no clean way to read what the run concluded.
- **Decision**: `run`, `resume`, `exec` and `record` take `-m/--model`, `--mode`, `-c/--config key=value` (repeatable) and `--profile`; `foundry -m x ...` with a flag first means `run`. A `-c` key is `backend.<key>`, `runtime.<key>` or a bare key from either table; its value is read as TOML and as plain text when it is not one, so `-c model=gpt-5` needs no quotes; an unknown key is an error, not a setting nobody reads. Profiles are `[profiles.<name>]` tables in the user's own `config.toml`, holding `backend`, `runtime` and `permissions` like the file itself, chosen by `--profile`, `FOUNDRY_PROFILE` or a top-level `profile = "..."`, in that order, and applied between the user's settings and the repository's, as section 4.3 always said; the profile's name is recorded in the session header. `exec --mode` takes `dont_ask` (the default whatever the files say), `plan` or `accept_edits`: an unattended run that may apply patches inside the workspace but still runs no command a rule does not allow, which is the closest Foundry comes to codex's `--full-auto`. In those modes the permissions paragraph adds that nobody can approve and that the run ends with `finish`. `exec -o/--output-last-message FILE` writes the run's last word -- the finish summary, or the final reply, or why it stopped -- scrubbed like the journal.
- **What it may not weaken**: secrets stay out of command lines, which other processes can read: `-c` refuses `api_key` and `headers`. Profiles come only from the user's own file; a repository's `profiles` table is never read, so it cannot redirect the endpoint by name. The repository layer still comes after a profile and can still only tighten. `exec` never takes its mode from configuration, only from `--mode`, and `default` is not offered there (nobody can answer its questions). `/new` builds the next session with the same flags.
- **Rejected**: a bare word as an implicit task (`foundry fix it`): a mistyped subcommand would start a paid run; `-c` for permission rules (rules belong in a file the user can read back); `exec --mode` choices that ask (they would all be refusals).
- **Deferred**: `--add-dir` (Foundry has one workspace root); `-c` lists for permission rules; a `/model` command mid-session.

## D-043 An MCP client over stdio, under the same policy
- **Date**: 2026-11-06 · **Status**: confirmed (the fifth step of the codex-parity order; V1 only aligned the IR with MCP's shapes)
- **Background**: codex, Claude Code and most other agents take tools from MCP servers -- a team's docs search, an issue tracker, a database -- and Foundry could only offer its own ten. The IR's content blocks were shaped after MCP from the start, so the work was the client and the policy, not the conversation.
- **Decision**: `[mcp_servers.<name>]` tables (`command`, `args`, `env`, `env_vars`, `startup_timeout_s`, `tool_timeout_s`, `read_only`, `enabled`) in the user's own `config.toml` or a profile. At session start every enabled server is started at once, over stdio: JSON-RPC 2.0, one message per line, protocol `2025-06-18`, `initialize` then `notifications/initialized`, then `tools/list` (paged, at most 100 tools a server) if the server has the tools capability. Each tool is offered as `mcp__<server>__<tool>` (letters, digits, `_` and `-`, at most 64 characters, a digest keeping long names apart), with the server's description and argument schema (an object schema, at most 16 KB; an empty object when it gives none); a name already taken is not offered. A call checks the required arguments, sends `tools/call`, and renders the result's text -- naming the content it cannot show (images, audio, binary resources) rather than dropping it -- truncated like a command's output with the full text kept as an artifact; `isError` makes it an error for the model. The server's own requests get an answer -- `ping`, and "not offered" to everything else (no sampling, roots or elicitation) -- and its notifications and any stray log lines on stdout are ignored. Rules may name tools by pattern (`mcp__docs__*`), matched case-sensitively; their arguments, as canonical JSON, are what a rule's pattern matches. `/status` lists the servers; each one's tools, or why it is not available, are journaled as a `capability_probe` record and shown at start.
- **What it may not weaken**: a server is a program, so only the user's own files can name one; a repository's config that tries is refused outright. Every MCP tool is a mutator to the policy: refused in plan mode and during `/review`, asked about otherwise, denied in `dont_ask` and headless runs, unless a rule allows it -- a server's own "read-only" hints are not trusted, since a read-only fetch is exactly how data leaves. Only `read_only = true` in the user's entry makes its tools read-only, which offers them in plan mode and `/review`, still asking first. The server gets the environment a command gets, with credential-shaped variables removed; a secret reaches it only by name through `env_vars`. It runs under a job object, and the session's end closes its input, then ends it and everything it started. A server that fails to start, hangs, or dies costs a warning or an error result, never the session; a call that hangs times out, and Ctrl+C reaches it. Its output is untrusted content, scrubbed before the model sees it like any tool's.
- **Rejected**: trusting `readOnlyHint` (see above); the HTTP transports (a server reachable over the network is a connection setting with its own trust questions -- later, if wanted); starting servers on first use (a slow server would stall the first turn that needs it, and its tools must be in the first request anyway); letting servers sample the model (a server could then spend the user's tokens on prompts of its own).
- **Deferred**: streamable HTTP servers; resources and prompts (`resources/list`, `prompts/list`); `notifications/tools/list_changed`; showing images once `view_image` lands.

## D-044 The model's reasoning, shown where the provider gives it
- **Date**: 2026-11-06 · **Status**: confirmed (the sixth step of the codex-parity order)
- **Background**: codex shows the model's reasoning summaries as it works; Foundry showed nothing between a task and the first tool call, which on a reasoning model can be a minute of silence. Each provider exposes reasoning differently, and the current Claude models return an empty thinking block unless a summary is asked for.
- **Decision**: a new stream event, `ReasoningComplete(text)`, which every adapter yields once a stretch of reasoning is complete and before the answer it led to. `anthropic_messages` asks for `thinking.display = "summarized"` (it costs nothing extra; the default leaves the text empty) and yields each thinking block's text when the block ends; the block itself is still replayed unchanged. `responses` yields a reasoning item's summary -- or, from an open-weights model, its `reasoning_text` -- when the item is done, and asks for `reasoning.summary` only when `backend.reasoning_summary` says so (`auto`, `concise` or `detailed`), since a model that does not reason refuses the field. `openai_compat` collects `reasoning_content` or `reasoning` (DeepSeek, vLLM, OpenRouter) and yields it when the answer starts, or at the end. `reasoning_summary = "none"` asks no provider for anything. The runtime turns each into a `Reasoning` event, unless `runtime.show_reasoning = false` or the request is a compaction's, and journals the text as `reasoning` on the `model_response` either way. The terminal shows it dim under "thinking", cut to eight lines unless verbose; `exec --json` carries it as `{"kind": "reasoning"}`.
- **What it may not weaken**: reasoning is never part of the conversation -- it is not sent back (DeepSeek refuses a request that replays it), and a resume does not rebuild it. It arrives whole, so the redactor sees it as one string on the screen, in `--json` and in the journal; it is model text, escaped and stripped of control sequences like any other.
- **Rejected**: streaming reasoning delta by delta (it would need the text stream's hold-back scrubbing a second time, for text that is usually a few sentences; a summary shown whole once ready is what codex shows too); asking Responses for a summary by default (a 400 on every model that does not reason); putting the reasoning on `ModelTurn` (it would arrive after the answer it explains).
- **Deferred**: Anthropic's `display = "updates"` progress notes (a beta); a `/reasoning` toggle in the REPL; reasoning shown live while it streams.
- **Fixed on the way**: a Responses gateway that sends only the terminal event had its answer recorded but never shown, because the screen draws text deltas and none was yielded; the terminal output's text is now yielded as one.

## D-045 Images: view_image, attachments, and an MCP tool's images
- **Date**: 2026-11-07 · **Status**: confirmed (the seventh step of the codex-parity order; the IR reserved an image block from M0)
- **Background**: codex can be shown a screenshot (`-i`, a pasted image) and has a `view_image` tool; a failing UI test, a design mock or a plot is something a coding agent is often asked about. Foundry could not carry an image at all, and an MCP server's images were named and dropped.
- **Decision**: an `ImageBlock(media_type, data, name)` in the IR -- base64 of the file's bytes -- on a user's message, and an `images` tuple on `ToolResultBlock` for a tool's. `core/images.py` checks an image before it is sent, from the file's own first bytes, never its name: PNG, JPEG, GIF or WebP, at most 3.75 MB (Anthropic's 5 MB of base64), no side over 8000 pixels; nothing is resized (standard library only). `view_image(path)` is a read-only tool, workspace-bound like `read_file` and allowed like it; `-i/--image PATH` (repeatable) on `run`, `resume` and `exec` attaches images to the first task, and `/image PATH` to the next message in a session, at most eight to a message. An MCP tool's image content that passes the checks rides on its result. Anthropic gets the images inside the user message and inside the `tool_result`; Chat Completions and Responses take text only in a tool's output, so a run of results that carried images is followed by one user message holding them, named by call -- the portable form, and codex's. The context counts an image as 1,600 tokens, not as its base64; masking an old result drops its images, and a compaction keeps the user's words but not their images. The journal keeps each image once, as an artifact under its digest, and every record refers to it by id (`{"kind": "image", "media_type", "name", "artifact"}`); a resume reads the bytes back from the session's artifacts, and one that is missing becomes a note saying it was not kept. `backend.images = false` turns all of it off for a text-only model: no `view_image`, `-i` and `/image` refused, an MCP tool's images named as before.
- **What it may not weaken**: an image is content, not instruction -- a screenshot of text that tells the model what to do is as untrusted as a file that does. It cannot be scrubbed: an image whose bytes hold a credential Foundry knows, or a run of bytes shaped like one, is still shown to the model (it is what the user or the workspace provided) but is not kept in the artifacts, so a session never stores a known secret. `view_image` cannot reach outside the workspace; `-i` and `/image` take the user's own paths, typed in the terminal.
- **Rejected**: resizing (it would need an imaging library in core); the image inline in every journal record (each request repeats the history, so a screenshot would be written once a round); the image as a separate block beside the tool result (masking and the Anthropic shape both want it on the result); `function_call_output` with image parts on Responses (newer, and unconfirmed on the corporate gateway); probing whether a model takes images (no provider offers a cheap probe; a text-only model refuses the request, and the setting says so).
- **Deferred**: pasting an image into the terminal; a PDF or other document; resizing an image that is too large.

## D-046 A Python repo map: the repo_map tool, from the standard library's ast
- **Date**: 2026-11-07 · **Status**: confirmed (the eighth step of the codex-parity order)
- **Background**: a model new to a repository spends its first rounds on `list_files` and on reading files to learn what is defined where. Aider's answer is a repo map -- the definitions and signatures of every file, ranked by how much the rest of the code refers to them, cut to a token budget -- built with tree-sitter and PageRank. Core takes no third-party package, so the stdlib cut is Python only, parsed with `ast`.
- **Decision**: a read-only tool, `repo_map(path=".")`. For one `.py` (or `.pyi`) file it returns the file's whole outline: each class with its bases and decorators, its annotated fields on one line, its methods; each function's signature with its return annotation; the module's constants and type aliases (upper-case names, a run of them on one line); the first paragraph of the module docstring. Each row carries the line where the definition starts (its first decorator), for `read_file`'s `start_line`. Definitions under an `if`, `try` or `with` (`if TYPE_CHECKING:`) count as the module's. For a directory the outline is brief -- no names with a leading underscore (`__init__` stays), no decorator arguments -- and the files are ranked by how many other files import them (absolute imports matched against every suffix of each file's dotted path, relative ones resolved against the file's directory, a name two files answer to credited to neither), tests last. A budget of 12,000 characters (about 3,000 tokens) is filled in three tiers, in rank order and greedily: a file's outline while it fits, with a third of the budget held back; then a line of its public names; then its path, in a closing note. The blocks print in path order. Pruned like `list_files` (build outputs, `node_modules`, reparse points), and of hidden directories, `site-packages` and `*.egg-info` too. At most 2,000 files and 10 seconds a call, files over 1 MB not read; whatever is left out is named. Outlines are cached in the tool by path, modification time and size, so a second map parses only what changed.
- **What it may not weaken**: `ast.parse` reads the source and runs nothing in it; a file that will not parse, or nests too deeply, is named with the reason, never a traceback, and its `SyntaxWarning`s are not printed over the terminal. The path resolves inside the workspace and the walk never follows a junction. The outline is tool output like any other: content, not instruction, and a known secret in a default value is scrubbed before the model sees it. Allowed in every mode, plan mode included, as the other read-only tools are.
- **Rejected**: a map in every request, as aider sends it (it costs its tokens on every round whether or not it is needed, would change the system prompt as files change, and a resume's request would no longer match the original's); ranking by references to each symbol rather than by imports (aider's PageRank; the import graph is the cheap half of the same signal, and the report can show whether more is needed); other languages by regular expressions (wrong often enough to mislead); a model-chosen budget (a narrower path is the way to more detail).
- **Deferred**: other languages (they need tree-sitter); ranking by symbol references; preferring the files the conversation has touched.

## D-047 /mode and /model: the mode and the model chosen again mid-session
- **Date**: 2026-11-07 · **Status**: confirmed (item 9 of the codex-parity order)
- **Background**: codex lets its user change the approval mode (`/approvals`) and the model (`/model`) without leaving the session. Foundry fixed both at the start: `--mode` and `-m` were the only way, so changing either meant `/new` and losing the conversation, and `/approve` (D-038) was the one move out of plan mode.
- **Decision**: `/mode [NAME]` shows the mode and what each allows, or switches to `default`, `accept_edits`, `plan` or `dont_ask` (either spelling, any case). As `/approve` does, it builds the permissions paragraph again, writes `mode_change` (`by: "repl"`), and tells the model with the next message, the mode's own line included; entering plan mode says that `/approve` ends it. `/model [NAME]` shows the model, or switches to another behind the same endpoint and credential -- a name of letters, digits and `. _ : / @ + -`, at most 200 characters, starting with a letter or digit; another endpoint is another session (`--profile`). The next request goes to the new model with the conversation as it stands; `model_change` is written (and synced, like `mode_change`), `/status` shows it, and a line with the next message says so. Several changes before one message are all told, in order. `/new` starts the next session with the model and mode chosen this way, as if they had been given on the command line. A resume does not carry them over: it starts with the configured model and mode, and says what it had been switched to.
- **What it may not weaken**: both are commands, read from what the user types and nowhere else, so the model cannot change its own mode or model; no mode exists beyond the four the policy already has, and a repository config still cannot pick a looser one. Every `policy_decision` keeps recording the mode it was made in.
- **The system prompt and preserved thinking**: `/model` leaves the system prompt alone (its environment paragraph still names the model the session started on; the line with the next message corrects it), because Anthropic's newer models bind each thinking block to the conversation before it, system prompt included, and a block replayed after that prefix changed is dropped -- Foundry's requests set `drop_block` (D-032) -- and its reasoning lost. A model switch alone is not such an edit: a block the new model cannot read is dropped too, but that is the routing, not the history. `/mode` rebuilds the permissions paragraph as `/approve` already did; what that, masking and a resume cost in thinking is D-048. (Corrected by D-048: this entry first said such a request is refused with a 400, which is what an enforced account does without `drop_block`.)
- **Rejected**: a model picker that lists what the endpoint serves (no listing call is common to the three protocols, and a gateway may not offer one); switching the endpoint or protocol in the session (a different credential and different adapters: a new session); carrying a switch over a resume (the configured mode and model are what the user asked for this time; the notice names the difference).
- **Deferred**: an `/approvals` alias; the context window of the new model (the backend's, as configured, is kept).

## D-048 Thinking made against an old prefix is left out of later requests
- **Date**: 2026-11-07 · **Status**: confirmed (item 10 of the codex-parity order; found while doing D-047)
- **Background**: Anthropic binds each thinking block to everything sent before it -- system prompt, tools and earlier messages. Foundry changes that prefix itself: masking an old tool result (D-031), rebuilding the permissions paragraph on `/approve` or `/mode` (D-038, D-047), a resume's newly built system prompt. Requests set `drop_block` (D-032), so nothing failed; but the history still held every invalidated block, so every later request sent them again, the API dropped them again, and the runtime showed a warning for each, round after round until a compaction: one warning per dropped block on every round, and those blocks' bytes sent each time.
- **Decision**: the context remembers the conversation's last request as sent. When a projection first differs from it at some position, every bound block from there on -- Anthropic `thinking` and `redacted_thinking` entries in an assistant's opaque block -- is left out, in this request and every later one; text and tool calls stay verbatim, and an opaque block left empty goes (the adapter rebuilds the turn from its text and calls). Blocks before the change keep their prefix and are sent; a reply made by the request that carried the change is bound to the new prefix and is sent too. A turn that only appends changes nothing. A compaction starts a new prefix. The live history keeps every reply as received; only the projection leaves reasoning out, and the journal's `model_request` records what was sent. A resume reads the last request back (`JournalState.last_sent`), so a changed system prompt is noticed on its first request, and puts back the original reply where the first request to carry it had already left its thinking out, from the `model_response` record that kept it. `drop_block` stays as the net for an edit this misses.
- **What it may not weaken**: the requests remain exactly what the journal records, and a resume rebuilds the same projection as the session it continues. Only reasoning the API would have dropped is left out; nothing the model said or called is.
- **Rejected**: append-only edits everywhere (masking exists to shrink the prefix; the documented alternative is server-side context editing, which only Anthropic has); a mid-conversation `system` message instead of a rebuilt permissions paragraph (newer Claude models take it, older ones and the other protocols differ); stripping all thinking after any edit (blocks before the edit are still valid); relying on `drop_block` alone (the cost above, and a gateway that rejects the beta header would leave nothing).
- **Deferred**: Anthropic server-side context editing in place of masking on that protocol.

## D-049 Programs are found on PATH, never in the current directory
- **Date**: 2026-11-07 · **Status**: confirmed (security; found while building the `notify` program of roadmap item 11)
- **Background**: on Windows a program named without a path is looked for in the directory the parent was loaded from, then in the parent's *current directory*, then in the system folders, and only then on PATH -- CreateProcess does this, and `shutil.which` still puts the current directory first when it is given a PATH. Foundry is usually started in the repository it works on, and it named its programs bare: `git` for the baseline and every diff, `powershell.exe` for every command, `taskkill` as a last resort, the doctor's PowerShell check, and MCP servers through `shutil.which`. A clone with a `git.exe` at its top therefore ran it when a session began, before anything was asked; one with a `powershell.exe` ran it for every command, those a rule allows without a question included. Measured on this machine with `NoDefaultCurrentDirectoryInExePath` unset, as Windows ships: `subprocess.run(["git", "--version"])` in such a folder ran the planted program, and `shutil.which("uvx", path=PATH)` returned `.\uvx.EXE`. (This test harness sets that variable, which is why nothing had shown it.)
- **Decision**: one resolver, `winapi.find_program(name, env)`. A bare name is looked up on that environment's PATH alone; a relative PATH entry (`.`, an empty entry, `bin`) is the current directory by another name and is skipped; PATHEXT applies as cmd.exe applies it (a name already ending in one is taken as it is). A name with a directory part must be absolute. Every program Foundry starts is started by the absolute path this returns -- CreateProcess does not search for a path -- and a program not found is named as before (`git is not on PATH`, `'x' was not found on PATH`).
- **What it may not weaken**: what PATH found before is found now, in the same order; only the current directory and relative entries are gone. The commands the model runs are unchanged: PowerShell does not run a program from the current directory without `.\`.
- **Rejected**: setting `NoDefaultCurrentDirectoryInExePath` in Foundry's environment (one process-wide switch that CreateProcess and `shutil.which` happen to honour, inherited by every child, and invisible at the call it protects; an absolute path can be checked at each site); changing directory at startup (paths the user typed are relative to where they typed them).
- **Not covered**: DLLs. Windows looks for a DLL a program loads in the program's own folder and the system folders before the current directory, which covers git, PowerShell and Python as installed; a program that loads a DLL from none of those is outside what Foundry can fix.

## D-050 A program the user names is told when a turn ends
- **Date**: 2026-11-07 · **Status**: confirmed (item 11 of the codex-parity order)
- **Background**: long work is left to run while the user does something else, and nothing told them it had stopped -- finished, blocked on a question, or out of budget. codex has `notify`: a program it runs at the end of each turn with a JSON description as its last argument.
- **Decision**: `notify = ["program", "arg", ...]` at the top of `config.toml` (or a profile; `[]` turns it off). When `run_turn` returns, the runtime starts it with one more argument, the JSON `{"type": "agent-turn-complete", "session-id", "cwd", "status", "input-messages", "last-assistant-message"}` -- codex's names, with `session-id` for its thread and `status` the task's terminal status, or `null` when the model answered without ending it. Not when the user stopped the turn: they are at the keyboard. The program is found on PATH (D-049), started without a shell, in the workspace, with the command environment (credential-shaped variables removed), in its own process group, with no stdin and its output discarded; Foundry does not wait for it. Each start is a `notified` record (`program` and `pid`, or `error`); a program that cannot be started is a warning the first time and a record each time, never a failed turn. The texts are scrubbed of the secrets Foundry knows and cut to 2,000 characters each, so the argument fits a Windows command line however it is quoted.
- **What it may not weaken**: a repository cannot name the program -- its config is refused, as for MCP servers (D-043) -- and `-c` cannot set it. The payload carries the model's words, so they are never read as commands: there is no shell, and on Windows a batch file or `cmd.exe` is refused, since cmd.exe parses its arguments again (`"`, `&`, `%`), the class of hole known as BatBadBut; the error names an interpreter instead (`["python", "notify.py"]`).
- **Rejected**: running it through the shell, as a command line in the config (the payload would have to be quoted for each shell, and a mistake runs the model's text); passing the payload on stdin (codex scripts read the last argument, and stdin would need a writer thread that a hung program blocks); a desktop notification built in (Windows toasts need an app identity and a COM call; a program is one line of config and works anywhere).
- **Deferred**: a payload for an approval waiting on the user (codex's newer events), and a timeout that ends a program that never exits.

## D-051 exec --output-schema: the run's result, of a shape the caller chose
- **Date**: 2026-11-07 · **Status**: confirmed (item 12 of the codex-parity order)
- **Background**: a script that runs `foundry exec` wants an answer it can parse -- a list of findings, a verdict, a version number -- not a summary in prose. codex has `exec --output-schema FILE`, which hands the schema to the provider's structured output for the final message.
- **Decision**: the schema becomes a `result` argument of `finish`, the only way a task reaches a terminal status (D-017). `--output-schema FILE` reads a JSON Schema (at most 64 KB) and refuses, before the run, any keyword outside the subset `core/json_schema.py` enforces -- types, `properties`/`required`/`additionalProperties`, `items`, `enum`/`const`, `anyOf`/`oneOf`/`allOf`/`not`, `$ref` within the schema (`#`, `#/$defs/...`), and the bounds on strings, numbers, arrays and objects; annotations (`title`, `description`, `format`, ...) are ignored. In finish's parameters the schema sits under `result`, its `$defs` moved to the top and every other ref rewritten to match. `finish` checks `result` itself: required with `completed`, optional with any other status, plain JSON (no NaN), and matching the schema; what does not match is an invalid call naming the first five problems by place (`$.tags[1]: must be one of ["a", "b"]`), which the model can correct. The result rides `TurnOutcome.result_json`, the termination record and the `Termination` event (`--json` consumers get it there). On stdout `exec` prints the result and nothing else, scrubbed, and `-o` writes it; without one, stdout stays empty, the summary goes to stderr and `-o` is not written -- the exit code says why. The reminder to call finish asks for the result too.
- **What it may not weaken**: `completed` still needs its claims to hold (D-017): a result does not vouch for itself, and a result whose claims fail ends `partial` with the result printed and exit 10. The result is model output: scrubbed of known secrets wherever it leaves (stdout, `-o`, events, journal) and never acted on.
- **Rejected**: the provider's structured output for the final message (the last turn is a tool call here, not a message; the three protocols spell it three ways and gateways may not pass it; Foundry would still have to check what came back); a separate request after finish asking for the JSON (another paid call, and a second account of the work that need not match the first); a third-party `jsonschema` package (the core is standard library only); accepting a schema with keywords Foundry does not check (a schema that is not enforced is worse than one refused).
- **Deferred**: `format` assertions, `patternProperties`, `if`/`then`/`else` and tuple `items`; the result for `run`'s REPL.

## D-052 A message of several lines at the prompt
- **Date**: 2026-11-07 · **Status**: confirmed (item 13: the first gap after the codex-parity list)
- **Background**: the prompt read one line per task. Pasting a stack trace, a log or a block of code -- the most ordinary way to show a model a problem -- sent each line as its own task: the first line went to the model alone, and every later line queued up as another request. codex's terminal UI takes a paste whole and has a key for a new line.
- **Decision**: `read_message` reads one message. After the first line it asks whether more input is already waiting at the terminal -- `msvcrt.kbhit()` on Windows, `select` elsewhere, allowing 30 ms between lines -- and while it is, reads the next line into the same message: a paste arrives at once, faster than anyone types. Blank lines at the ends of a paste go, its indentation stays, and the prompt says how many lines were sent as one. A line of three double quotes, typed (nothing waiting after it), opens a block that the next such line closes, for writing several lines by hand; Ctrl+C inside discards the block and the session goes on. Input that is not a terminal is read a line at a time, as before. Checked in a real console: a child process with a console of its own puts a three-line paste into its input buffer as key events, the way the console does, and reads one message.
- **What it may not weaken**: only the task prompt reads messages; approval questions read a single line as before. A slash command's pasted continuation becomes its arguments, as `parse_command` already allowed.
- **Rejected**: a trailing backslash to continue a line (a Windows path ends in one); `prompt_toolkit` or a full-screen UI (a dependency the corporate machines this targets may not install; the stdlib console already gives line editing and history); bracketed paste (the Windows console's line input does not pass the markers through).
- **Deferred**: a key for a new line inside a typed message (it needs raw console input), and editing an earlier message.

## D-053 exec - reads the task from stdin
- **Date**: 2026-11-07 · **Status**: confirmed (item 14)
- **Background**: a long task -- a bug report, a spec, a prompt a script fills in -- does not fit a command line, and Windows quoting mangles one with quotes in it. `codex exec -` reads the prompt from stdin.
- **Decision**: `foundry exec -` reads the task whole from stdin, at most 1 MB. A byte-order mark decides the encoding (UTF-8, or UTF-16 as PowerShell 5.1's `Out-File` writes it); without one it is UTF-8, or else the console's code page, as command output is decoded (`winapi.decode_output`). Line ends become `\n` and the ends are trimmed. A terminal on stdin, no stdin, nothing but blank lines, or more than the limit is refused with exit 2 before anything starts. A task named on the command line never reads stdin.
- **What it may not weaken**: the task is the user's, as one typed is; nothing else is read from stdin, and approvals in exec stay off (ASK is DENY).
- **Rejected**: reading stdin whenever no task is given (a script that forgets the task would hang on an open pipe); appending stdin to a task given on the command line (two sources for one task, and a pipe a script did not mean to send).
- **Note**: Windows PowerShell 5.1 sends a string piped to a program as `$OutputEncoding`, ASCII by default, so non-ASCII text arrives as `?`; setting `$OutputEncoding = [Text.UTF8Encoding]::new($false)` first, redirecting a file in cmd (`foundry exec - < task.md`), or PowerShell 7 keeps it.

- **Decision**: once the conversation has begun, a dim line above `foundry>` says "N% context left": 100 less the share `/status` shows, from the same estimate (the projected request against `max_context_tokens`), never below 0. Under 20% the line is yellow. A new session shows the plain prompt.

## D-055 `!COMMAND` at the prompt runs a command for the user
- **Date**: 2026-11-07 · **Status**: confirmed (item 16)
- **Background**: to show the model what `git log` or a failing test prints, the user had to run it in another terminal and paste the output, or ask the model to run it and approve that. codex's prompt runs a line that starts with `!` as a shell command and puts its output in the conversation.
- **Decision**: a message that starts with `!` is a command the user runs. It is the user's own, so no policy rule or approval stands in front of it, but it runs as `run_command` does: from the workspace root, in Windows PowerShell 5.1, with the same minimal environment (`child_environment`) and time limit, nothing on its input, and its process tree ended by Ctrl+C or the limit. What it printed -- stdout, then stderr, line ends made `\n`, scrubbed, cut to a tool result's size -- is shown, and the model is told it with the user's next message, saying the command was the user's. A command that does not start is said and not recorded; one stopped with Ctrl+C is recorded and the model is not told. `!` alone shows how to use it. Each command is journaled as `user_command` (command, exit code, timed out, stopped, duration).
- **What it may not weaken**: the evidence chain. A command the user ran may have changed any file, and which ones is not known, so no command run before it can vouch for the workspace: it counts as a change, as an undo does. The model cannot cite it either, since it is not one of the model's recorded commands, and the note says so. What reaches the model, the screen and the journal is scrubbed of registered secrets; the environment keeps API keys out of the command, as it does for the model's.
- **Rejected**: the user's full environment (its output goes to the provider, and a stray `env` would send every key); running it through `cmd.exe` or a shell of the user's choosing (one shell for the user and the model, so a command that worked for one works for the other); citing it in `finish` (the claim would rest on a command the model did not choose or see run); sending it to the model at once, as a turn of its own (a turn costs a request; the user's next message says what to do with it).

## D-056 /rewind goes back to before one of the user's messages
- **Date**: 2026-11-07 · **Status**: confirmed (item 17)
- **Background**: a message that sent the model the wrong way stayed in the conversation: the only ways out were arguing it back or `/new`, which loses everything. codex's Esc Esc goes back to an earlier message, to send it again edited.
- **Decision**: `/rewind [N]` goes back to before the user's last message, or the Nth last, since the conversation or its last compaction began. The model no longer sees that message or anything after it; the message is shown, to be sent again as it was or edited. Nothing in the workspace is reverted -- `/undo` does that -- and the model is told so with the next message, naming the files it patched after that point (those this process saw: since the session started, resumed or was last compacted) and saying commands may have changed others. Every file is read again before it is patched, as after a compaction. The history kept is journaled whole as `rewound` (with each message's round, so masking resumes where it was), and the resume fold takes it as it takes a compaction's; synced, as a compaction is.
- **What it may not weaken**: what is kept is unchanged, so the reasoning in it stays bound to the request it came from (D-048): the last request sent is cut to the same prefix, and so is the set of replies whose reasoning had stopped being sent. The evidence chain is unaffected: the workspace did not change. A rewind record that does not hold together -- messages and rounds of different lengths, rounds out of order or past the session's -- stops a resume rather than being guessed at.
- **Rejected**: reverting the files patched after the point as well (that is `/undo`, and a revert the user did not ask for loses work); going back past a compaction (its summary is what the model knows of the work before it; dropping it drops everything); journaling only the number of messages kept (a resume would have to rebuild the history at that point from the requests and their tail, a second path to get wrong); putting the old message back on the prompt line to edit (the console's line input cannot be filled from the program on every terminal; it is printed instead).

## D-057 `foundry resume` with no id lets the user pick
- **Date**: 2026-11-07 · **Status**: confirmed (item 18)

## D-058 `@path` in a message attaches the file
- **Date**: 2026-11-07 · **Status**: confirmed (item 19)
- **Background**: codex and Claude Code let the user name a file with `@` in a message. Here the model had to be asked to read it, a round trip for something the user had already pointed at.
- **Decision**: in a message the user types, `@path` -- or `@"a path"` with spaces -- names a file in the workspace, and that file goes with the message as read_file would show it: numbered, its first window of lines, cut to a tool result's size, after the user's text and saying it was attached with `@`. It counts as read, so the model can patch it without reading it again. Not after a word character, so an e-mail address is not a mention; punctuation after a path ends the sentence, not the path. At most ten files go with one message, each once. A name that is not a file in the workspace is sent as written, and said so when it looks meant as one (a separator or an extension, or quoted), so `@property` in pasted code passes quietly.
- **What it may not weaken**: only a file inside the workspace, resolved as every tool resolves paths; a policy rule that refuses reading the file refuses this too, while one that would ask is answered by the user having typed it; what is attached is scrubbed of registered secrets, as a tool result is. Only what the user types is looked at: a slash command's prompt, a repository's custom prompt included, is not, so a prompt someone else wrote cannot attach files.
- **Rejected**: completing paths as they are typed (the console's line input has no completion hook on Windows without a third-party library); attaching a whole long file (the window and the size cut keep one message from filling the context; the model pages as read_file does); attaching images with `@` (`/image` does that, with the checks images need).

## D-059 An interactive session says how to continue it as it ends
- **Date**: 2026-11-07 · **Status**: confirmed (item 20)
- **Background**: when a codex session ends it prints the tokens used and the command that resumes it. Here a session ended silently; continuing it meant finding its id with `foundry sessions`, and nothing said what it had cost.
- **Decision**: when `foundry` / `foundry run` / `foundry resume` ends -- `/exit`, Ctrl+C or end of input at the prompt, a one-shot task, or `/new` for the session it ends -- one dim line gives the tokens the session used (input, cached input when there was some, output; a resumed session's figures include its earlier runs) and `foundry resume <id>`, with `--workspace` when the current folder is not the workspace. A session that never began a conversation says nothing. When its journal could not be written in full, the line says so instead of offering a resume that may fail.
- **What it may not weaken**: the figures are the provider's, as `/status` shows them, never estimates; `exec` prints nothing new (its stdout belongs to the caller, and `--json` already carries usage).
- **Rejected**: printing it in `exec` (a script reads the exit code, and `--json` carries the usage in its `token_count` events; that `exec` does not yet report its session id is a gap of its own); a cost in money (Foundry does not know the gateway's prices).

## D-060 `exec` says which session it records
- **Date**: 2026-11-07 · **Status**: confirmed (item 21)
- **Background**: `exec --resume ID` continues an unattended run, but nothing an `exec` printed said what its id was: a script had to guess `last` -- wrong as soon as two runs share a workspace -- or read the sessions folder. codex's exec prints its session id, and its JSON stream opens with it.
- **Decision**: before anything else it says, `exec` emits a `session_started` event: the session id, the workspace, the model, and whether it was resumed. With `--json` it is the first line on stdout; without, one dim line on stderr (`session <id>`, or `resumed session <id>`), so stdout stays the caller's. A resumed run names the same id.

## D-061 Reasoning effort on every protocol, and `/effort`
- **Date**: 2026-11-07 · **Status**: confirmed (item 22)
- **Background**: `backend.effort` reached Claude alone (`output_config.effort`); on the Responses API and Chat Completions it was refused. Those APIs take an effort too -- `reasoning.effort` and `reasoning_effort` -- and codex lets its user choose it, in the config and mid-session from `/model`. A hard task wanted more reasoning than the API's default, and a quick question less, without editing the config and starting again.
- **Decision**: `backend.effort` is sent on every protocol, as each spells it: `output_config.effort` for Claude (low, medium, high, xhigh, max), `reasoning.effort` beside `reasoning.summary` for the Responses API, `reasoning_effort` for Chat Completions (none, minimal, low, medium, high, xhigh for both). `load_config` checks the value against the protocol it ends up with, after every layer and the command line, and names the protocol and its levels when it does not fit. `/effort` shows it; `/effort LEVEL` changes it for the following requests, and `/effort default` stops sending one. The change is written as `effort_change` (synced, as `model_change` is), shown in `/status`, and kept by `/new` as `/model`'s choice is.

Only the user changes it: the command is read from what they type. The model is not told, and the system prompt is not rebuilt: the effort is how the API runs the model, not something the conversation says.

## D-062 Ctrl+C stops the turn, not the session
- **Date**: 2026-11-07 · **Status**: confirmed (item 23)
- **Background**: at the interactive prompt, a Ctrl+C while the model answered or a tool ran ended the whole session, and so did (a)bort at an approval: the conversation, the grants and the context built up were gone, and the only way on was `foundry resume`. codex stops the turn and comes back to its prompt. An abort also left the turn's later calls with no result, and stayed set, so a task after it would have been cancelled before it began.
- **Decision**: in an interactive session, a Ctrl+C during a task -- while the model streams, a tool runs, or a compaction is written -- or (a)bort at an approval ends that task as `cancelled` ("interrupted by user", journaled as before) and the prompt comes back, saying the session is still open. Every call of the model's last message that has no result gets one, journaled as `tool_reply`: the one whose tool was running is told it was stopped and that what it changed is not known; the ones after it, that they did not run. The model is told with the next message that the user stopped its previous turn. A cancellation is spent by the task it stops, so the next one starts afresh. A Ctrl+C during `/compact` stops the summary and leaves the conversation as it was. A Ctrl+C at the prompt still ends the session, and so does a second one while the first is being handled; a one-shot `foundry run TASK` and `exec` end on Ctrl+C as before.
- **What it may not weaken**: a call stopped while its tool ran may have changed something, so it counts as a change, as its result would have: no command run before it can vouch for the workspace, and the files it named are read again before they are patched. A command stopped is not counted, as a command that finishes is not (it is evidence, not a change); its process tree is ended as before. The calls are answered from what the runtime knows -- which call was running, not a guess from the journal -- and a resume reads the replies back with nothing left to repair. A Ctrl+C arriving as a task's ending is written does not write a second one.
- **Rejected**: catching Ctrl+C inside the runtime for every caller (an unattended run that is interrupted should end, and its journal is repaired on resume as before); keeping what the model had streamed of an interrupted reply (it was not finished, and a half answer read back as the model's own is worse than none); a "press Ctrl+C again to quit" prompt (one at the prompt already ends the session, as it always has).

## D-063 A task's ending is not the session's
- **Date**: 2026-11-07 · **Status**: confirmed (item 24)
- **Background**: the system prompt tells the model to call `finish` when a task is done, and at the interactive prompt that ended the session: the user who wanted to ask a follow-up, or start the next change in the same context, had to resume. So did a task stopped by its budget (`max_tool_rounds`, `max_tool_calls`) or a full context. codex ends a turn and waits for the next message; only its user ends the session. Only a blocked turn (D-035) and, since D-062, a stopped one went back to the prompt.
- **Decision**: at the interactive prompt, every task's ending goes back to the prompt: it is shown as before (status, reason, summary) and a dim line says the session is still open. The session ends when the user ends it -- `/exit`, Ctrl+C or end of input at the prompt -- or starts another with `/new`. Before anything is sent again, the calls the task left are answered and journaled as `tool_reply`: `finish` as accepted, with the status it ended with and the reason when it adds one; a call after it, or one a budget kept from running, as not run, saying how the task ended. The next task's limits start afresh, as they did (each task already had its own).
- **What it may not weaken**: each task still writes its own termination, and `completed` still comes only through the finish gate, which checks a later task's claims as it checks any: each must cite a command the session recorded, run after the last change to the workspace. A resume rebuilds the conversation from the replies, with nothing to repair. An unattended run (`exec`, a one-shot `foundry run TASK`) ends with its task as before, and its journal is unchanged -- a resume of it answers what the task left, as it did.
- **Rejected**: answering the calls as the task ends, in every caller (an unattended run has no next request, and its journal would change for nothing); taking `finish` away from interactive sessions (it is how a task reports its outcome and its evidence, which the user reads); an interactive session's exit code from its last task (the session ends when its user ends it, 13 as `/exit` always gave; `exec` is the command whose exit code is a task's).

## D-064 `/mcp` lists the servers and their tools
- **Date**: 2026-11-07 · **Status**: confirmed (item 25)
- **Background**: a session said once, as it started, how many tools each MCP server offered (D-043), and `/status` repeats that count; nothing showed which tools those were, whether the model may use them without asking, or that a server had died since. codex's `/mcp` lists the configured servers and their tools.

Under each, its tools as the model sees them -- `mcp__<server>__<tool>` -- with `read-only` when the entry says `read_only = true` and `may change things` otherwise, and the first 60 characters of what the server says the tool does. Tools a server listed that are not offered follow, with why. With no server configured it says how to add one.

A tool's description is the server's own text, so it is cleaned of terminal control sequences and escaped before it is shown, as every other untrusted string on the screen is. The command only reads what the session already knows; it starts nothing and asks no server anything.

## D-065 `/image` alone takes the clipboard's image
- **Date**: 2026-11-07 · **Status**: confirmed (item 26)
- **Background**: a screenshot reached the model only as a file: `-i PATH` or `/image PATH` (D-045). On Windows a screenshot (Win+Shift+S) lands on the clipboard, and saving it first is a detour codex does not ask for: its Ctrl+V pastes the image into the message. Foundry reads its input a line at a time with the console's own editing, so a key that pastes an image is not one it can see.
- **Decision**: `/image` with no path takes the image on the clipboard for the next message, as `/image PATH` takes a file's: checked by the same rules (PNG from its own bytes, at most 3.75 MB, no side over 8000 pixels), counted against the eight a message may carry, and refused before the clipboard is read when the backend is set up without images or the message is full. It is read by Windows PowerShell, found on PATH by its absolute path (D-049), started with no profile, nothing on its input, no window and a single-threaded apartment (the clipboard needs one), running a fixed script that writes the image as PNG in base64; fifteen seconds at most. A clipboard without an image says so and attaches nothing; one that cannot be read says why. Elsewhere than Windows it says the clipboard is read on Windows only. `-i` still needs a path.
- **What it may not weaken**: only the user's own command reads the clipboard -- what the model or a tool writes never does -- and what it holds is treated as any image the user attaches: untrusted content, kept by digest, never inline. Nothing is written to disk to read it, and nothing from the clipboard reaches the script, which is a constant.
- **Rejected**: a key binding for it (the console's line editing owns the keys); text from the clipboard too (a paste already arrives as typed text, D-052); a copied image *file* (`/image PATH` names it).

## D-066 `/review` of a branch, or of one commit
- **Date**: 2026-11-07 · **Status**: confirmed (item 27)
- **Background**: `/review` (D-039) looked only at what is not committed. codex's `/review` also reviews a branch against its base, as a pull request shows it, and a single commit -- the reviews people ask for once the work is committed. Foundry's model had no way to see either: `git_diff` showed only the working tree and the index, and `run_command` is refused while a review runs.
- **Decision**: `git_diff` takes `base` -- what this branch changed since it left that branch, tag or commit: the diff from their merge base to the working tree, so the commits and what is not yet committed -- or `commit` -- that commit's message and its patch (`git show`, so the first commit shows too). At most one of `staged`, `base` and `commit`; `path` narrows any of them. `/review --base REV [focus]` and `/review --commit REV [focus]` resolve the revision to a commit id before the task starts; one that names no commit is reported and nothing is sent. The task names the revision as the user typed it and the full id, and tells the model to call `git_diff` with the id, so what it reviews is what the user named even if the branch moves. `/review [focus]` is unchanged. The review prompt no longer says what to review; the line before it does.
- **What it may not weaken**: a revision reaches git only as a full commit id, resolved by `rev-parse --verify` with `^{commit}` appended. A name that starts with `-` (git would read `--output=FILE` as an option and write the file), has a space or a control character in it, or is over 200 characters is refused before git runs -- in the tool's arguments and at the REPL alike. Every git call keeps the hardened arguments, `--no-ext-diff --no-textconv` included. The review is read-only as before: `git_diff` is a read-only tool, and every mutator is refused while it runs. A commit message is untrusted content, as a file is; the task text holds the revision's name and id, never its message.
- **Rejected**: letting the model run `git log` / `git diff BASE...` itself (commands are refused during a review, and allowing some would make "read-only" a parser's judgment); a three-dot diff (it leaves out what is not committed, which the user is usually still reviewing); a picker of branches and commits (codex's is a menu; here the revision is typed, and an unknown one says so).

## D-067 `/model` lists the endpoint's models
- **Date**: 2026-11-07 · **Status**: confirmed (item 28)
- **Background**: `/model NAME` (D-047) switches to another model behind the same endpoint, but nothing in Foundry said which names the endpoint takes: on a gateway that fronts several providers the user had to look the spelling up elsewhere (`us.anthropic.claude-...:0`, `openai/gpt-5`), and a wrong one surfaced only as a failed turn. codex's `/model` offers a list to choose from.
- **Decision**: `/model` with no name asks the endpoint for its models -- `GET {base_url}/models`, which OpenAI-style endpoints, the Responses API and Anthropic's API all answer as `{"data": [{"id": ...}]}` (Anthropic's with `?limit=1000`, one page) -- and prints the ids sorted, each once, the session's own in bold, at most 200 of them, then the usage line as before. It is asked each time, only when the user types `/model` with no name; a switch by name does not ask. Fifteen seconds at most to connect and between reads, a megabyte of answer at most, never retried. An id that `/model NAME` would not take is left out and counted. A backend that cannot list (a scripted or replayed one) says so; a failure says what kind (`request rejected (HTTP 404)`, `authentication rejected (HTTP 401)`, a timeout) and the session goes on; Ctrl+C stops the asking, not the session. `/model NAME` is unchanged: a name the endpoint does not list is still accepted, since a gateway may serve more than it lists.
- **What it may not weaken**: the request goes only to the endpoint the session already talks to, with the credential and headers every turn sends -- Anthropic's without the betas a turn asks for -- through the same client (proxy handling, TLS, no redirects). What comes back is untrusted text: only ids shaped as model names are shown, escaped, and they are never sent to the model or written to the journal. An error shows its status, never the server's answer, which could echo anything back, the credential included.
- **Rejected**: an interactive picker (the console's line editing owns the keys, as in D-065; a typed name is one command away); caching the list for the session (the request costs no tokens, and a cached list goes stale); checking `/model NAME` against the list (an endpoint may serve models it does not list, and the check would cost a request per switch).

## D-068 What a command printed, in view
- **Date**: 2026-11-07 · **Status**: confirmed (item 29)
- **Background**: a command the model ran showed as `-> python -m pytest -q` and then `ok` or `failed`; the exit code appeared only with `-v`, and what the command printed never: the model read the test results, the person watching did not, and had to take the model's word for them or run the command again. codex shows the last lines of a command's output under it. `ToolOutputDelta` has been in the event protocol from the start, and nothing emits it.
- **Decision**: `run_command` keeps the last lines of what the command printed -- at most 20, and 4,000 characters, the end kept, without the blank lines it ends with -- and `tool_end` carries them as `output` (empty for every other tool). The renderer shows the exit code on the `ok` / `failed` line for a command whatever the verbosity, and under it the last 5 of those lines, dim and indented, with `...` above when there were more; with `-v`, all 20. A line is cut at 240 characters. `exec --json` carries `output` in its `tool_end` events. The model still reads the whole output, truncated as before; nothing new is journaled (the journal already keeps the command's output).
- **What it may not weaken**: a command prints anything. What reaches the screen is stripped of control sequences (OSC 52, cursor movement, screen clearing) and printed as plain text, never read as rich markup; `output`, like every string an event carries, passes the redactor on its way out, so a credential the command printed reaches neither the screen nor `exec --json`.
- **Rejected**: streaming the output while the command runs (`ToolOutputDelta`; the capture is collected whole by `run_process`, and a live view of a long build is a larger change -- left for later); showing the whole output (the model's copy can be a megabyte; the journal and `read_artifact` keep it); the output of other tools (a file read or a search is the model's to read; a patch is shown when it is approved).

## D-069 Working, and for how long
- **Date**: 2026-11-07 · **Status**: confirmed (item 30)
- **Background**: while the model was asked, or a command ran, nothing on the screen moved: a test suite that took four minutes looked the same as a hung request, and the only way to tell was to wait or press Ctrl+C. codex shows `Working (12s • esc to interrupt)` under the conversation for as long as it waits.
- **Decision**: the renderer puts up a line -- `working (12s, Ctrl+C to stop)` while the model is asked, `running (...)` while a tool runs -- with an ASCII spinner and the time since it went up, redrawn four times a second by rich's live display. It goes up on `turn_started` and `tool_begin`, and comes down before anything else is drawn: every other event, an approval question, the end of a task however it ends (Ctrl+C and an exception included, in `run_task`) and the end of the session (`_close`). It is drawn only on a terminal -- never into a pipe, a file or `exec`'s redirected stderr -- and is transient: once down, nothing of it is left on the screen.
- **What it may not weaken**: the line holds only Foundry's own words and a time, nothing the model or a tool wrote. Nothing is asked while it is up: approval and the prompt each take it down first, so a question is never redrawn over or hidden.
- **Rejected**: the line during `/compact` and `!COMMAND` (they say what they are doing, and are short); naming the command on the line (the `->` line above it already does); Esc to stop (the console's line editing owns the keys between turns, and Ctrl+C already stops the turn, D-062).

## D-070 The answer as Markdown
- **Date**: 2026-11-07 · **Status**: confirmed (item 31)
- **Background**: the model writes Markdown -- headings, `**bold**`, inline code, fenced code -- and Foundry printed it raw, markers and all, as it streamed. codex renders it as it streams, committing a line when the line ends. Building this turned up a bug in the raw path: the text was escaped for rich markup *and* printed with markup off, so `list[int]` reached the screen as `list\[int]`.
- **Decision**: on a terminal, the model's text is rendered a line at a time (`cli/markdown.py`): a line is held until its newline (or the end of the text) and then printed with a small, fixed subset -- headings bold (levels 1 and 2 underlined too), `**bold**`, `*italic*` (not `_italic_`, which would eat snake_case), inline code, a link as its text and its address, quotes, rules -- and a fenced block is highlighted by its language once the fence closes (one left open is shown when the text ends). Lists and tables are left as the model wrote them. Text still held when a task ends -- however it ends -- is printed then. Off a terminal (a pipe, a log, `exec`'s redirected stderr) the text is printed as it comes, exactly as the model wrote it; the escaping that added backslashes is gone from both paths.
- **What it may not weaken**: the text is untrusted. Each whole line is stripped of control sequences -- whole, so a sequence the stream split across two chunks is still caught, which stripping each chunk could miss -- and carriage returns are dropped, so a line cannot overwrite itself; what is printed is built as rich `Text`, so a `[red]` or `[link=...]` the model writes is shown, not obeyed; and a link is never a terminal hyperlink, whose target the reader would not see.
- **Rejected**: rich's own Markdown renderer (it centres headings in boxes, turns links into terminal hyperlinks, and needs whole blocks, so it cannot commit line by line); rendering off a terminal (a log should hold what the model wrote); showing text before its line ends (a half-line cannot be rendered and then redrawn without a full-screen UI).

## D-071 Named placeholders in custom prompts
- **Date**: 2026-11-07 · **Status**: confirmed (item 32)
- **Background**: a custom prompt (D-039) took `$1`..`$9` and `$ARGUMENTS`, so a prompt with several inputs had to be called with them in a fixed order, and nothing said which was which. codex's prompts also take named placeholders -- `$FILE`, `$TICKET_ID` -- filled by `FILE=src/x.py` on the command line.
- **Decision**: a whole word in capitals after `$` is a named placeholder (`$FILE`, `$TICKET_ID`, `$D_2`); `$PSVersionTable`, `$env:PATH` and `$fileName` are not, and `$ARGUMENTS`, `$1`..`$9` and `$$` keep their meaning. A word `NAME=value` (quotes respected; the last one given wins) fills `$NAME` -- but only when the prompt uses NAME, so `DEBUG=1` stays an ordinary word for a prompt that does not. The other words are the positional ones; `$ARGUMENTS` is still everything typed. A named placeholder with no value stops the prompt: nothing is sent, and the user is told which `NAME=...` to add, and that `$$NAME` writes a literal `$NAME`. `/help` shows a prompt's named values (`/draft TICKET=... FILE=...`) when its front matter gives no `argument-hint`.
- **What it may not weaken**: commands still come only from the user's typed line. The values are the user's own text, put in once and never expanded again (a value of `$2` stays `$2`). A repository's prompt is still read only where the user trusts the repository.
- **Rejected**: leaving an unfilled `$NAME` in place (the model would get a prompt with a hole, and act on it); treating every `KEY=value` word as named (a prompt about environment variables would lose its arguments); asking for missing values one by one (a prompt is one line, as codex's are).
- **A change for existing prompts**: a capitalised `$HOME` or `$PATH` meant literally is now a placeholder, and the prompt says it needs `HOME=...`; write `$$HOME`.

## D-073 How long a task took
- **Date**: 2026-11-07 · **Status**: confirmed (item 34)

## D-074 The newest line of a running command
- **Date**: 2026-11-07 · **Status**: confirmed (item 35)
- **Background**: while a command ran, the working line (D-069) said `running (2m 10s, Ctrl+C to stop)` and nothing else; what it printed came only with its end (D-068). A long build or test run looked the same whether it was busy or stuck. codex shows a running command's output as it comes. Two things stood in the way: the pipe reader asked for 64 KB at a time, and on a pipe that waits for 64 KB or the end, so a command printing a line a second delivered nothing for minutes; and `ToolOutputDelta`, in the event protocol from the start, had no producer.
- **Decision**: the reader takes what has arrived (`read1`) and keeps the last 4 KB of each pipe, past the capture budget too. While `run_process` waits for the command, at each 0.2 s slice, it looks for the newest complete line -- of whichever pipe ended a line last -- and passes it on at most every half second, and only when it changed. The runtime sets the call's teller on the tool context for the call (and clears it however the call ends) and emits `ToolOutputDelta{call_id, text, stream}`; on a terminal the renderer puts the line after the working line, cut to the screen's width, without taking the line down: `running (2m 10s, Ctrl+C to stop): collected 340 items`. Off a terminal it is ignored; `exec --json` carries the events.
- **What it may not weaken**: redaction. The redactor recognizes a credential only whole, so only whole lines leave: ended by a newline, or by the carriage return a progress bar redraws its line with. A window that has filled drops its first line, which may begin partway through one. NULs are removed, so UTF-16 text read as UTF-8 is matched like any other. Each line passes the event sink's scrub and is stripped of control sequences before it is drawn. The model's copy, the journal and `ToolEnd` are unchanged; nothing new is written.
- **Open**: a program that buffers its output when it is not writing to a terminal (Python without `-u` or `PYTHONUNBUFFERED`) shows its lines as it flushes them; the child's environment is not changed to hurry it.
- **Rejected**: streaming every line (the screen has one line to give it, and the whole output comes at the end); a pseudo-terminal (a different process model, and programs would then print colour codes into the model's copy).

## D-075 What a patch changed, in view
- **Date**: 2026-11-07 · **Status**: confirmed (item 36)
- **Background**: a patch was shown only when someone was asked to approve it, and then as proposed. In `accept_edits` mode, or under an "always" rule, an edit went by as `-> apply_patch: update src/app.py` and `ok`: the person watching learned that a file changed, not how. D-068 rejected showing the output of tools other than `run_command` because "a patch is shown when it is approved" -- which is exactly when it is not needed most. codex shows every edit, with its added and removed lines, whether or not it asked.
- **Decision**: once a patch lands, `ToolEnd.output` carries what it changed -- for each file that landed, `updated src/app.py (+2 -1)` (`created`, `deleted`, `updated and moved a -> b`), then its unified diff with three lines of context -- computed by the tool from the text before and the text written. The renderer shows the first 40 lines under the patch, coloured (added green, removed red, hunk headers cyan), and all of them with `-v`. A file the patch could not change has no diff (the model hears about it). A deleted file's lines are shown if it is UTF-8 text of at most a megabyte, else just its name. The model is told what it was told before, and the journal keeps no copy: the diff is in the event, not the tool result.
- **What it may not weaken**: redaction and the screen. A line is never cut -- the redactor recognizes a credential only whole -- so a line over 1,000 characters is replaced by its length; the whole is at most 400 lines, the rest counted. The diff passes the event sink's scrub, is stripped of control sequences, and is printed as Text, never as markup.
- **Rejected**: the patch as proposed (the diff of what landed is what the person needs, after fuzzy matching and indentation fixes); a diff in the model's tool result (the model wrote the patch; its context is not the place for a copy); the diff in the journal (the before and after are already kept for undo).

## D-077 Ctrl+C twice at the prompt ends the session
- **Date**: 2026-11-07 · **Status**: confirmed (item 38)

## D-080 Which of an MCP server's tools are offered
- **Date**: 2026-11-07 · **Status**: confirmed (item 41)
- **Background**: every tool a server listed was offered, up to a hundred. ## D-081 MCP servers reached over streamable HTTP
- **Date**: 2026-11-07 · **Status**: confirmed (item 42)
- **Background**: a server was a program Foundry started and spoke to over stdio. Many now run elsewhere -- a team's docs or tickets server, a hosted service -- and are reached at an address; codex's `[mcp_servers.<name>]` takes `url` and `bearer_token_env_var` for them, over the protocol's streamable HTTP transport.
- **Decision**: `url = "https://..."` in place of `command` (with `command`, `args`, `env` or `env_vars` it is refused: a server is a program Foundry starts or an address it reaches), and `bearer_token_env_var = "NAME"`, the environment variable holding a bearer token. Each message is a POST of its own accepting JSON or an event stream; the reply to a request is one JSON body or the event in the stream that answers it, and a request of the server's own inside the stream gets a ping and nothing else, answered with another POST, as over stdio. The session id the server hands out at initialize, and the protocol version agreed there, go with every message after it; closing the session sends DELETE so the server ends it too, not waited for past two seconds. A 404 for the session means the server ended it: the server is stopped (`/mcp` says so) and its tools fail until a new session, as when a program exits. The rest is shared with stdio -- tool names, `enabled_tools` and `disabled_tools`, the policy (a mutator unless `read_only = true`), the timeouts, Ctrl+C, the 8 MB bound (per JSON body, per event), truncated results -- and the requests go through the client the model's do, so the proxy settings and the Windows certificate store apply.
- **The token**: read from the environment when the server starts, held in memory for the Authorization header only, and registered with the redactor, so a server that echoes it, or an error that quotes it, shows `[redacted]`. A variable that is not set costs the server, and says so; a value a header cannot carry is refused without being quoted (http.client's own error would quote it). It is sent only over https or to this machine: `http://` to another host with a token is refused when the config is read, as is a user name or password in the url. `bearer_token_env_var` must look like a variable's name, and its refusal does not echo it, in case the token itself was pasted there. `/mcp` shows a url server's scheme and host, not its path or query, either of which may carry a secret.
- **Cancellation**: http.client cannot interrupt a read, so each request runs on a thread of its own while the caller waits, watching for Ctrl+C and the timeout. On either the server is told (`notifications/cancelled`, sent in the background) and the connection cut by closing its socket's handle -- on Windows a socket shut down does not wake a read blocked on it.
- **What it may not weaken**: a url server is named where a program is -- the user's own config, never a repository's (D-043); its output is untrusted content and its tools are under the policy, as before.
- **Rejected for now**: `http_headers` and `env_http_headers`; OAuth (`codex mcp login`); the GET stream for messages a server starts on its own (Foundry offers a server nothing to ask for); re-initializing a session the server ended (a new Foundry session does it).

## D-082 `foundry mcp list | add | remove`
- **Date**: 2026-11-07 · **Status**: confirmed (item 43)
- **Background**: a server was added by writing an `[mcp_servers.<name>]` table into config.toml by hand, and the configured servers were seen only from inside a session (`/mcp`). A codex user runs `codex mcp add NAME -- COMMAND` (or `--url URL --bearer-token-env-var VAR`), `codex mcp list` and `codex mcp remove NAME`.
- **Decision**: the same three. `foundry mcp add NAME [--env KEY=VALUE] [--env-var NAME] [--read-only] -- COMMAND [ARGS...]` -- everything after `--` is the command, its own options included -- or `foundry mcp add NAME --url URL [--bearer-token-env-var VAR] [--read-only]`, into the user's own config.toml only. `foundry mcp list [--json] [--profile NAME]` lists the servers a session would start, as `/mcp` shows them -- a program, not its arguments; an address's host, not its path; the variables passed through and the token's variable by name; any `enabled_tools`/`disabled_tools` -- without starting any (`/mcp` says how each is). `foundry mcp` alone lists; `foundry mcp remove NAME` takes one out.
- **Editing the user's file**: the standard library reads TOML and does not write it, and the file's comments and layout are the user's, so an edit is text: a table appended (in the file's own line ends), or one server's tables -- its subtables such as `env` too, with comments right under it and the comment block set apart just above it -- taken out. It is checked before anything is written: the settings go through the same checks as reading them, and the edited text must parse to exactly the old settings with that one server added or gone. Otherwise it is refused and the file left as it was; a server written another way (inline, dotted keys, under a profile) is the user's to change by hand. The file is replaced in one step (a temporary file beside it, then a rename), so a failure never leaves half of one.

Only the user's own config is ever written, as before (D-043).
- **Found on the way**: answering `always` wrote its rule's pattern into config.toml unquoted, so a command with a quote in it (`echo "hi"`) left a file that no longer parsed and every later start failed; it is now written as a TOML string. And the empty `/mcp` line printed "an  table": `[mcp_servers.NAME]` was taken for markup and vanished; it is escaped.
- **Rejected**: `codex mcp get` (the listing shows the same); `mcp login` (no OAuth, D-081); overwriting a server of the same name on add (it is refused, naming `remove`).

## D-083 Which variables a command gets
- **Date**: 2026-11-07 · **Status**: confirmed (item 44)
- **Background**: a command -- the model's `run_command`, the user's `!COMMAND` -- got a fixed list: what a build needs (PATH, the system and profile folders, the proxy and certificate variables, toolchain homes, `PYTHON*`, `PIP_*`, `NPM_CONFIG_*`, `NUGET_*`, `DOTNET_*`, `MSBUILD*`), never a credential-shaped name. ## D-084 Where a backend's key, headers and query come from
- **Date**: 2026-11-07 · **Status**: confirmed (item 45)

## D-085 Retries you can see, and none that cannot help
- **Date**: 2026-11-07 · **Status**: confirmed (item 46)
- **Background**: a model request that failed in a way worth trying again -- a 429, a 5xx, a dropped or refused connection, a stream that failed before its first event -- was retried up to `request_max_retries` times, waiting as Retry-After asked or 1s, 2s, 4s, up to a minute a try, and said nothing while it did. A gateway shedding load looked exactly like a hang, and a person watching could not tell a slow model from a server answering 503. codex says "Reconnecting... 2/5" as it retries. And OpenAI answers a spent quota (`insufficient_quota`) with a 429 too: taken for a rate limit, it was waited out four times, then reported as "provider unavailable".
- **Decision**: `retry_with_backoff` (and `open_retrying_stream`, through it) takes `on_retry(exc, attempt, attempts, delay)` and calls it before each wait -- not after, since the wait is what has to be explained -- with the number of the try about to be made and the wait actually taken (Retry-After, capped at a minute). Each of the three backends takes `on_retry` and passes it to both its paths; the runtime sets it to its own when it is made. The runtime says `server error (HTTP 503); retrying in 4s (try 2 of 4)` as a warning notice -- in the terminal, and as a `notice` event in `exec --json` -- and journals a `model_retry` record (`attempt`, `attempts`, `delay`, and the reason with the provider's own words, as an error is reported). `foundry report` counts them (`model retries`, `model_retries` in `--json`). A 429 whose body says `insufficient_quota` is `QuotaExceeded`, which is not transient: it is tried once, and the task ends `blocked` with the reason -- blocked, not failed, as nothing about the task went wrong.
- **What it may not weaken**: the notice passes the event sink's redactor and the record the journal's, as every other one does. A resume ignores `model_retry` records, which sit between a request and its response.
- **Not changed**: what is retried, how often and how long it waits; a stream that fails after its first event is still not retried, since deltas have been shown.

## D-093 Tab completion for the shell
- **Date**: 2026-11-07 · **Status**: confirmed (item 54)

## D-095 The model's context window on every protocol, and compaction before it is full

## D-103 Foundry as an MCP server: `foundry mcp-server`, as codex's
- **Date**: 2026-11-07 · **Status**: confirmed (item 64)
- **Background**: codex runs as an MCP server (`codex mcp-server`), so another agent or an editor can hand it a task as a tool call. Foundry could be driven only from its own command line: `exec` was the nearest thing, a process per task, and an agent that wanted to go on with a session had to start another with `exec --resume`.
- **Decision**: `foundry mcp-server [-m MODEL] [--mode MODE] [-c KEY=VALUE] [-p PROFILE]` speaks MCP over stdio (a JSON-RPC message a line; protocol versions 2025-06-18, 2025-03-26 and 2024-11-05) and offers two tools, as codex's `codex` and `codex-reply`: `foundry` (`prompt`, and `cwd`, `model`, `profile`, `mode`, `config`) starts a session on the task and answers once it has ended; `foundry-reply` (`sessionId`, `prompt`) gives a session another task -- the one the server holds open, or, when it no longer holds it, the session resumed from its journal as `exec --resume` would. The answer is the session's last word (finish's summary, or its reply) and a line with its id and how it ended; `structuredContent` carries `sessionId`, `status`, `text` and any `reason`; `isError` marks only a task that could not be worked on (blocked or failed). The command line's settings are every session's defaults and a call's own win; `config` takes what `-c` takes, as typed values. With a `progressToken`, each tool call the task makes is a progress notification.
- **A task runs as exec runs one**: nobody is asked to approve anything, so what the permission mode would ask about is refused. `mode` is `dont_ask` (the default), `plan` or `accept_edits` -- `default` is refused, as exec refuses it, and a configured mode never decides. A repository's own instructions are not loaded until the folder has been trusted interactively, and only `finish` reports a task completed.
- **While a task works**: each `tools/call` runs on a thread of its own, so a ping is answered and `notifications/cancelled` stops the task. The cancel reaches the task where it is: the runtime now checks for it between the pieces of a model's answer and before each of the answer's tool calls, and a running command, search or MCP call polls it through `ToolContext.cancelled`, which nothing had set. A cancelled request is not answered, as the protocol asks; the session goes on with the next reply. One task at a time in a repository (by its Git top level), so no session patches a file another is changing under it. Up to 8 sessions are held open; past that the one least recently used is closed, and a reply resumes it. When the client's input ends, the tasks at work are cancelled and waited for up to 10 seconds, and every session is closed.
- **stdout is the protocol alone**: the sessions' display goes to stderr, and so does anything else that writes to stdout -- `sys.stdout` and the descriptor are pointed there, so a print or a process that inherits it cannot break a message. A process Foundry starts reads its stdin from nowhere: on Windows, git started while the server waited for the client's next line hung on the pipe they shared, until it timed out.
- **Not done**: approvals asked of the client (codex sends an elicitation request; Foundry refuses instead, as exec does); codex's `codex/event` notifications of every event; images; `--output-schema`'s result; the HTTP transport.

## D-111 A url server's own headers

## D-115 Lifecycle hooks, as codex's: PreToolUse and PostToolUse
- **Date**: 2026-11-07 · **Status**: confirmed (item 76, the first part of codex's hooks)
- **Background**: codex runs the user's programs at points in a turn -- before and after each tool call, when a prompt is sent, when a turn stops -- named in a `hooks.json` beside each config layer or in `[hooks]` tables of `config.toml`, each told the moment as JSON on its stdin and answering in JSON on its stdout. Teams use them for command policies, a linter after an edit, a log of what ran. Foundry read none of it, and a `config.toml` holding `[hooks]` stopped the load as an unknown table (D-091). (codex no longer keeps a list of known-safe commands that run unasked -- it leaves that to its sandbox and its `.rules` files -- so Foundry adds none.)
- **Decision**: `hooks.json` in the Foundry folder and `[hooks]` in the user's `config.toml` or a profile, and the same beside the machine's `policy.toml`, read in codex's format: events; matcher groups, whose `matcher` is `*` or empty for every call, names joined by `|`, or else a regular expression searched for; handlers of `type = "command"` with `command`, `commandWindows` (`command_windows`), `timeout` (seconds, 600), `async`, `statusMessage` and `additionalContextLimit` (tokens, 2,500, 0 for no cut). Two events run. `PreToolUse`, before a call reaches policy, refuses it with `permissionDecision: "deny"` and a reason, codex's older `decision: "block"`, or exit code 2 and a reason on stderr, and rewrites it with `"allow"` and `updatedInput`. `PostToolUse`, after a tool gave its result -- not after one that raised, was refused, or `finish` -- puts the reason of a `decision: "block"`, or of `continue: false`, in place of the result. Either adds its `additionalContext` to the result as a note from the hook, whichever way the call ends; a `systemMessage` is a warning. What codex parses and does not act on (`ask`, `allow` without a rewrite, `approve`, `suppressOutput`, a reason with no decision) is a failed hook, as there. A hook is told codex's names: `Bash` for `run_command`, which a matcher may also call by Foundry's name, and `apply_patch`, matched by `Edit` and `Write` too, with the patch as `tool_input.command`; other tools by their own names and arguments. The hooks that match start together; one that cannot start, fails, times out or answers in a shape it does not know is a warning and the call goes on, as codex has it. A refusal is the policy pipeline's step 1, journaled as a `policy_decision` of rule `hook.PreToolUse`; each event's runs are a `hook` record. `/hooks` lists the hooks with each one's file.
- **What carries it**: a hook is a program, so only the user's own files and the machine's policy name one -- a repository's `config.toml` may not, and its `.foundry/hooks.json` or `.codex/hooks.json` is not read -- and, read only from there, nothing waits on codex's review by hash (codex's `hooks.state` record of that review is refused with a reason, so a hook turned off there is not run here unawares). A hook can refuse or change a call and never let one through: a rewrite is validated as the model's call was, then goes through the breaker, the rules, the mode and the approval like any call, and the model is told what ran; two hooks rewriting one call differently refuse it. On Windows it runs as codex's do, `cmd /C "<command>"`, with `/S` so the outer quotes are the ones removed whatever the command holds and `/D` so no AutoRun command runs first; in the workspace, with the command environment (credential-shaped variables left out, `shell_environment_policy` applied) and `NoDefaultCurrentDirectoryInExePath`, so the program a command names is the one on PATH and not one a clone put in the workspace (D-049); under a job object, ended with its process tree at its timeout or when the session is stopped; its payload written on a thread, so a hook that prints much and reads nothing cannot hang the turn. The payload is scrubbed of the secrets Foundry knows string by string, before it is made JSON, and so is everything a hook says to the model, the user and the journal.
- **Not yet**: codex's other events (`UserPromptSubmit`, `Stop`, `SessionStart`, `SessionEnd`, `PermissionRequest`, `PreCompact`, `PostCompact`, `Interrupt`, the model-request ones) are refused by name until they run; `mcp_tool` handlers; an `async` hook runs to its end, its answer informing and never deciding, rather than in the background; `[features] hooks` and `--dangerously-bypass-hook-trust`.

## D-116 Lifecycle hooks, as codex's: UserPromptSubmit and Stop

## D-145 Memories, as codex's
- **Date**: 2026-11-09 · **Status**: confirmed (item 106)
- **Background**: codex keeps memories: with `[features] memories = true` it reads a user's earlier sessions once they have been idle a while, asks a model what a later session should know, merges what each one kept into a set of notes and a summary, and starts each session with the summary in its instructions; `[memories]` tunes it, and `/memories` decides, for the current chat, whether it uses them and is read for them. Foundry took `memories = false` and refused `true` (D-144), and refused `[memories]` as a table no code reads (D-091).
- **Decision**: `features.memories` (off by default, as codex's) turns them on, and `[memories]` is read from the user's own layers -- a repository's config may not set it. A pass reads each of the workspace's recorded sessions that has been idle `min_rollout_idle_hours` (6, 1 to 48), is no older than `max_rollout_age_days` (30, 0 to 90), has had a model answer, is not in use, and has grown since it was last read -- the newest `max_rollouts_per_startup` (16, 1 to 128) of them -- and asks the model (`extract_model`, or the session's) what a later session there should know, or `NONE`; a session that could not be read is not tried again until it changes, one the model failed on is. The newest `max_raw_memories_for_consolidation` (256, 1 to 4096) sessions' memories are kept, and when any changed they are merged (`consolidation_model`, or the session's) into the notes (`MEMORY.md`) and a summary of at most 300 words (`memory_summary.md`). A session in a trusted workspace starts with the summary in its instructions, as notes from earlier sessions that may be out of date and are not instructions, with the read-only `read_memories` to read the notes in full (a sub-agent gets the same); `use_memories = false` leaves them out, `generate_memories = false` keeps a session from being read, and `disable_on_external_context` (codex's older `no_memories_if_mcp_or_web_search`) skips a session that called an MCP tool or read an MCP resource. Unlike codex's, memories stay with the workspace they came from -- one folder for each under the Foundry folder's `memories/` -- since a model reads a repository's files and what it keeps of one must not reach another's instructions; they are kept and given only in a workspace the user trusts, and what is written is scrubbed of every secret the redactor knows. The pass runs as codex's does, in the background at the start of an interactive session, as a process of its own that outlives it (`foundry memories update --quiet`, started with Python's `-P` from the Foundry folder, so nothing in the workspace is imported in Foundry's place), one at a time for each workspace; `foundry memories update` runs it now, `foundry memories show` prints the summary and the notes, and `foundry memories reset` forgets them -- the sessions before it are never read for them again, as codex's "Delete Codex memories". `/memories` says where they are, whether this session uses them and is read for them, and when the pass last ran; `/memories use on|off` changes what this session's instructions carry from its next message, and `/memories generate on|off` whether this session is read, journaled so the pass goes by the last one. codex's `version`, `dual_write`, `max_unused_days`, `min_rate_limit_remaining_percent`, `consolidation_service_tier` and `dedicated_tools` are refused, each saying what Foundry does instead.

## D-147 A failure the provider reports inside an answer is asked again
- **Date**: 2026-11-10 · **Status**: confirmed (found in P1, D-146)
- **Background**: OpenAI-family providers report a failure part-way through a stream in the stream itself, in a 200 answer: the Responses API sends an `error` event (code and message at the top level) or `response.failed` (the error under `response`); OpenRouter sends an `error` beside a `finish_reason` of `"error"` and then closes the stream with `[DONE]` as usual; vLLM sends a chunk that is the error, its HTTP status as the code. A failed Responses answer that was not streamed answers 200 too. Played behind a local relay that injects these, the Chat Completions adapter kept the cut answer -- "Let me loo" -- as the model's whole one and lost the tool call it was making, which D-099 was written to prevent; the Responses adapter took any of them for a protocol fault and ended the run `failed`, and for the API's own error event reported `provider reported a failure: {}`, having looked for the message under a key that event does not have. A failed answer that was not streamed was an empty turn.
- **Decision**: one classifier, `raise_reported_error` in `backends/base.py`, for both OpenAI-family adapters. A used-up quota (`insufficient_quota`, as code or type) is `QuotaExceeded` and stops the task blocked, as D-085's 429 does. `context_length_exceeded`, `invalid_prompt`, `invalid_request_error` and `usage_not_included` -- or an integer code below 500 other than 429 -- are a `FatalError`: the task fails at once. Every other code, one Foundry has never seen included, is a `StreamDropped`, and the runtime asks the turn again as D-099 does, saying "the provider reported CODE mid-turn: MESSAGE" (or "in its answer"); codex retries the same way. "try again in 1.5s" (or "250ms") in the message is a wait the runtime keeps to, never shorter than its own backoff and never past its 60-second ceiling. Claude's error events were already handled (D-099) and are unchanged.
- **What it may not weaken**: nothing of the failed answer is kept; a failure the request's own retries already had is not asked again on top of them; the cancellation and try-count rules of D-099 hold.

## D-148 A read-only task is not offered the tools it may not use

## D-149 What P1's second round found: unattended tools, and four small ones
- **Date**: 2026-11-10 · **Status**: confirmed (found in P1, D-146)
- **Background**: the second round of P1 played the model through a REPL session with `/compact` and `/undo`, a refactor under injected faults, MCP and hooks, and memories. The stand-in model reported, and its requests confirmed: (1) an unattended run offered an MCP server's tool that no rule allowed -- even a `read_only = true` server's still asks (D-043), and nobody could answer, so every call was refused at step 6; the same held for `apply_patch` and `run_command` when no rule allowed them; (2) the permissions paragraph said files with uncommitted changes "need explicit approval to edit" in a run where nobody can give it; (3) `list_files` documents its path as "Defaults to the root", yet `{"path": ""}` was refused as an empty path, as was `search_text`'s, and the memories feature then kept that as a workspace gotcha; (4) `search_text` stripped each line, so a model that wanted to patch a match read the file again for its indentation; (5) a command's output reached the model with `\r\n` line ends, which the REPL's own `!` output already normalized; (6) nothing said whether several calls in one reply run in order, which decides whether a test run sent beside a patch is evidence for it.
- **Decision**: `PolicyEngine.may_allow(tool, kind)` says whether some call to a tool could be allowed as things stand, and a request offers only those tools: a read-only task's mutators are out (D-148, now through the same method), and where nobody can approve -- `dont_ask`, or `interactive` off -- so is a tool no allow rule names by name or pattern, no session grant covers and the mode does not allow. It answers yes whenever the outcome turns on the arguments, which a request cannot know: an allow rule naming the tool keeps it offered even if a given call will not match it. A call to a tool left out is refused by the policy as before. The unattended paragraph says files with uncommitted changes are refused. An empty `path` is the root for `list_files` and `search_text`. `search_text` keeps a line's indentation and cuts 200 characters after it. `combined_output` turns `\r\n` into `\n`. The base prompt says calls in one reply run one at a time, in order.
- **Rationale**: as D-148 put it, offering a tool that can only be refused invites a turn spent on a refusal; the prompt already lists the allow rules, and a model still tries the tool it is offered. codex has no such gap because its sandbox, not approval, bounds an unattended run. The tool list follows the policy as it changes -- `foundry mcp-server` turns asking on once its client can answer (D-104) -- so a prompt cache sees it change where the system prompt already does. Not changed: the compaction request still carries the tools (a history holding tool calls is refused without them, D-040), a Stop hook's edit still makes earlier runs stale evidence (the evidence rule cannot tell which files a check covers), and a workspace that is not trusted still sends no FOUNDRY.md (D-041).
